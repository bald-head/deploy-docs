本教程以“邮箱与密码注册”为例，演示如何把一个功能交给 Agent，并核对它是否完成。先完成[快速上手](/skills/quickstart/)，在目标业务仓库中操作。教程里的功能、路径和验收是示例，实际方案以项目现状和已确认需求为准。

## 1. 描述结果与约束

在 Claude Code 或 Codex 中输入：

```text
为当前项目增加邮箱与密码注册功能，注册成功后进入已登录状态。
先检查已有认证、用户模型、页面、请求层和迁移方式。
复用适用的项目能力，核对必要的产品和安全边界，再给出完整功能计划。
```

Agent 应先定位现有实现，再处理会改变结果的未决问题，例如注册入口面向谁、是否需要邮箱验证、已有账号如何处理，以及注册成功后是否允许直接登录。仓库能查到的技术事实无需由你重新提供。

新功能完成必要研究、方案比较、产品定义、适用 UI/UX、架构和逐 Feature 技术选型。明确 Bug 或已有批准任务的续作不重复这套规划。

## 2. 核对计划中的完整功能

一项注册功能应同时覆盖页面与真实 API、用户数据、密码哈希、唯一性约束、认证会话、输入校验、异常恢复和适用权限。不能把只实现接口当成整个注册功能完成。

核对当前开发者唯一 TODO 中的条目：

| 内容 | 应能回答的问题 |
| --- | --- |
| 功能与入口 | Feature ID 是什么，用户从哪个页面或调用方进入 |
| 用户结果 | 注册成功后用户能做什么 |
| 契约与边界 | 输入、响应、会话、重复账号及异常如何处理 |
| 技术结论 | 选用哪些具名技术，为什么适合当前项目 |
| 依赖与写集 | 前置功能是否就绪，允许修改哪些目录和资源 |
| 验收与交付面 | 数据、API、页面、安全、联调和验证是否完整 |

可以这样要求补齐：

```text
把注册功能按一个完整 Feature 写入我的唯一 TODO，
覆盖真实页面、API、数据、会话与异常处理，并给出可观察的验收条件。
```

示例验收应由项目实际需求决定，例如：

| 验收 | 可观察结果 |
| --- | --- |
| AC-001 | 合法输入提交后建立账号，页面进入约定的已登录状态 |
| AC-002 | 重复账号按项目安全策略响应，不创建第二条账号记录 |
| AC-003 | 非法输入在适用层被拒绝，页面显示对应状态 |
| AC-004 | 请求失败时有可恢复的反馈，不误显示注册成功 |
| AC-005 | 数据库保存密码哈希，响应和日志不包含明文密码 |

已有具名技术结论直接复用；“沿用现有技术”只是采用方式，不替代具体技术选择。

## 3. 开始纵向实现

计划明确后输入：

```text
开始实现已批准的 USER-REG 功能。
核对当前 TODO、项目记忆和技术结论，完成全部适用交付面。
本轮复用已有检查，不新增测试源码。
```

当前实例先通过 TODO 状态机领取该 Feature，确认依赖和写集。再由适用专业 Skill 配合完成实现：

- 数据表、约束、迁移和回滚：`database-design` 与 `database-ops`。
- 请求校验、业务契约和错误语义：`api-development`。
- 认证、权限及数据保护：按已有技术采用对口安全能力。
- 注册页面、真实接口调用和加载、失败、成功状态：`ui-pc` 或 `ui-app`。
- 跨层实现与统一收口：适用时由 `dev` 组织。

这些是功能的内部交付面，不是多个可单独宣布完成的 Feature。不要把教程里的示例技术栈或伪代码直接复制进未知项目。

## 4. 让验证对应验收

```text
运行当前项目适用的已有检查，并通过真实注册入口验证上述验收。
分别说明构建、接口和页面主路径实际验证了什么，未覆盖的内容如实列出。
```

Agent 应使用项目真实启动与检查命令，确认页面调用的是实际后端。验证覆盖成功、重复账号、非法输入和请求失败等已批准行为；数据层另核对哈希、约束和迁移。

已有测试可以运行。只有你本轮明确要求写或改测试源码时才使用 `test-development`；设计测试策略或用例则使用 `test-strategy`，两者不是同一个授权。构建通过不能代替页面和接口的真实验收。

## 5. 审查并修复

```text
对 USER-REG 的完整 diff 做一次 code-review，
核对功能验收、认证与数据边界，并修复严重和重要问题。
```

Review 应覆盖本次全部适用交付面。修复后定向复核 findings 和受影响路径，不重复整份审查。验收证据不足时保留未完成状态，说明具体缺口。

## 6. 按授权交付

需要提交和推送时明确说明：

```text
把 USER-REG 的业务改动、必要文档和唯一 TODO 的完成状态一起提交，
并推送到当前已配置的 upstream。只包含本次功能范围，随后核验远端。
```

在有效 Git 授权内，先把真实验收与 Review 摘要写入 TODO，由状态机准备 `[x]`；再将业务文件和该 TODO hunk 放进同一个功能提交并推送。远端核验后才解锁依赖，不另建一次“事后更新 TODO”的提交。

本地实现与 Git 交付不代表已部署到服务器。需要发布时按项目发布流程和对应授权执行。

## 7. 中断后继续

继续同一仓库的当前 TODO，可以直接说：

```text
读取我的唯一 TODO，继续 USER-REG，先核对已有改动与未完成验收。
```

需要恢复另一段 Claude Code 或 Codex 历史时，使用[历史会话接续](/skills/usage/session-resume/)；单纯继续当前 TODO 不读取另一段历史。

后续按任务查[使用指南](/skills/usage/)，并行条件见 [TODO 管理](/skills/usage/todo-management/)，Git 细节见 [Git 操作指南](/skills/usage/git-workflow/)。
