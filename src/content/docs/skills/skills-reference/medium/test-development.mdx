## 用途

`test-development` 只在用户本轮明确要求写、补或修改测试源码时实施最小测试改动，包括相关 fixture、快照和配套资产。运行已有检查、分析测试失败或查看覆盖率不触发它。

## 如何表达请求

| 请求 | 是否进入测试源码实施 |
| --- | --- |
| 给订单状态转换补单元测试代码 | 是，按指定被测对象实施 |
| 修改这个错误的测试断言 | 是，先核对实际契约 |
| 给该接口追加鉴权集成测试 | 是，复用已有测试框架与目录 |
| 运行已有测试，不新增文件 | 否，直接执行现有命令 |
| 看一下为什么测试失败 | 否，先诊断原因 |
| 设计一个测试方案 | 否，使用 [`test-strategy`](/skills/skills-reference/medium/test-strategy/) |

覆盖率不足、Review finding、CI 门禁或旧 TODO 的测试事项不替代本轮测试源码要求。“不要写测试”也不会因句子中出现“写测试”而被忽略。

## 使用示例

```text
为当前订单取消规则补单元测试代码，覆盖允许取消、禁止取消与重复取消。
复用仓库已有框架和测试文件，依据实际契约编写，并运行本次修改的测试。
```

## 实施过程

1. 明确被测对象、已批准契约和本轮授权的测试范围。
2. 读取现有测试目录、框架、fixture、隔离方式和运行命令。
3. 选择有判别力的层级与断言，优先扩展已有测试，不机械镜像实现。
4. 控制数据库、网络、时间、账号和资源副作用，沿用现有隔离与清理方式。
5. 执行受影响测试，报告通过、失败与未执行内容，并按实际证据说明边界。

找不到可运行测试栈时先说明缺口，不生成无法执行的模板。测试暴露生产问题时交给对应实现 Owner，不能把单独的测试请求扩成未授权业务改动。

## 结果怎么判断

测试应能区分目标行为正确与错误，断言来自契约而非当前实现的偶然细节。单元测试不证明跨模块集成，mock 接口测试不证明真实网关、数据库或页面已联通。

报告修改路径、运行命令、实际结果与覆盖边界；没有运行就明确未运行，不预填“通过”。真实浏览器业务流程使用 [`real-browser-automation`](/skills/skills-reference/medium/real-browser-automation/)，完整 diff 审查使用 [`code-review`](/skills/skills-reference/high/code-review/)。
