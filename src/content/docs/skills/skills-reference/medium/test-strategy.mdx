## 用途

`test-strategy` 只在用户本轮明确要求设计测试方案、策略或用例时使用。它根据验收、仓库事实和真实风险选择验证层级，说明每项证据能支持什么结论。

它出方案，不写测试源码，不替代普通开发验证、缺陷 Review 或 Bug 诊断。方案里提出新增测试，也不自动获得实施授权。

## 使用示例

```text
请为订单导出设计测试方案和用例，重点覆盖筛选范围、租户隔离与大数据量。
先检查现有实现和已有检查，说明每个场景的输入、预期、取证方式与未覆盖边界。
本轮先出方案，不修改测试代码。
```

“运行已有检查”“看看覆盖率”“这个测试为什么失败”不进入策略设计。明确要求写或改测试源码时使用 [`test-development`](/skills/skills-reference/medium/test-development/)。

## 方案包含什么

| 内容 | 应说明的事实 |
| --- | --- |
| 验收与风险 | 对应的用户结果、契约、权限、数据或异常风险 |
| 真实消费者 | 哪些页面、接口、后端或外部调用方受影响 |
| 场景 | 前提、输入、动作与可观察的预期结果 |
| 取证方式 | 复用现有检查、真实请求、浏览器操作或需另行实施的测试源码 |
| 环境与隔离 | 账号、数据、设备、时间与清理条件 |
| 未覆盖边界 | 尚缺的服务、权限、设备或真实业务证据 |

已有需求、验收或实现至少提供一个明确依据；证据不足时列出缺口，不套用与任务无关的通用场景矩阵。

## 证据与结论对应

| 证据 | 适用结论 |
| --- | --- |
| 编译或类型检查 | 对应构建或类型约束通过 |
| 单元测试 | 被隔离逻辑符合已覆盖的契约 |
| mock 契约检查 | 模拟边界下的请求与响应满足预期 |
| 实际组件集成 | 已验证环境中的协作路径成立 |
| 真实页面、设备或外部流程 | 实际执行的用户路径符合预期 |

不能用低层结果代替高层验收。人工步骤写明执行条件和证据要求，尚未执行时保持未验证；交接文档完成不等于设备或业务流程已通过。

方案保持与风险相称。范围简单时可以给出简短、可执行的验证步骤，不扩成独立报告；结论交给 Feature Owner，本 Skill 不改 TODO 状态或执行 Git。
