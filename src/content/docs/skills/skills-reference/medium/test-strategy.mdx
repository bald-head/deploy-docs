## 概述

"这个功能要怎么测"如果没人问，就不该有答案。给每个功能都配一套成功 / 失败 / 边界 / 权限四件套，代价是团队从此不再相信"测试通过"这四个字——因为里面绝大部分测试从来没照出过任何东西。

`test-strategy` 把测试方案从"流程里的固定环节"改成"你点名才启用的入口"。启用之后它替你固定的是一件更要紧的事：**每一级证据能撑住什么说法、撑不住什么说法**，让汇报里的"通过"重新变得有含金量。

它出方案和用例，不写测试代码，不找缺陷，也不维护任务状态。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这个功能怎么测" | 动手前先想清验证路径 |
| "帮我设计测试用例" | 需要场景清单和取证方式 |
| "出个测试方案" / "测试计划" | 需要分层选择和覆盖边界 |
| "要测哪些" | 从需求和风险里挑真正值得测的 |
| "测到什么程度算够" | 需要确定证据等级，而不是一个覆盖率数字 |
| "这个跨端功能怎么保证两边都对" | 生产者与消费者的一一对应 |
| "真机那部分怎么交给测试同学" | 人工验收的交接步骤 |

<Aside type="danger">
两条边界，混淆任何一条都会付出代价。

**它不会被自动叫起来。** 普通开发、修 Bug、日常验证、Review 的高风险 finding、里程碑提测——都不触发它。原因很直接：一旦每个功能都自动生成一份测试方案，方案就变成了没人读的附件，而真正需要设计的那几个功能反而混在里面看不见了。

**拿到方案不等于拿到写代码的许可。** 方案里标着"这里需要新增测试代码"，那是一条待办，不是一个已完成动作。要它真的写，你得另外开口——[test-development](/skills/skills-reference/medium/test-development/) 那边的门是独立的。
</Aside>

## 什么时候不要用

- **要真的把测试代码写出来** → [test-development](/skills/skills-reference/medium/test-development/)。
- **要找缺陷** → [code-review](/skills/skills-reference/high/code-review/)。日常开发发现问题的默认入口是 Review，不是测试方案。
- **要实现功能** → [universal-development](/skills/skills-reference/low/universal-development/)。
- **要定位一个具体 Bug 的根因** → [bug-detective](/skills/skills-reference/high/bug-detective/)。
- **要定产品需求** → [product-manager](/skills/skills-reference/critical/product-manager/)；**要做架构设计** → [architecture-design](/skills/skills-reference/high/architecture-design/)。

## 前置条件

**你这一轮开口了。** TODO 里写着"设计测试"不算——那是上一轮的产物，不是这一轮的要求。

**手上至少有需求、验收标准或已写好的实现之一。** 三样全无的时候设计出来的只能是通用模板，指不向任何真实风险。你能给的越具体，方案里能被删掉的通用条目就越多。

它不改任务状态。已经有 TODO 在跑时，它只把结论交给负责人，不去替你勾选或新增事项。

## 一条贯穿全篇的原则

测试分层不是为了齐全，是为了知道每一层能说什么话。

一次静态检查通过，能说的是"能编译、类型对得上"，不能说"业务是对的"。一组 mock 契约测试通过，能说的是"请求结构和错误分支符合约定"，不能说"数据库事务没问题"。一次集成测试通过，能说的是"在这个测试环境里几个组件配合正常"，不能说"生产网络下也是这样"。

所以方案里每条场景都带两样东西：打算用哪种取证方式，以及**这条证据不能替你回答什么**。低等级的结果不能用来关掉高等级的门禁——这一条听起来抽象，但它决定了你的验收结论可不可信。

## 使用示例

### 场景 1：实现前先想清怎么验

**你的输入**：

```text
下一个要做的是「优惠券叠加下单」。实现前先给我个测试方案，我想知道哪些地方必须测。
```

**你会拿到的产出**（直接在回复里，不落文件）：

```text
## 真实风险（来自 PRD#优惠券叠加 + 现有 OrderService）
R1 金额算错（叠加顺序、精度、归零）——直接资损
R2 券被重复使用（并发下单）——直接资损
R3 越权用别人的券——数据边界
R4 券失效后仍可下单——状态时序

## 场景与取证方式

S1  叠加顺序与精度              R1
    取证：新增单元测试（需另行授权）
    这条证据不能说明：真实下单接口的整体行为

S2  同一张券并发下两单只成功一次   R2
    取证：新增集成测试 + 数据库唯一约束（需另行授权）
    这条证据不能说明：多实例部署下的分布式竞争

S3  携带他人券 ID 下单被拒        R3
    取证：复用已有 OrderControllerTest 的鉴权用例，追加一条
    这条证据不能说明：网关层的令牌校验

S4  券在下单瞬间过期             R4
    取证：一次真实主路径验证 + 可控时钟（无需新增测试源码）
    这条证据不能说明：跨时区场景

## 不建议覆盖的
券列表分页、券名称文案、优惠说明的样式——
Review 能直接判定，机械补四件套只增加维护面。

## 本方案不能支持的结论
不能支持「优惠券功能已完整验收」。缺的是真实支付回调链路，
那部分要么在联调环境走一次真实下单，要么标为待人工执行。

## 状态
未执行任何命令。S1 / S2 标为需另行明确授权才可新增测试代码。
```

### 场景 2：跨端功能怎么保证两边都对

契约一改，改的那一端总是最先被想到，被漏掉的永远是另一端。方案会把两边一起列出来：

**你的输入**：

```text
用户详情接口的返回结构要改，加了 avatarUrl，去掉了 nickname。
Web 和 App 都在用。怎么测？
```

**你会拿到的产出**：

```text
## 生产者 / 消费者矩阵（featureId: USER-PROFILE-V2）

契约变化      UserDetailDTO：+avatarUrl，-nickname

生产者
  backend    UserController.detail()        必测：新字段有值、旧字段确实移除
  数据库      user 表新增 avatar_url        必测：迁移后旧数据默认值

消费者
  Web        src/web/pages/profile/         必测：不再引用 nickname，头像位有兜底
  App        src/app/screens/Profile/       必测：同上 + 旧版本客户端兼容
  导出任务    jobs/user-export.ts           必测：模板里 nickname 已替换

## 缺口
App 端目前只有 fixture 测试，没有真实接口联调证据。
只有 fixture 通过时，能说的是「App 能渲染新结构」，
不能说「App 与真实后端已联通」。

## 结论
在 App 拿到真实接口证据之前，这个功能保持未完成状态——
不是因为流程要求，是因为漏掉的那一端上线就是白屏。
```

### 场景 3：真机那部分怎么交出去

有些证据只能人来取：真机权限弹窗、弱网、专用硬件首次推理、真实样本效果。方案会给可执行的交接件：

```text
## 人工交接：扫码登录（真机）

环境      iOS 17.4 / Android 14，各 1 台真机；测试包 build 2891
账号      qa-scan-01 / qa-scan-02（已在测试环境开通）
前置      清除应用数据，确保首次授权弹窗会出现

步骤
1. 首次进入扫码页 → 期望：出现相机权限弹窗，拒绝后给出可点击的引导
2. 授权后扫描 5 秒内失效的二维码 → 期望：明确提示已失效，可重新扫描
3. 弱网（Network Link Conditioner，3G）下扫描 → 期望：不重复提交，
   超时后给出可重试入口
4. 后台切前台 → 期望：相机恢复，不黑屏

证据模板
  步骤号 / 设备与系统版本 / 截图或录屏 / 实际结果 / 与期望的差异

## 状态
待人工执行。交接件已备齐 ≠ 已验收；在拿到上表证据之前，这几条都是未验证。
```

### 场景 4：它拒绝机械补齐的样子

```text
你：给「用户列表加一列创建时间」出个测试方案。

它：这个不值得单独出方案。改动是一列展示字段，没有业务规则、
    没有权限变化、没有状态流转，Review 就能判定对不对。

    建议的验证方式：跑一次受影响范围的现有命令（前端 typecheck +
    列表页一次真实打开），确认时间格式与时区符合仓库既有约定即可。

    如果这一列涉及排序或筛选，那才有真实风险，我再出方案。
```

<Aside type="note">
合法但极端的业务值不该仅因为"看起来不正常"就被判为异常。金额可以是 0，数量可以是一万，日期可以是十年后——范围校验的依据是明确写下来的业务规则，不是写测试的人的直觉。方案里出现范围断言时，它会一并注明依据来自哪一条规则。
</Aside>

## 场景库

需要更完整的场景清单时，它会按需读 `references/product-test-scenarios.md`——里面覆盖成功路径、替代路径、边界、错误、权限、并发与幂等、兼容、可访问性、埋点这些实际会出问题的面。它是候选池，不是清单模板：只挑当前功能真的有风险的那几类，不逐项填满。

## 常见坑

**用覆盖率当验收标准。** 覆盖率回答的是"哪些行被执行过"，不回答"哪些风险被证明了"。一个把 getter 全测一遍的 90%，价值低于一个覆盖并发扣减的 40%。

**方案里的"需新增测试代码"被顺手实现了。** 那一条是给你做决定用的。被自动实现之后，你既没做决定，也多了一份不知道要不要维护的测试。

**汇报时把证据升一级。** "集成测试通过"写成"功能已上线验收"，"fixture 渲染正常"写成"端到端联通"。后果不是这一次汇报不准，而是下一个人会跳过真实验证，因为他以为已经做过了。

**给每个改动都配四件套。** 字段映射、样式、文案、静态结构——这些 Review 一眼就能判。给它们配测试的真实成本是：以后每次改文案都要改测试。

**交接件当验收证据。** 人工交接文档写得再齐，没有设备和证据回来之前，那几条都是"待人工执行"。

## 最佳实践

- **实现之前叫它。** 事后补方案能做的只是给已有证据分类；事前叫它才能影响你怎么实现。
- **把真实风险说出来。** "这块涉及钱"或"这块之前出过一次事故"，会让方案的重心完全不同。
- **要执行就明说。** 默认它只出方案、标"未执行"。要它跑现有验证，你说一句就行，跑完给你实际命令和结果。
- **重点看"本方案不能支持的结论"那一段。** 那是整份方案里最省事的部分——它直接告诉你还差什么才能说"验收通过"。
