## 用途

`store-pc` 按目标仓库已有状态方案设计、实现或排查 PC/Web 的共享状态、Store、selector、Hook/composable 和跨页恢复。

它处理客户端内存与适用的浏览器持久化。后端表、ORM 与数据持久化使用 [`database-ops`](/skills/skills-reference/high/database-ops/)，不要仅凭“存用户信息”就选择前端 Store。

## 使用示例

```text
订单筛选条件在列表和详情页之间需要保留，退出登录后必须清空。
先定位现有 Store、路由 query 与请求缓存，复用已有方案实现，
核对账号切换、刷新恢复和旧请求覆盖新请求的情况。
```

```text
这个 composable 的订阅在切页后没有释放，请检查生命周期和共享状态归属。
```

## 先判断状态归属

| 数据 | 常见落点 | 核对重点 |
| --- | --- | --- |
| 仅当前组件使用的开关、输入 | 组件本地状态 | 不因字段存在就提升为全局状态 |
| 需要分享和恢复的筛选视图 | 适用时使用 URL query | 沿用路由契约、解析和默认值 |
| 服务端数据与请求状态 | 已有请求或缓存层 | 避免再复制一份权威数据 |
| 跨组件或跨页面共享状态 | 已确认的 Store / Hook / composable | 读写 Owner、派生状态和清理边界 |
| 需要刷新恢复的偏好 | 项目已有持久化机制 | 版本、过期、损坏、配额和身份隔离 |

这些是判断依据，不是强制改用某个库。先从仓库确认 Pinia、Redux、Zustand 或其他实际方案；已有技术结论适用时直接复用，新增状态库才比较技术选择。

## 实现与验证

定位定义和调用方后，核对字段、动作、selector、派生值和 reset。异步请求区分加载、空、错和成功状态，按请求身份处理过期响应、取消、重试与卸载清理。

登出、账号或租户切换时按真实数据边界清理状态。持久化内容遵循项目安全约定，不能把上一身份的数据恢复到新身份，也不能把跨页共享当成后端授权。

验证至少覆盖当前改动涉及的状态转换与真实调用页面；复用已有检查，不因修状态而默认新增测试源码。发现需要改变后端契约、权限或已批准验收时，先定向更新范围。

页面实现见 [`ui-pc`](/skills/skills-reference/high/ui-pc/)，API 契约见 [`api-development`](/skills/skills-reference/high/api-development/)，新状态方案比较见 [`tech-decision`](/skills/skills-reference/high/tech-decision/)。
