## 概述

`doc-coauthoring` 不是"你说要什么，我给你生成一篇"。它是一个会主动追问的协作流程：先把你脑子里的上下文掏干净并问到自己真的懂了，再一节一节地发散、筛选、起草、返工，最后开一个**干净会话**当第一个读者来试读——因为写的人永远看不见自己留下的盲点。

它写的是要交给人看的东西：正式文档、提案、简历、法律草案。内部通知和沟通模板不走这里（见下一节）。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "帮我写个文档" / "起草文档" | 从零写一份要给人看的正式文档 |
| "文档协作" / "协作编辑" | 你有想法，但需要有人陪着逐节往下推 |
| "校对一下" | 要的是定位问题，不是重写一遍 |
| "改改这份稿子" | 已有草稿，问题在结构或论证层面 |
| "文案撰写" | 提案、说明、对外材料的成稿 |
| "帮我看看简历" | 简历评审与岗位适配 |
| "写个 NDA / 隐私政策" | 法律草案，只是草案，见下方硬边界 |

## 什么时候不要用

- **内部通知、状态更新、发布说明** → [internal-comms](/skills/skills-reference/low/internal-comms/)。那边是对内沟通的固定形态，这边是要署名交出去的正式稿。
- **产品需求文档** → [product-manager](/skills/skills-reference/critical/product-manager/)。PRD 的内容来自产品定义，不该在共创过程里现编。
- **项目文档目录还没建起来** → [init-docs](/skills/skills-reference/medium/init-docs/) 搭骨架，本 Skill 往里填内容。
- **代码注释、API 文档** → 这两类应该由代码和契约生成，手工共创只会让它和实现越走越远。
- **日报、开发过程文档** → [daily-report-writer](/skills/skills-reference/low/daily-report-writer/)、[development-process-doc-writer](/skills/skills-reference/low/development-process-doc-writer/)。它们从事实生成，不需要陪你打磨措辞。
- **中文读起来一股 AI 味，想去味** → [humanizer-zh](/skills/skills-reference/low/humanizer-zh/)。那是表达改写，不是内容共创。

## 前置条件

**得是一份要交给人看的文字成品。** 目标是成稿。把想法整理成几条 bullet 用不上这套流程。

**文档类型和读者要先说清。** 读者不定，详略、术语和论证顺序全都定不下来——所以第一阶段的第一个问题永远是"谁会读它"。

**这份东西值得来回改几轮。** 一次生成就能用的短文本，走完整流程是浪费。

## 三个阶段，你会看到什么发生

### 第一阶段 · 把上下文掏干净

它会先问一圈元问题：这是什么类型的文档、谁读、读完你希望发生什么、有没有格式或篇幅限制、哪些话不能说。然后请你把手里的材料一次性倒出来——邮件、聊天记录、旧版本、零散笔记都算——再用一组澄清问题跟你确认它理解对了。

这一阶段的产出不是文字，是一份双方一致的写作前提。

<Aside type="tip">
如果需求本身还没想清，或者有个会实质改变结果的决定悬着，先用 [grilling](/skills/skills-reference/medium/grilling/) 一次一个问题问到底；不知道该写哪些内容时先用 [brainstorm](/skills/skills-reference/medium/brainstorm/) 发散一轮。这两个都是它的上游。
</Aside>

### 第二阶段 · 一节一节往下推

它不会先铺完全文再回头改，而是每次只处理一节，每节都走同一个小循环：

```text
问清这节要承担什么 → 发散几种写法 → 筛掉不要的 → 起草 → 跟你来回改 → 过关 → 下一节
```

好处是每节都有明确的关口，你在早期就能把方向掰回来，而不是读完三千字才发现整篇的角度不对。

### 第三阶段 · 找一个没参与过的读者

环境支持子代理时，它直接开一个干净会话，把文档原样丢进去让它读；不支持就请你找个没参与写作的人读一遍。

关键在"没参与过"。带着写作过程记忆的读者会自动补全文档里其实没写的信息——你和它都已经不适合当第一读者了。发现误解就回到第二阶段改那一节，直到读者的理解和你的意图对得上。

## 使用示例

### 场景 1：一份对外提案

**你的输入**：

```text
帮我写份提案，说服客户把现在的批处理换成实时管道。
```

**第一阶段你会被问到的**：

```text
1  谁会读它？技术负责人，还是要签字的业务方？两者的说服路径完全不同
2  读完你希望对方做什么？立刻批预算，还是先同意做一次 POC？
3  他们现在最不满意的是什么？（这决定开篇第一句写什么）
4  有没有不能提的东西？比如上一次迁移失败的原因
5  篇幅和形式？两页纸、一封邮件，还是要配演示？
```

**第二阶段的推进方式**：

```text
[1/5] 现状与代价      草稿 → 你说"代价要用他们的口径" → 改 → 过
[2/5] 方案与边界      草稿 → 你补了两条约束 → 改 → 过
[3/5] 迁移路径        澄清：能不能双跑一段时间？ → 草稿 → 过
[4/5] 成本与风险      发散 3 种呈现方式 → 选表格 → 草稿 → 过
[5/5] 下一步          待写
```

**第三阶段的读者测试结论**：

```text
干净会话读完之后的反馈：
✗ 以为双跑期是 2 周，实际文中没写周期 → 已在第 3 节补上
✗ 把"降低延迟"读成了性能优化诉求，没读出合规动因 → 已改开篇
✓ 能准确说出你要对方批的是 POC，不是全量迁移
```

### 场景 2：只要校对，不要重写

**你的输入**：

```text
这份稿子帮我校一下，别动我的语气。
```

**你会拿到的产出**——每条都指到位置，说清是什么问题、会造成什么后果、最小怎么改：

```text
第 2 段第 3 句   逻辑   "因此"前后不构成因果，前句说的是成本，后句结论是合规
                        读者会在这里卡一下，怀疑你在偷换论据
                        最小改法：把"因此"换成"另一方面"

第 4 段          事实   "行业平均 3 天"没有出处
                        对外材料里这类数字会被追问，答不上来会削弱全篇
                        最小改法：补出处，或改成"我们观察到的多数情况"

第 5 段第 1 句   行文   58 字的长句，三个逗号后才出现主语
                        最小改法：在"而"处断句

第 7 段          语法   "部署到生产环境上" 多一个"上"
```

<Aside type="caution">
校对的时候它**不整篇重写**。重写会让你没法判断改了什么、为什么改，也会顺手抹掉你有意为之的表达——包括那些看起来别扭但其实是故意的措辞。
</Aside>

### 场景 3：简历与法律草案

简历评审基于你的真实经历和那份 JD 调结构、补证据、对齐关键词。你没给过的数字它不会替你造出来：

```text
已改：把"负责用户中心"改成结果导向的写法，动词前移
待确认：<你需要补的数字>
  · 你说"接口性能优化明显"，量级是多少？没有数字我按"显著降低 P99"写，
    但面试会追问，建议你自己确认后填实数
  · 团队规模 5 人是否包含实习生？
未写入：任何我没有依据的百分比、奖项和职级
```

<Aside type="danger">
"提升 30% 效率"这种数字，如果你没给过，就不会出现在简历里。那不是润色，是造假，而且代价要你在面试现场付。缺的地方一律标成待确认。
</Aside>

NDA 和隐私政策会先把当事人、用途、你们实际怎么处理数据、适用哪个法域问清楚，再动笔：

```text
草案已生成，以下条款标记为需法务复核：
  §3 保密义务期限        涉及可执行性
  §5 跨境传输            涉及适用法域与传输机制
  §7 敏感数据处理        涉及特殊类别数据的合法性基础
  §9 救济与违约金        涉及法律效果
  §11 争议解决与管辖     涉及管辖选择

本文档是草案。签署或发布前必须由当地执业律师复核。
```

这三类专项任务的方法和硬边界写在 Skill 目录的 `references/product-writing-toolkit.md` 里，三阶段流程的细节在 `references/coauthoring-workflow.md`。

## 文档最后放哪

| 情况 | 文档去哪 |
| --- | --- |
| 你给了路径 | 就用你给的，不改写目录，也不再问一遍 |
| 你没给，但仓库有文档目录约定 | 沿用仓库的约定 |
| 两样都没有 | 落第一个文件**之前**先问你要一个前缀，然后放在该前缀下的 `doc-coauthoring/` 里 |

同一个任务里问过一次就不再问，也不会把你的个人前缀写成团队默认值。你给的原始文件留在原地不动；过程稿走临时目录；只有定稿进交付目录。

## 产出与验收

交付的是一份能给人看的定稿，加上一条清楚的落盘记录：

```text
定稿      在你指定的路径、仓库既有约定目录，或你确认过的前缀下
过程稿    留在临时目录，没污染交付目录；你给的原始文件仍在原位
读者测试  干净会话读完后误解了什么，这些误解在第二阶段是否已经改掉
待确认    所有没有依据的事实、数字、法域和合规状态都显式标出，不是顺手填上
法律类    带着明确的法务复核标记
```

判断真的完成了：一个没参与写作的人读完，能得出你想让他得出的结论，而且不用回来问补充问题。

## 常见坑

**跳过第一阶段直接写。** 省下的十分钟提问，会在第二阶段以整节重写的形式还回来。

**受众含糊地写成"相关同事"。** 受众不明确，详略和术语就只能靠猜，最后所有人都觉得这份文档不是给自己看的。

**自己当读者做第三阶段的测试。** 你已经知道文档想说什么，读不出缺口。测试必须交给没参与过的人或干净会话。

**校对被做成了重写。** 你要的是能逐条判断的清单，不是一份看不出改了哪里的新稿。

**让它替你把空缺补圆。** 数字、职责、合规状态一旦被"合理推测"填上，就很难再被发现——所以缺的地方必须留成待确认。

**把法律草案当成能签的文件。** 草案是草案，法务复核标记不是免责客套。

## 最佳实践

- **第一句先说读者是谁。** 这一句能省掉后面一半的返工。
- **把手里的材料一次倒完。** 旧版本、被否掉的方案、来回的邮件都有用，尤其是被否掉的那些。
- **一节一节验收。** 每节过关再往下，比整篇写完再大改省力得多。
- **第三阶段的反馈直接对应到节。** 哪一节被误解就改哪一节，不要整篇重排。
- **未定的事情留成待确认，别替它做决定。** 待确认清单本身也是交付物的一部分。
