## 概述

认证代码最危险的地方是"看起来能用"：登录接口返回了 Token，带上 Token 请求也能过，于是就认为链路通了。真正的问题往后才出现——多节点部署后会话随机失效、Token 因为每次访问都顺延而永远不过期、权限改完旧会话还照旧生效。

`satoken-core` 的做法是先把真实链路还原出来再写代码。它会去看构建文件里到底装了哪个版本、Token 实际从哪个位置读出来、配置和持久化怎么接的、过滤链在哪一层拦、身份对象是框架给的还是仓库自己封的、注销和踢人各自作用到哪。这些不摸清，写出来的类名和配置键全是猜的。

它只管 Sa-Token 这一层的认证与会话，也不会把仓库里自己写的 Helper、用户模型或配置键当成框架自带的东西。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做个登录接口" | 凭据校验、身份构建、Token 返回与审计 |
| "怎么拿当前用户" | 当前主体、用户类型、角色权限、租户的读取入口 |
| "Token 一直不过期" | 有效期、活跃超时与硬上限的排查 |
| "退出登录没生效" | 分清作废这次会话、撤销某个 Token、把账号或设备请出去 |
| "多端登录要互斥" | 同端互斥、全端互斥、允许并发、指定设备下线 |
| "跨节点会话偶发失效" | 持久化实现、节点配置、命名空间、序列化、过期时间 |
| "加个权限注解" | 注解能挡住什么，以及它挡不住什么 |

## 什么时候不要用

这个 Skill 的边界特别容易和相邻两个能力混淆，先记住这张对照：

| 你要做的事 | 归属 |
| --- | --- |
| 威胁建模、通用安全策略、接口授权体系、安全审计 | [security-guard](/skills/skills-reference/high/security-guard/) |
| 登录态、Token 生命周期、Session、多端、踢人、权限注解接入 | satoken-core（本页） |
| 租户内的行级、字段级可见范围 | [data-permission](/skills/skills-reference/high/data-permission/) |
| 租户级隔离与跨租户运维 | [tenant-management](/skills/skills-reference/medium/tenant-management/) |

另外这几种情况也不要找它：

- **前端登录页、Token 存哪、路由守卫** → [ui-pc](/skills/skills-reference/high/ui-pc/) 或 [ui-app](/skills/skills-reference/high/ui-app/)。
- **OAuth、扫码、第三方账号登录** → 不在范围内，先过 [security-guard](/skills/skills-reference/high/security-guard/)。
- **部署 Redis、网关这类基础设施** → 不在范围内。
- **项目根本不用 Sa-Token** → 走 [security-guard](/skills/skills-reference/high/security-guard/) 和 [tech-decision](/skills/skills-reference/high/tech-decision/)。把一个框架的 API 套到另一个框架上，是最费时间的返工。

## 开始之前

**项目得真的在用 Sa-Token，而且版本要确认得下来。** 不同版本的 API 名字、异常类型和配置键并不一致，版本没定住的时候，任何方法签名都只是猜测——写出来能编译过纯属运气。

**得有一个具体的认证需求。** "把登录做一下"这种说法会换来一堆你用不上的登录方式。说清是补一个接口、修一个现象，还是改一条策略。

<Aside type="danger">
证据链是硬门禁：依赖装了没、配置在哪、初始化和过滤链怎么串的、身份模型是谁定义的、生产代码里真的这么调过没、有没有现成的测试。缺一环，它就不会把某个工具类、注解或某版本的配置键写成可以直接抄进项目的代码，也不会假设你这里存在某个登录 Helper、统一响应类或用户类型枚举。

最容易踩的一条：**看到项目依赖里有 Redis，不等于 Sa-Token 的持久化已经配好了。** 这两件事完全独立，很多"跨节点会话丢失"就出在这里。
</Aside>

## 怎么调用

说清要做的事就行——"补个登录接口"、"退出登录没生效"、"多端要互斥"。它会先做一遍事实发现，把版本、Token 读取位置、持久化与过滤链、现有登录入口、身份信息的来源、以及注销与踢人的既有覆盖摸清楚。项目里同时存在几套认证体系时，它会逐条对上，不会拿 A 体系的上下文去喂 B 体系的接口。

事实清楚之后，它会按你要做的事把该定的契约先问定：

| 你要做的 | 它会先把这些问题问定 |
| --- | --- |
| 登录 | 用什么当身份标识？算哪一类用户？要不要按设备区分？多久算过期？同一个人能同时在几个端？Token 从响应体、Header 还是 Cookie 回去？ |
| 拿当前用户 | 谁在调？拿到的是标识还是完整对象？角色和权限从哪读？租户信息在不在里面？没有登录态时是返回空还是直接抛？ |
| 退出 | 是把这一次的凭据作废，还是把这个账号所有端都请出去？只踢某台设备呢？ |
| 会话 | 存在哪？怎么序列化？往里放多少数据？多久失效？多个节点读到的是同一份吗？ |
| 续期 | 每次访问顺延，还是到期换发新的？有没有一条"最长也就活这么久"的硬上限？换发之后旧的还能不能用？ |
| 凭据校验 | 密码怎么哈希的？验证码怎么防重放？连续失败几次锁？账号被禁用时走哪条分支？ |

## 使用示例

### 场景 1：补一个登录接口

**你的输入**：

```text
管理端补个账号密码登录，登录完前端要能拿到当前用户的角色。
```

**你会拿到的产出**：

```text
## 已确认事实
依赖      sa-token-spring-boot3-starter 1.39.0（构建文件）
持久化    sa-token-redis-jackson，命名空间 admin:  （配置文件 + 启动日志）
过滤链    SaTokenConfigure 注册，放行 /auth/login、/actuator/**
身份来源  仓库自封的 LoginUser（已找到定义 + 3 处生产调用），不是框架自带
Token     响应体返回，前端存 localStorage（现有 4 个接口一致）

## 本次改动
AuthController.login       参数校验 → 账号状态 → 凭据比对 → 建登录态
AuthService.login          复用仓库已有的密码哈希实现，未新写加盐逻辑
LoginUser                  只放 userId / userType / roles / tenantId
                           （原型里那三个易变业务字段没进去，理由见注释）

## Token 与会话契约
读取位置  Header: satoken
有效期    30 天总上限，活跃超时 2 小时
续期      访问顺延活跃超时，但不突破 30 天硬上限
注销      作废当前凭据；账号级下线走另一个入口，本次未涉及

## 验证
目标模块编译 ✓   正确/错误密码 ✓   禁用账号 ✓   缺失 Token ✓
未验证    多节点一致性（本地单节点）、网关透传、真实前端联调
```

注意最后那两行。单节点跑通不会被写成"集群没问题"——这是它和"看起来能用"之间的区别。

### 场景 2：退出登录没生效

**你的输入**：

```text
用户点了退出，换个浏览器还是登录状态。
```

**你会拿到的产出**：

```text
## 结论：调的是"作废当前会话"，但你要的是"账号全端下线"

现状      退出接口只作废了发起请求那一个凭据
          另一个浏览器持有的是另一个凭据，没被牵连
你要的    同一账号在所有端一起失效

## 三个入口的作用范围（别混用）
作废当前     只影响这次请求带来的那个凭据
撤销指定凭据  你手上得先有那个凭据本身
账号/设备下线 按账号或设备批量踢，跟当前请求无关

## 顺带发现
调用时把账号标识当成凭据传进了按凭据撤销的方法。
这类参数在检测到的版本里语义完全不同，编译能过，运行时静默不生效。
```

## 排障时它先看哪里

| 现象 | 先看的地方 |
| --- | --- |
| 请求带了 Token，服务端说没登录 | 读取位置和前缀对不对、过滤链有没有放行、网关有没有把这个 Header 透传下来 |
| 换个节点就掉登录 | 各节点是不是同一份持久化、命名空间是否一致、序列化能不能互相读 |
| 一登录别的端就被踢 | 并发策略和设备维度的配置，是否本来就是互斥语义 |
| 凭据像是永不过期 | 只配了活跃超时、没有一条总有效期上限 |
| 权限改了旧会话照旧 | 角色权限是登录时快照进去的，还是每次请求现查 |
| 注解没拦住 | 代理是否生效、注解加在了哪一层、这条路径有没有被放行 |

<Aside type="caution">
登录、角色权限、资源归属、租户、行级权限是**五条不同的边界**。注解拦下来了，只说明这个人登录了并且有这个角色——不说明这条记录是他的，也不说明租户和行级规则已经生效。后两件事分别属于 [tenant-management](/skills/skills-reference/medium/tenant-management/) 和 [data-permission](/skills/skills-reference/high/data-permission/)。
</Aside>

<Aside type="danger">
手边没有 Redis、网关、浏览器或多节点环境时，它只会声明已经做到的那一层——编译过了、现有测试过了、单节点跑通了，**不会顺势推断跨节点和生产结果**。同时几件事是明确禁止的：错误提示区分账号存不存在、用不安全的随机源生成验证码、允许任意来源携带凭据、完整凭据落进日志、把凭据放进 URL。
</Aside>

## 常见坑

**"Token 永不过期"通常不是 bug。** 每次带凭据访问都会把活跃超时往后顺延，如果没有另外配一条总寿命上限，它理论上可以一直活着。想让它必须过期，靠的是那条上限，不是活跃超时。

**看到 Redis 依赖就以为会话已经共享。** 依赖在、但持久化实现没接上的项目非常多，单节点跑起来毫无异常，一上多实例就随机掉登录。

**把账号标识和凭据混着传。** 有些方法收的是账号，有些收的是凭据，编译都能过。传错的那次不会报错，只是什么也没发生。

**身份对象里塞业务字段。** 部门名、头像、当前项目——这些东西一变，会话里的还是旧的。只放鉴权真正需要的稳定字段。

**登录失败提示写得太"贴心"。** "该账号不存在"和"密码错误"分开提示，等于给对方一个账号枚举接口。对外给一句不区分的中文提示，内部日志里记脱敏主体加一个可追的关联 ID。

**后台任务里直接拿当前用户。** 定时任务、消息消费者没有请求上下文，取到的是空。需要主体信息就显式传进去。

## 最佳实践

- **先说现象，别先说结论。** "换个浏览器还登录着"比"退出登录的方法有 bug"有用得多——后者会把排查方向带偏。
- **多用户体系优先用框架自带的类型隔离。** 自己拼一个复合标识再解析，只有在仓库已经把它当稳定协议并且有测试的情况下才成立。
- **多端策略明确说出来。** 同端互斥、全端互斥、允许并发、只踢某台设备，是四种不同的产品决定，不是技术细节。
- **改配置时把所有环境一起看。** 只改本地那份，测试环境上去照样出问题。
- **验证结论按实际跑过的层级写。** 单节点证据就写单节点，别升级成集群结论。
