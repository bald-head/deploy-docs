## 概述

缓存出问题，很少是因为不会写 `get` 和 `set`。真正咬人的是这些：两个功能的 key 撞在一起、TTL 没人说得清是谁定的、事务回滚了但缓存已经更新、锁在进程卡顿期间过期被别人拿走而原持有者还在往下写。

`redis-cache` 的做法是把这些边界一次性摆到台面上。每个缓存点它都要你能回答同样几件事：这个 key 长什么样、缓的是什么类型、多久失效、真正的权威数据在哪、缓存和权威数据怎么保持一致、命中率和热 key 从哪看。

它同样先做事实发现——项目现在用的是 Redis、别的远程缓存、进程内缓存，还是几套并存；业务代码该走哪个入口。它不设计数据库（[database-design](/skills/skills-reference/high/database-design/)），不做性能诊断（[performance-doctor](/skills/skills-reference/medium/performance-doctor/)），也不负责把缓存基础设施部起来。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这里加个缓存" | 热点读取要减少回源，得定 key 和 TTL |
| "缓存穿透怎么办" | 大量不存在的 key 直接打到数据库 |
| "缓存击穿" / "热 key" | 单个热点失效那一瞬间并发全打过去 |
| "加个分布式锁" | 多实例互斥，涉及租期、续期、释放和防旧持有者写入 |
| "限流怎么做" | 要定主体、窗口算法、阈值和失败时的取舍 |
| "缓存优化" | 命中率、序列化、大 key、淘汰策略 |
| "Redis 缓存不一致" | 事务边界、失效时机、并发回填竞态 |

## 什么时候不要用

- **设计表结构、索引、迁移** → [database-design](/skills/skills-reference/high/database-design/)。
- **还不知道瓶颈在哪就想加缓存** → 先走 [performance-doctor](/skills/skills-reference/medium/performance-doctor/)。没有指标支撑的缓存，通常是新增一个故障点，不是优化。
- **写业务逻辑本身** → [universal-development](/skills/skills-reference/low/universal-development/)。
- **部署 Redis 实例、集群、监控栈** → 属于基础设施，不在范围内。
- **需要持久化、回放、消费确认的消息** → 发布订阅给不了这些保证，改用真正的消息系统。
- **前端本地缓存与状态** → [store-pc](/skills/skills-reference/medium/store-pc/)。

## 开始之前

**项目已经在用缓存，或者本轮决定引入。** 如果是"引入"，新增依赖或中间件先过 [tech-decision](/skills/skills-reference/high/tech-decision/) —— 加一个中间件是架构决定，不是实现细节。

**有具体的缓存点或具体的现象。** 没有具体对象，key 和一致性策略无从定义，只能生成一堆通用建议。

**客户端和序列化方式确认得下来。** 这两个不定，写出来的 key 结构和 value 类型全是假设。

<Aside type="danger">
硬门禁是一条完整证据链：依赖装了没、配置在哪、在哪初始化的、生产代码真的这么调过没、有没有现成的测试或运维证据。任一环缺失时，它不会把 `Redisson`、`Lettuce`、`Jedis`、`Spring Cache` 或某个 `XxxUtils` 的方法签名当成这个项目的默认写法，也不会说缓存链路已经通了。仓库自己写的工具类，只有在找到定义、导入、生产调用和测试之后才会被用上。
</Aside>

## 怎么调用

说清缓存点或现象就行——"商品详情加缓存"、"这个接口偶发脏数据"、"库存扣减要加锁"。

它先摸清现状：现在到底跑着什么缓存、有没有几套并存、业务应该从哪个入口进；序列化是谁在做、key 前缀谁定的规矩、租户怎么隔开、TTL 现在谁在管、锁和限流分别落在哪个组件上；集群模式、连接池、超时、重试、监控和降级怎么配的；旁边同类代码和现有测试实际覆盖到哪。几套抽象并存时它会逐一对上，不擅自互换，也不会为了"写法统一"再包一层。

然后才给每个缓存点定死这六件事：

| 要定的 | 具体是指 |
| --- | --- |
| key | 命名空间、业务主键、版本位、租户或用户边界、长度上限 |
| value | 真实类型、序列化格式、版本兼容、空值怎么表达、体积上限 |
| TTL | 谁定的、带不带抖动、什么时候主动失效、"永不过期"由谁负责运维 |
| 权威数据 | 数据库还是外部服务；缓存只是副本，还是它自己就是状态 |
| 一致性 | `cache-aside`、`write-through`、失效消息、延迟双删——选哪个，失败了怎么补 |
| 可观测 | 命中率、回源量、延迟、错误、热 key、内存和淘汰指标从哪看 |

这六件事优先落在具名类型、配置项和必要的源码注释里。只有你明确要求，或者这东西要给外部对接、要走迁移回滚、要交给运维或监管，才会另外写文档。

## 使用示例

### 场景 1：给商品详情加缓存

**你的输入**：

```text
商品详情接口 QPS 很高，加个缓存。
```

**你会拿到的产出**：

```text
## 已确认事实
客户端    spring-boot-starter-data-redis（Lettuce），未装 Redisson
序列化    自定义 RedisConfig 里的 Jackson 序列化，已确认可读写泛型对象
现有入口  CacheService（找到定义 + 11 处生产调用），本次沿用，未新增封装
key 前缀  现有约定 <业务域>:<对象>:<id>，租户 id 拼在业务域后面

## 缓存点契约
key        mall:t{tenantId}:sku:detail:{skuId}
value      SkuDetailVO（具名类型，不是 Map）
TTL        30 分钟 ± 3 分钟随机抖动（避开集体失效）
权威数据   MySQL sku / sku_stock 两张表
一致性     cache-aside；写路径在事务提交之后删 key，不在事务里删
空值       缓存 60 秒的空标记，防止不存在的 skuId 反复打库
可观测     沿用现有 Micrometer 指标，新增 tag cache=sku_detail

## 本次改动
SkuQueryService.getDetail    读路径接入现有缓存入口
SkuCommandService.update     事务提交后失效，不动全局序列化配置
application-*.yml            4 个环境都补了 TTL 配置键

## 验证
本地真实 Redis：命中 / 未命中 / 空值 / 过期 / 并发回源 ✓
Redis 停掉时降级为直接查库 ✓
未验证    生产数据规模下的命中率、跨机房延迟
```

注意 TTL 那一行的抖动，和"事务提交之后"那半句——这两处是最常被漏掉的，也是最常引发线上问题的。

### 场景 2：偶发脏数据

**你的输入**：

```text
订单状态偶尔显示成旧的，刷新几次又对了。
```

**你会拿到的产出**：

```text
## 结论：缓存在事务提交前就被删了

现在的顺序    开启事务 → 改库 → 删缓存 → 提交
出问题的窗口  删缓存之后、提交之前，另一个请求读不到新数据，
              于是把旧值又写回了缓存
表现          偶发、不可复现、刷新几次"自己好了"（等到 TTL 过期）

## 另一处同类问题
批量改状态的定时任务整批删 key 之前没有确认租户边界，
一次误删了另一个租户的命名空间前缀。

## 修复方向
1. 失效动作挪到事务提交之后（本仓库已有事务同步回调可用）
2. 并发回填加单飞，避免同一 key 多个线程同时回源
3. 批量删除先确认精确前缀与租户边界，加限速
```

## 四类故障，和四种错误解法

| 故障 | 可用的手段 | 它不会让你这么干 |
| --- | --- | --- |
| 穿透（查不存在的东西） | 入参校验、短期空标记、布隆过滤器 | 把"查不到"永久缓存起来 |
| 击穿（热点失效瞬间） | 单飞回源、逻辑过期、提前刷新 | 抢不到锁就返回一个假数据 |
| 雪崩（大面积同时失效） | TTL 抖动、分批预热、容量保护、数据库侧降级 | 靠无限重试把数据库顶回来 |
| 大 key / 热 key | 拆分、降低访问集中度；压缩要先跑基准 | 没测就上压缩，或者直接放着不管 |

## 锁的几条硬要求

分布式锁是这一页里最容易写错的部分：

- **key 里必须带稳定的业务标识。** 用一个全局锁保护所有订单，等于把并发降到 1。
- **只在确认自己还持有的时候才释放。** 否则你释放的可能是别人刚拿到的锁。
- **等待时长、租期、续期都要显式定。** 还要想清楚进程被挂起、重入、线程被中断这几种情况分别会怎样。
- **锁可能过期后被别人重新拿到。** 这种情况下需要一个额外手段——版本号、令牌，或者数据库条件更新——拦住旧持有者的写入。

<Aside type="caution">
锁保证的是同一时刻只有一个人在改，不保证数据最终是对的。真正兜住正确性的是唯一索引、幂等键或状态机——涉及钱和库存时，这两道都得有。

另外：缓存里不放原始密码、凭据或敏感请求体。不可变集合能不能缓存，取决于实际用的序列化器和反序列化目标，不能一概禁止，但要拿目标项目的真实样例确认一次。
</Aside>

<Aside type="danger">
生产路径上不允许一次性把键全扫一遍；要按模式找 key，只能用目标客户端已经验证过的游标式迭代。跨命名空间扫、批量删这类动作影响面很大，动手前把精确范围、租户边界、限速和退路都说清楚。
</Aside>

## 常见坑

**先加缓存，再找瓶颈。** 顺序反了。缓存是一个新增的故障点，没有指标证明它值得加的时候，你只是把问题换了个形态。

**在事务里删缓存。** 提交之前那段窗口足够让另一个请求把旧值写回来。这是"偶发脏数据"的头号来源。

**TTL 全填一样的整数。** 一批数据同一时刻集体失效，回源流量瞬间打满。加个随机抖动，成本几乎为零。

**为了"统一写法"再包一层缓存工具。** 项目里已经有一套的时候，第二套只会让下一个人不知道该用哪个。

**把 key 前缀当实现细节。** 租户边界、版本位都在前缀里。前缀改一次，等于把线上所有缓存作废一遍——如果你还没想好回滚怎么做，这就是一次事故。

**用发布订阅传重要消息。** 断线期间的消息就是没了，没有重放也没有确认。

**后台任务里假设有登录上下文。** 定时任务、消息消费者、跨租户的运维调用，拿不到当前用户，key 会拼错或者拼成别人的。

## 最佳实践

- **一次只说一个缓存点。** "整个模块加缓存"会得到一堆通用建议；"商品详情加缓存"会得到能直接落地的 key 和 TTL。
- **先说清权威数据在哪。** 这一句决定了后面一致性策略怎么选。
- **改配置时把所有环境一起补。** 只改本地那份，测试环境上去照样出问题。
- **没有真实 Redis 就说没有。** 它会只做静态契约并把边界写出来，不会假装验证过。
- **验完拿指标复核。** 命中率和 p95 才是缓存有效的证据，代码合进去不是。

<Aside type="note">
力气基本都花在代码、配置、调用链和真实排障上。它不建 TODO、不写方案报告或测试手册，也不改功能状态、不动 Git，结果直接返回给这个功能的负责人。

最终回复里只有这次任务真的碰到的东西：确认下来的事实和文件位置、选中的入口、关键契约、验证到哪一步、哪些边界没验。判断真的完成了，标准是你能指着每个新增缓存点说出它的 key 全貌（含命名空间和租户边界）、TTL 从哪来、什么时候失效、Redis 挂了会怎样，并且分得清哪些验证跑在真实 Redis 上、哪些只是静态契约。
</Aside>
