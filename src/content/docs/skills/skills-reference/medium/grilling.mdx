## 概述

返工大多不是因为代码写错了，是因为开工那天有三件事没问。`grilling` 就是开工前把你按住、一件一件问清楚的那个角色。

它的克制体现在两处：能从代码、配置和现有文档里查到的，它自己去查，不来占用你；真的只有你能拍板的，一次只递一个过来，等你答完才决定下一个问哪儿。

它只负责把话说清楚，不负责往下做。产品范围与验收归 [product-manager](/skills/skills-reference/critical/product-manager/)，方案发散归 [brainstorm](/skills/skills-reference/medium/brainstorm/)，选型和架构不在它手里。它也不留访谈记录、确认单和清晰度评分表——问完就把结论交给下游，自己不占地方。

<Aside type="caution">
顺序别反：先问清楚，再想方案。倒过来做的结果是对着一个还会变的目标生成一堆候选，然后整批作废——发散得越认真，浪费越多。
</Aside>

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "拷问我一下" / "挑挑毛病" | 想给自己的计划、想法做一次压力测试 |
| "帮我理清楚" | 自己也说不出边界，需要有人带着捋 |
| "这个需求你先问清楚再动" | 新功能启动，怕做到一半才发现方向偏了 |
| "还有什么我没想到的" | 觉得已经想全了，想找人补漏 |
| "再确认一下" | 你和另一个人对范围或验收的理解不一致 |
| "问清楚" | 有一个决定拿不准，想先把取舍摆开 |

它也会自己出现：一个新功能刚开口时，它先把仓库里能查的查完，如果剩下的问题里还有会改结论的，就先问再动手。

## 什么时候不要用

- **需求已经清楚了** → 直接往下走。把已经确定的事再确认一遍，是最没有产出的一种礼貌。
- **正在做一件已经批准过的事** → 已排期条目的续作、边界明确的 Bug、Review 提的修复、不改变行为的维护，都不该被拦下来重新面谈。只有目标或边界真的变了，才值得再问一轮。
- **要产出完整的产品需求和验收** → [product-manager](/skills/skills-reference/critical/product-manager/)。这一页负责把话问明白，那一页负责把它定下来并写清怎么算通过。
- **需求已清晰，接下来是比较几种做法** → [brainstorm](/skills/skills-reference/medium/brainstorm/)。
- **已经批准的需求变了，要看影响面** → [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。这一页面对的是还没定的新需求，那一页面对的是已经在跑、现在要改的东西。
- **技术选型与架构** → [tech-decision](/skills/skills-reference/high/tech-decision/)、[architecture-design](/skills/skills-reference/high/architecture-design/)。

## 使用示例

### 一轮长什么样

每一轮只有三行：一个问题、它推荐的答案、以及为什么推荐它。你答完，才有下一轮。

```text
问题：订单"超时未支付自动取消"，30 分钟是业务定死的，还是要可配？
推荐：做成可配，默认 30 分钟，值放系统参数。
原因：写死的话，运营下次做活动想改 15 分钟就得发版；做成可配只多一次配置读取，
      而且验收时能直接改成 1 分钟来验，不用干等半小时。

你：可以配，但只有超管能改。

问题：改了配置之后，已经在计时的那批订单跟不跟新值？
推荐：不跟。已生成的订单沿用它下单当时的时限。
原因：跟新值的话，用户正看着的倒计时会突然跳变，客诉解释不清；
      不跟只需要在订单上多存一个到期时间。

你：不跟。

问题：取消之后库存立刻回补，还是等对账？
...
```

<Aside type="tip">
你不会收到一张十条待答清单。这是刻意的——清单会让人挑着答，剩下的那几条从此再没人回来处理，而它们往往正是最贵的几条。
</Aside>

### 它会问到哪些方面

不适用的直接跳过，不会为了凑齐而问。

```text
谁在用      功能给谁的、从哪个入口进、用完能看到什么变化
不做什么    哪些相邻的事这次明确不做（这一条最省返工，也最少有人主动说）
规则        正常流程之外，什么算异常、异常之后停在哪个状态
谁能看      角色、租户、数据归谁、留多久
不可逆      要不要动线上数据、要不要迁移、出错了能不能退回去
怎么算完    验收看什么证据，哪些步骤必须你本人操作
```

### 门禁松开时你会收到什么

不是打分，是一段可以直接往下用的结论：

```text
需求清晰度门禁已满足。共享结论：

目标      未支付订单 30 分钟自动取消，库存同步回补
范围      仅限普通商品单；预售单、拼团单本期不做
关键规则  时限可配（仅超管），已生成订单沿用下单时的时限
验收      把时限改成 1 分钟，下单不付款，1 分钟后订单为已取消且库存回补
低风险假设  取消原因文案沿用现有枚举；跳过对账链路（本期无对账）
待你确认  无
```

## 它什么时候才放你走

"约 95%" 不是算出来的分数，是一条能判断的线：

```text
可以往下走了
  剩下没定的事，猜错了换个默认值就能改回来
  剩下没定的事，它自己还能从代码或配置里查出来

还不能走
  还有一个答案会让方案换一条路
  还有一个答案会改验收怎么判
```

只剩一个这种问题，它就不会进入产品定义、设计、架构、选型、排期或编码。

### 你说"这个我现在定不了"

```text
会改结果的决定    它停在这里，并告诉你最少补哪一条就能接着走，不拿假设替你选
只是实现细节      它按仓库现有写法挑一个可逆的默认值，不再纠缠
```

## 与其他 Skill 的关系

**上游**：没有。它可以直接作为入口，你张口就能用。

**下游**：[product-manager](/skills/skills-reference/critical/product-manager/)、[brainstorm](/skills/skills-reference/medium/brainstorm/)、[frontend-design](/skills/skills-reference/high/frontend-design/)

**协作**：[product-manager](/skills/skills-reference/critical/product-manager/)、[architecture-design](/skills/skills-reference/high/architecture-design/)

```text
grilling（先问清：一次一个问题，问到能判断为止）
   ↓
brainstorm（后发散：在已经定住的约束上生成候选）
   ↓
product-manager（范围与验收）／frontend-design（页面与交互）
   ↓
architecture-design → tech-decision → project-manager → dev
```

还有一条反向的边：`brainstorm` 收敛过程里冒出一个会改结论、又查不出答案的选择时，会回头借它问一次，拿到答案再继续收敛。

## 常见坑

**让它问了本该自己查的事。** 如果它问你"你们用的什么数据库""这个接口现在返回什么"，那是它偷懒了，直接让它去看代码。你的耐心额度有限，得留给只有你能回答的问题。

**收到了一张问题清单。** 那说明这一轮跑偏了。清单最典型的结局是前三条被答完、后七条永久搁置。

**把推荐当成已经定了。** 推荐只是它的建议，你说不就是不，改一半也行——三种反应都算有效回答。

**为了追求"问全"而抠细节。** 按钮文案、字段命名这类改起来只要一分钟的事，不值得占用一轮问答。真觉得它在磨，直接说"这个你自己定"。

**问完没落盘。** 结论要进项目现有文档和当前的 TODO。留在对话里，下一个环节又要从头问一遍，前面的追问全白费。

## 最佳实践

- **主动说"不做什么"。** 这一句话的省事程度超过其他所有回答，因为范围外的东西不会被做进来，也就不用再拆出来。
- **定不了就明说。** 它会给你最短的恢复条件——通常是"问谁"或"看哪张表"——而不是替你猜一个然后往下写。
- **把它放在方案发散之前。** 顺序反了，发散出来的候选会连带作废。
- **只留一段结论。** 访谈过程不用保存，下游需要的是"最后要什么"，不是"怎么问出来的"。

<Aside type="note">
怎么算真的完成了：下游任何一个环节拿到这段结论，都不需要回来问"那到底要什么"。反过来说，如果产品定义或页面设计一开工就发现还有决定悬着，那就是这一轮提前放行了。
</Aside>
