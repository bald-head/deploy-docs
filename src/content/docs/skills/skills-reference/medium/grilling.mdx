## 用途

`grilling` 处理无法从仓库查明、且会实质改变用户结果的决定。先读取代码、配置和已有结论，剩余关键问题一次只问一个，并给出推荐答案与理由。

它不替代产品定义、架构或技术选型，也不为已批准 TODO、明确 Bug、Review 修复和普通维护重复做需求访谈。

## 什么时候用

| 请求或情况 | 处理方式 |
| --- | --- |
| 这个新需求先帮我问清楚 | 核对已有事实，再追问真正未决的边界 |
| 对权限、数据范围或验收存在不同理解 | 一次确定一个会影响结果的决定 |
| 方案中出现无法查明的关键取舍 | 把选项、推荐与影响交给用户决定 |
| 泛泛地说“分析一下”“具体怎么做” | 先判断是否存在关键用户决定，不仅凭词语触发 |

需求已经足够清楚时直接交给下一项适用能力。剩余问题只是可逆实现细节时，沿用仓库已有做法，不反复确认。

## 一次追问的例子

```text
问题：订单超时规则修改后，已经创建的订单是否跟随新时限？
推荐：已创建订单沿用创建时的到期时间。
理由：倒计时保持稳定，后续修改只影响新订单；仍需以业务规则为准。
```

收到答案后再决定是否有下一项关键问题，不一次堆出待答清单。推荐不是用户决定，仓库证据也不能替代无法从仓库得出的业务意图。

## 何时结束

“约 95% 清晰”是任务判断，不是统计分数。影响目标、范围、业务规则、权限、数据边界或验收的未决问题已解决，剩余细节可通过代码取证或可逆选择处理时，就可以继续。

输出只保留目标、范围、关键规则、验收、必要假设和仍未决事项；由适用 Owner 归并进项目现有文档与唯一 TODO，不另存访谈记录或评分表。
