## 概述

你名下已经有一份在跑的 TODO，现在想再往里塞一个功能。`add-todo` 只管这一段路：找到那份唯一的 TODO，确认新来的这条不是已有条目换了个名字，把它排到依赖允许它待的位置，写进去，然后告诉你接下来能开工的是哪一条。

它不写代码、不做 Review、不碰 Git，也不替你把某条从待办改成进行中。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "再加一个用户注册" | 单个新功能，前面的规划已经做完了 |
| "把订单模块那三块加进去" | 一批相关功能，可能需要一层聚合 |
| "补个任务" / "加个功能" | 口头追加，边界还得它帮你问清 |
| "这个之前漏了" | 项目文档里承诺过、清单里却没有的功能 |
| "先加着，等接口好了再做" | 有依赖的功能，需要排在正确位置 |

## 什么时候不要用

- **手上还没有 TODO** → [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/)。追加的前提是有东西可追加；从零建一份、决定整份清单长什么样，是它的活。
- **要改的是已有条目的范围、契约或验收** → [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。往末尾补一行和改动一条已经批准的功能不是一回事，后者要顺着受影响的接口、数据和页面一路更新。
- **只是要改某条的完成状态** → [update-status](/skills/skills-reference/medium/update-status/)。
- **这个"功能"其实还只是一句想法** → [product-manager](/skills/skills-reference/critical/product-manager/)，先说清给谁解决什么问题。
- **一次要铺开整个项目或一整块新模块** → [project-manager](/skills/skills-reference/high/project-manager/)。一遍生成完整清单，比一条条追加省事得多。
- **只想知道做到哪了** → [progress](/skills/skills-reference/medium/progress/)；**只想知道接下来做哪条** → [next](/skills/skills-reference/medium/next/)。

## 前置条件

**得先有一份属于你的 TODO。** 它按当前仓库的 Git 身份找你名下那一份，不翻别人的目录，也不会因为没找到就随手在仓库根上新建一个。找不到时它直接说找不到，让你先去建——这比默默造出第二份任务源要划算得多。

**功能得已经想清楚了。** 追加动作本身不产出产品定义。它往里写的是"谁用、从哪进、做完之后用户能做到什么、怎么算验收"这几项；如果这几项还是空的，它会把你退回去先补。写一条自己都说不清验收的待办，等于提前给未来订了一次返工。

**别指望标题能替你判断新旧。** 你说"加个邮箱登录"，而清单里已经有一条登录做的就是邮箱密码登录，它会告诉你这是同一件事，而不是安静地多写一行。

<Aside type="note">
它只追加和整理。想让某条真的被做出来，追加完之后走实现类 Skill；想让某条被勾掉，走 [update-status](/skills/skills-reference/medium/update-status/)。
</Aside>

## 使用示例

### 场景 1：追加一个功能

**你的输入**：

```text
再加一个用户注册。
```

**你会拿到的产出**：

```text
## 查重
现有 6 条，逐条比对入口与用户能做到的结果 → 没有覆盖，可以追加

## 写入
docs/<developer-id>/tasks/todo/user-system.md    +1 条

- [ ] `USER-REG` 用户注册
  - Owner: <developer-id>
  - 来源: docs/prd.md#用户注册
  - 入口: /register（公开路由）
  - 谁用: 尚未注册的新访客
  - 做完之后: 填邮箱能收到验证信，点开链接账号可用
  - 验收: AC-001 表单校验 / AC-002 验证信送达 / AC-003 激活生效
  - 依赖: 无
  - 写集: src/api/auth/register/, src/pages/register.vue
  - 交付面: data / api / backend / web

## 接下来能开工的
USER-REG（没有依赖，排序后就在队首）
```

「写集」那一行填的是仓库相对的目录前缀，用来判断两条功能能不能同时开工，不是让你把要改的文件名全列在这儿。

### 场景 2：一次给一批相关功能

**你的输入**：

```text
加订单管理：查询、导出、统计。
```

它会先替自己回答一个问题——这三块能不能各自独立验收、各自独立提交？能，就给它们一个聚合标题挂在一起，方便你和别人看清这是一整块；不能，就合成一条，别为了好看多摆一层缩进。

**你会拿到的产出**：

```text
## 判断
查询 / 导出 / 统计 各有独立入口、独立验收，能分开提交 → 值得聚合

## 写入
- [ ] 【订单管理】ORDER-MANAGE    入口: order.*
  - [ ] `ORDER-QUERY`  订单查询   依赖: 无            写集: src/api/order/query/,  src/pages/order/list.vue
  - [ ] `ORDER-EXPORT` 订单导出   依赖: ORDER-QUERY   写集: src/api/order/export/, src/pages/order/export.vue
  - [ ] `ORDER-STATS`  订单统计   依赖: ORDER-QUERY   写集: src/api/order/stats/,  src/pages/order/stats.vue

## 说明
聚合那一行是个壳，自己不记执行状态、也不需要单独的完成证据，三条子项全勾之后它自然算完。
导出和统计都要复用查询那套筛选条件，所以依赖指向查询，而不是三条平铺。
```

### 场景 3：撞上已有功能

**你的输入**：

```text
再加一个邮箱登录。
```

**你会拿到的产出**：

```text
## 撞车
你要的            邮箱登录     入口 /login    用户能做到: 用邮箱登进来
已有 USER-LOGIN   用户登录     入口 /login    用户能做到: 用邮箱 + 密码登进来
                                             AC-001 写的就是「邮箱登录成功」

## 结论
同一件事，不追加。

## 你可能真正想要的
- 要加微信 / QQ 这类第三方入口 → 新入口新验收，说一声就给你开一条
- 要让邮箱登录多支持验证码     → 那是改 USER-LOGIN 的验收范围，走 change-impact-analysis
```

查重看的不是标题像不像，而是入口、用户拿到的结果、验收这三样是否指向同一件事。标题不同但这三样重合，它一样会挡下来——清单里躺着两条实质相同的功能，代价是真的会有人把它做两遍。

### 场景 4：新功能要等别的东西先做完

**你的输入**：

```text
增加用户信息页面。
```

**你会拿到的产出**：

```text
## 排序
USER-INFO-PAGE 要拿用户信息接口的数据，而 USER-INFO-API 还没做完
→ 依赖: USER-INFO-API，落在它后面

## 写入后的顺序
- [ ] `USER-INFO-API`   用户信息接口    依赖: 无
- [ ] `USER-INFO-PAGE`  用户信息页面    依赖: USER-INFO-API
                                        写集: src/pages/user/info.vue

## 接下来能开工的
USER-INFO-API。页面这条依赖没清，暂时不进可开工队列。
```

依赖填的是具体那条的 ID。写成"依赖后端接口"这种话没法参与排序，最后你会看到页面排在接口前面，而且没人觉得奇怪。

### 场景 5：两条功能想写同一个目录

**你的输入**（此时 `ORDER-QUERY` 正在进行中，写集含 `src/api/order/`）：

```text
增加订单详情页面。
```

**你会拿到的产出**：

```text
## 写集比对
进行中 ORDER-QUERY    src/api/order/            src/pages/order/list.vue
要追加 ORDER-DETAIL   src/api/order/  ← 重叠     src/pages/order/detail.vue

## 结论
目录前缀重叠，两条不能同时开工。

## 两条路
1) 排队：ORDER-DETAIL 依赖 ORDER-QUERY，等它完成再领
2) 分家：把 ORDER-DETAIL 的写集收窄到 src/api/order-detail/，两条就互不干扰
```

同时挂着多条进行中是允许的，前提是它们各归各的执行实例，而且要动的目录互不重叠。重叠还硬并行，结果通常不是冲突报错，而是一方的改动被另一方悄悄覆盖掉。

### 场景 6：什么都不用加

```text
你：把登录页的按钮文案改一下，要加个任务吗？

它：不用。这不是一条新功能，它落在 USER-LOGIN 已有的验收范围里。
    想让它别被忘掉，就在 USER-LOGIN 下面补一句说明，不另开条目。
```

## 一条追加进去的功能长什么样

<Aside type="tip">
一条就是一条，从数据到页面点得通算同一条。建表、接口、后端逻辑、页面、权限、联调、Review、提交，全是这一条内部要走完的事，不会被切成一排小勾放在清单里。
</Aside>

所以你不会在清单里看到这种形状：

```text
✗ 按技术层切开——每条都无法单独验收，进度看着在动，用户什么也用不上
- [ ] USER-REG-DB     建表
- [ ] USER-REG-API    接口
- [ ] USER-REG-PAGE   页面

✓ 一条纵向的功能——交付面写在条目里，验收针对用户能做到的事
- [ ] `USER-REG` 用户注册
    交付面: data / api / backend / web
```

## 常见坑

**把"加个功能"理解成"加个前端页面"。** 页面能点开不等于功能可用。只报前端那一半，后面补数据和接口时才发现验收根本过不了。

**依赖写成一句话。** "依赖后端接口"参与不了排序。要么给具体 ID，要么就别指望顺序是对的。

**写集留空。** 留空等于宣称这条谁都不冲突，于是它真的会和别人同时开工，然后你们在同一个目录里互相覆盖。

**给单个功能套一层聚合。** 只有一条子项的聚合层不提供任何额外信息，只多一级缩进和一次误读机会。

**需求还没定就先占位。** 先写一行"待补"进去，之后大概率不是有人回来补，而是被当成已确认范围直接开工。

**在别人的目录里追加。** 任务归属跟着当前 Git 身份走。属于另一位开发者的功能应该转交给他，由他在自己那份清单里受理，写进你这份只会让两边都统计不准。

**找不到 TODO 就换个地方写。** 仓库级 `docs/` 根、别人的目录都不是兜底位置。写错地方的后果不是报错，而是从此有两份互相不知道对方存在的任务源。

## 最佳实践

**一次只说一件事。** "加订单管理"和"加订单导出的 Excel 模板配置"是两种粒度：前者会被拆开，后者会被并进已有条目。你想要哪种，说清楚就少一轮来回。

**把入口说出来。** 菜单路径或路由是查重最有效的输入，也是之后判断前端是否真的能点到的唯一线索。

**验收写成能勾的句子。** "体验流畅"没法验收；"提交后 2 秒内出结果，失败有明确提示"可以。

**想并行就先看写集。** 目录前缀不重叠才谈得上同时做；重叠就老实排队，或者把边界调开。

**追加完看一眼"接下来能开工的"。** 如果队首不是你以为的那条，通常是依赖填错了，趁这时候改最便宜。

## 故障排查

| 症状 | 大概率原因 | 怎么办 |
| --- | --- | --- |
| 说你没有活动 TODO | 文件不在你名下的 todo 目录里，或者根本还没建 | 用 [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 建一份；已有文件的话确认它在 `docs/<developer-id>/tasks/todo/` 下 |
| 说发现多份，停住不动 | 同一个目录里躺着两个以上清单文件 | 先自己合并成一份，它不会替你猜哪份是当前在用的 |
| 清单里出现两条实质相同的功能 | 追加时只对了标题，没对入口和验收 | 合并成一条，把两边的验收并进去 |
| 页面排在接口前面 | 依赖写的是描述而不是 ID | 换成具体 featureId 再重排 |
| 两个人改同一个文件 | 写集重叠却都在进行中 | 收窄其中一条的写集，或者补上依赖让它排队 |
