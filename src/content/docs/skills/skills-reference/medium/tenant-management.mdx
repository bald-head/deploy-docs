## 概述

多租户的事故很少发生在"忘了加租户字段"上，而是发生在缝隙里：拦截器管住了普通查询，报表那条手写 SQL 从旁边过去了；异步导出用的线程还带着上一个任务留下的租户值；缓存 key 没带租户，A 租户先查一次，B 租户直接命中；管理员代管功能顺手把过滤关了，于是导出了全站数据。

`tenant-management` 的做法是不看声明、只看执行：把租户标识从哪来、经过哪些链路、最后在哪一层被真的挡住，一条一条摊开，然后指出哪几条没挡住。

它管租户模型、上下文传播、数据与缓存与消息与文件的边界、跨租户运维、迁移和验证。谁是登录人交给 [security-guard](/skills/skills-reference/high/security-guard/) 和 [satoken-core](/skills/skills-reference/medium/satoken-core/)；一个租户内部谁能看哪几行交给 [data-permission](/skills/skills-reference/high/data-permission/)。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这个系统要做成多租户的" | 先定隔离模型：一张表里加租户字段，还是一个租户一套库/schema |
| "A 租户看到了 B 租户的数据" | 有路径绕过了过滤——通常是手写 SQL、批量更新、报表或导出 |
| "异步任务里租户丢了" | 线程池、定时、消息、长连接、文件、缓存的上下文传递 |
| "管理员要能跨租户查" | 跨租户运维的授权范围、审计与资源保护 |
| "支持一下切租户" | 切换与恢复的作用域 |
| "这几张表是所有租户共用的" | 共享资源怎么分类、依据是什么、变更怎么审 |
| "租户注销了，数据怎么处理" | 停用、保留、延迟删除与不可逆擦除 |

## 什么时候不要用

| 你要解决的问题 | 归属 |
| --- | --- |
| 谁是登录人、Token 怎么发、会话怎么续 | [security-guard](/skills/skills-reference/high/security-guard/)、[satoken-core](/skills/skills-reference/medium/satoken-core/) |
| 租户之间不能互看、管理员如何跨租户 | tenant-management（本页） |
| 同一个租户里，销售 A 能不能看销售 B 的单子 | [data-permission](/skills/skills-reference/high/data-permission/) |
| 建表、加索引、写迁移脚本本身 | [database-design](/skills/skills-reference/high/database-design/)、[database-ops](/skills/skills-reference/high/database-ops/) |

另外三种情况也不用它：**系统只服务一个客户**——别提前埋一套用不上的机制，每个绕过点都是将来的事故来源；**要做租户切换的界面** → [ui-pc](/skills/skills-reference/high/ui-pc/) 或 [ui-app](/skills/skills-reference/high/ui-app/)；**要在网络或容器层面做物理隔离**——那是部署话题，不在这一页。

## 开工前它一定会先确认的事

**隔离模型是否已经定了。** 这一条不能边做边定：一张表里加字段、一个租户一套 schema、还是混合，三者的迁移方式、索引形状和连接路由几乎没有共同代码。模型没定就开始写，写出来的东西基本要整段重来。

**这次到底是在动租户边界，还是在动别的。** "让这个角色看不到那几行"听起来像隔离问题，其实是租户内部的可见范围，走错页会把两层权限搅在一次改动里，出事时也分不清是哪一层漏的。

它不会拿某个插件的用法、某个字段名、某份排除表清单当作通用答案。同样的需求在不同项目里落点差别很大，所以它先看你的代码，再给写法。

<Aside type="danger">
请求里带来的租户 id——URL、请求头、表单字段、批量参数——**只能当候选值**，必须回到已认证身份和租户成员关系里重新核一遍。直接信任传入值是这类系统最短的一条越权路径：改一个请求头就能读别人的数据，而且日志上看起来完全正常。
</Aside>

## 使用示例

### 场景 1：A 租户看到了 B 租户的数据

**你的输入**：

```text
客户投诉在报表里看到了别家公司的订单号。我们明明有租户拦截器。
```

**你会拿到的产出——按访问路径逐条摊开，而不是一句"已加固"**：

```text
## 隔离在哪一层真的生效
访问路径                            谁挡住的                     结论
GET /orders 列表（Mapper 方法）      MyBatis 租户拦截器           已强制
GET /report/sales（XML 手写 SQL）    无                           未强制 ← 泄漏点
POST /orders/updateBatch            无                           未强制
Excel 导出（Service 里拼 SQL）      无                           未强制
Redis 缓存 order:{orderId}          key 里没有租户               可跨租户命中
Kafka order-created 消费            生产端写了租户，消费端没复验   可被伪造
OSS orders/{orderId}.pdf            只靠 key 前缀                签名 URL 未校归属

## 结论
拦截器只覆盖走 Mapper 接口的查询。报表、批量、导出各自绕过一次，
其中报表是本次投诉的直接来源。
```

```text
## 租户从哪来、传到哪去
来源      登录态里的租户成员关系             可信
          请求头 X-Tenant-Id                 只当候选，回到成员关系核对
HTTP      过滤器写入 → 请求结束清理          正常与异常两条路都清了
线程池    异步导出任务                       没有显式传递，拿到的是上一个任务残留的值 ← 修复点
定时任务  凌晨对账                           没有租户上下文，当前按共享跑，实际扫了全表 ← 修复点
消息      order-created                      生产端写入，消费端未复验 ← 修复点
```

<Aside type="caution">
最危险的那种写法是"为了让报表跑通，临时把租户过滤关掉"。只要这个"临时"不是包在最小作用域里、并且保证一定恢复，它就会顺着线程复用、异常分支或下一次重构泄漏到别的请求上。这类问题在单节点单请求的测试里几乎测不出来，出事时也很难复现。
</Aside>

### 场景 2：把现有单租户系统改成多租户

**你的输入**：

```text
现在是给一家客户用的，要改成 SaaS，预计接 200 多家。
```

**它会先把模型和代价摆出来，再动代码**：

```text
## 隔离模型
选定    单库单表 + 租户字段
依据    租户量 200+ 且功能完全同构；运维只有 1 人，一租户一库的备份与
        逐个迁移这个团队扛不下来
代价    每张业务表都要带租户维度，并且必须有人保证每条访问路径都过滤
        → 下面这份清单才是这次改动的主体，加字段只是开头

## 表结构上的租户维度
订单表    租户字段进联合索引首位；原来的"订单号唯一"要变成"租户 + 订单号唯一"
用户表    同上；注意手机号唯一——是全站唯一还是每租户唯一，这是个业务决定
字典表    确认为共享：所有租户读同一份，只有运维能写，变更走审计
```

```text
## 迁移
第 1 步  加字段（可空）、加索引，先不加约束
第 2 步  回填：现有数据全部归属首个租户 —— 前提是它们确实都属于这一家
第 3 步  双读校验：新旧两条路查同一批数据，比对行数与关键字段
第 4 步  收紧：字段非空、唯一约束换成含租户的版本
第 5 步  切换 + 保留回滚脚本
```

<Aside type="danger">
迁移这一段有两条踩过就很疼的线。**别用一个"默认租户"把归属不明的数据兜住**——那不是迁移完成，那是把问题埋到有第二个客户之后，届时你已经分不出哪些数据本来属于谁。**一租户一库/schema 的迁移必须逐个记录执行状态**，不能因为前 180 个成功就宣布整体完成，剩下 20 个会在最不方便的时候暴露。
</Aside>

### 场景 3：管理员要跨租户导出

**你的输入**：

```text
客服要能跨租户查订单，出问题时导出给客户看。
```

**产出形态**：

```text
## 授权
入口   仅运维后台 /ops/export，与业务后台不同域、不同鉴权
范围   只能覆盖角色绑定的租户集合；不接受请求参数指定目标租户
执行   按租户逐个进入最小作用域执行，不用一条无过滤的 SQL 一次捞完
       （集合查询只在专用运维面上开放，且带字段与行数上限）
批量   分批 + 幂等键 + 限流 + 超时 + 检查点；部分失败要能说清失败在哪几个租户
```

```text
## 一次导出留下的审计记录（示例）
operator   ops:zhangsan（运维后台）
scope      授权 12 个租户，本次命中 3 个
target     t_1042, t_1189, t_1355
reason     客户投诉核查（工单 #48213）
grant      role:ops-export → tenant-group:cn-east
trace      exp-20260904-0031
window     03:12:07 → 03:12:59
result     成功；4,821 行；t_1189 超时重试 1 次后成功
备注       这条记录业务操作者删不掉
```

<Aside type="danger">
删除、回填、批量通知、管理员代管这类动作，在授权、影响上限、预演或抽样、审计、回滚路径没有全部到位之前不会执行。共享表和共享资源的调整按安全边界变更对待——因为它一改，所有租户同时受影响。
</Aside>

## 它怎么验，以及哪些结论不算数

```text
会真的去试的几件事
  伪造一个租户 id 打进来，看能不能读到
  用 A 租户的登录态去改 B 租户的数据
  手写 SQL、批量、报表、导出各走一遍
  异步任务连跑两次，看第二次拿到的是不是第一次残留的租户
  A 租户查一次之后 B 租户再查，看缓存会不会串
  管理员跨租户操作后回查审计

跑完了也不能声称通过的部分
  数据库自身的行级安全      本地库通常没开
  多节点缓存与消息重试      单进程验不出来
  连接池复用与事务边界      要在真实并发下才暴露
  网关那一层的租户注入      本地起的是应用，不是完整链路
  生产迁移                  只在生产数据量上才有意义
```

<Aside type="caution">
单进程绿灯不等于验收。证据到不了的部分它会直接列成未验证边界，而不是用一句"已加固"盖过去——因为这类系统一旦声称过了却没过，代价是客户看到别人的数据。
</Aside>

## 常见坑

**以为加了拦截器就等于隔离了。** 拦截器只盖住它能盖住的那一类调用。手写 SQL、批量方法、报表、导入导出、数据库函数、搜索索引都是各自独立的一条路，得一条一条看。

**缓存和锁忘了带租户命名空间。** 缓存串数据的表现很像"偶发脏数据"，几乎不会有人第一时间怀疑到 key 上。分布式锁少了租户维度更隐蔽：两个租户互相排队，业务上表现为莫名的卡顿。

**只做了 key 前缀就当文件隔离了。** 对象存储的前缀不是权限。真正决定别人能不能拿到的是读取授权和签名 URL 是怎么签的。

**在异步链路里指望上下文自己跟过去。** 线程池、协程、响应式链路都不会替你搬。更糟的是它不报错，而是给你上一个任务留下的值。

**把"能跑通"当成隔离已完成。** 单租户测试永远是绿的——这个系统里的所有 bug 都要两个租户才能看见。

## 最佳实践

- **共享的东西要显式声明。** 没带租户 id 就自动当共享处理，是最容易被利用的默认行为；共享清单要有依据、有写入者、有审计。
- **过滤、归属校验、功能权限、行级权限当成四道独立的门。** 任何一道被绕开，其他三道不会跟着失效，也正因为如此，别指望"反正还有别的门"。
- **切换和绕过写成最小作用域，并且保证一定恢复。** 恢复要放在异常也会走到的位置。
- **跨租户能力放在专用入口。** 和业务入口共用一套鉴权，早晚会有人从业务侧走到它上面。
- **停用和删除先盘点数据落在哪几处。** 库、缓存、消息、文件、搜索、审计通常都存了一份，删一处不叫删除。

<Aside type="note">
怎么算真的完成了：对每一条数据访问路径，你都能说出租户从哪来、在哪一层被挡住、异常路径怎么清理；能说出跨租户操作留下了哪些字段；并且清楚哪些结论只有单进程证据。
</Aside>
