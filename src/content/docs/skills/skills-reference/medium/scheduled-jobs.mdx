## 概述

写一个定时任务只要一个注解，出问题却几乎总在注解之外：扩到四个副本之后每个节点都跑了一遍、cron 在夏令时那天跑了两次或一次没跑、失败之后无声无息、批处理跑到一半挂掉从头再来。

`scheduled-jobs` 的做法是先把这个任务的行为讲清楚——什么时候触发、重复触发会怎样、失败算哪一类、跑一半挂了从哪继续——再按你仓库里真实用的那个调度器落地，最后在真实调度器上跑一次给出证据。

它不替你选调度器，也不会把某个控制台地址、某个注解当默认答案。审批流转、消息体系和容量性能各有归属，它只管调度这一段。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "加个定时任务" | 周期性的清理、汇总、同步 |
| "每天凌晨跑一次" | cron 表达式、时区、错过窗口怎么办 |
| "半小时后自动取消" | 延迟任务的到期时间、持久化、取消与改期 |
| "任务没执行" | 触发条件、执行器注册、控制台创建、时区排查 |
| "多实例重复执行了" | 集群单例、租约与幂等 |
| "要跑批处理" | 游标、批次上限、断点续跑 |
| "失败了要重试" | 哪类该重试、退避多久、重试完了归谁 |

## 什么时候不要用

- **同步就能解决的事** → [api-development](/skills/skills-reference/high/api-development/)。任务会附带幂等、并发和可观测三份长期成本，能同步返回就别排队。
- **实时推送、进度通知** → [websocket-sse](/skills/skills-reference/medium/websocket-sse/)。用几秒一次的轮询任务冒充推送，最后既不实时也不省资源。
- **普通业务逻辑** → [universal-development](/skills/skills-reference/low/universal-development/)。
- **前端定时刷新** → 前端实现类 Skill。
- **要设计一整套消息或延迟队列体系** → 不在这一页。高吞吐的延迟投递先看项目现有的消息能力，别自己造。
- **想换调度框架** → 先过 [tech-decision](/skills/skills-reference/high/tech-decision/)。

## 开工前它会先看清什么

**这件事真的需要变成任务。** 一个定时任务的长期成本不是那段业务代码，是它带来的三个新问题：重复触发会不会重复写数据、多实例会不会并发跑、失败了谁会知道。同步接口没有这三个问题。

**这个仓库用的是哪个调度器，版本是哪个。** 注解语义、重试模型、集群行为在不同框架之间没有可移植性，混着写的结果是日志显示重试了、实际一次都没重试。仓库里并存多套调度器时，它会先输出"哪个任务归哪个调度器、执行器在哪注册、触发配置写在哪、告警走哪条路"，不跨框架照搬语义。

**触发条件和要做的事已经说清楚了。** 触发条件模糊时写出来的 cron 只能靠猜；要做的事模糊时定不出幂等键——而这两样恰好是任务出事时唯一能救你的东西。

<Aside type="danger">
在依赖、各环境配置与时区、执行器注册、任务定义、调度入口这条链没走通之前，它不会先把注解写上去。原因很实际：这类代码"看起来对"的成本极低，而验证成本极高——客户端注册成功不等于服务端真的触发过，控制台里有这条任务不等于它跑过，本地跑通不等于集群里只跑一次。
</Aside>

## 使用示例

### 场景 1：每天凌晨清理历史日志

**你的输入**：

```text
操作日志表两千万行了，加个定时任务清掉 30 天前的。
```

**你会先拿到这个任务的行为说明——不是抽象清单，是填好值的那种**：

```text
## 任务契约：清理 30 天前的操作日志
触发    cron 0 15 3 * * ?，时区写死 Asia/Shanghai（不吃服务器默认时区）
        错过窗口（发版、停机）→ 跳过本次不补跑；清理任务补跑没有意义
投递    至多一次即可，不做补偿
范围    每批 2000 行，按主键游标推进；单次最长 20 分钟，超时停在断点
幂等    删除天然幂等；重复触发只会少删，不会多删
并发    集群单例：4 个副本里只有拿到租约的那个跑，租约 30 秒续一次
失败    连接超时 = 临时错误 → 退避重试 3 次
        表不存在 = 永久错误 → 不重试，直接告警
可观测  执行 ID、起止时间、删除行数、停在哪个主键、耗时；连续 2 次失败告警
变更    保留天数放配置；改天数不用发版，回滚就是把配置调回去
```

**再落实现，重点只有三处**：

```text
入口    只接收已校验的具名参数；调度器传进来的东西按不可信输入对待
批处理  稳定游标 + 批次上限 + 检查点，不要 select 出全表再删
事务    一批一个事务；事务边界不要包住重试，否则重试会连着已提交的批一起算
```

**验证与交回的结论**：

```text
已验证  本地把 cron 改成每分钟、起 2 个实例，10 分钟内每分钟只有 1 条执行记录
        断点续跑：跑到第 3 批 kill 掉，重启后从记录的主键继续
未验证  生产 4 副本的选主、凌晨真实数据量下的耗时、告警是否真的到人
配置    dev / test / prod 三份配置都补了保留天数与时区（不是只改了 dev）
```

### 场景 2：多实例重复执行了

**你的输入**：

```text
昨天有用户收到了 4 条一样的提醒短信。我们扩到 4 个 pod 之后就这样了。
```

**排查结论**：

```text
## 结论：这个任务从来不是集群单例，4 个副本各跑一遍
证据
  配置     只有定时注解，没有任何选主或租约配置
  日志     03:15:00 同一秒 4 条 "start notify"，来自 4 个不同 pod
  数据     同一批用户各 4 条提醒记录，落库时间相差 12 毫秒
  顺带     隔壁清理任务也在跑 4 遍，只是删除幂等所以没人发现

## 修复顺序（顺序不能颠倒）
1. 幂等先落到数据上：提醒记录表加 (user_id, biz_date) 唯一约束
2. 再补集群单例（用仓库现有能选主的组件，不为这件事引新框架）
3. 最后处理已发出的重复数据：只统计，不自动清理

## 为什么是这个顺序
只加单例的话，锁失效、进程假死、时钟漂移的那几次仍会重复发出去；
唯一约束是那几次的兜底，而且它不依赖任何运行时状态。

## 验证
本地起 2 个实例，cron 改成每分钟，10 分钟内提醒条数必须恒等于用户数
```

<Aside type="caution">
别用分布式锁代替幂等约束。锁只是把重复的概率压低，而锁失效、进程被暂停、时钟漂移、节点下线这几种情况都必须有一个"重复了也不出事"的结果。涉及外部副作用或所有权转移时，还要再想一层：唯一约束、原子的状态迁移、或者带序号的令牌，哪一个能挡住迟到的那次执行。
</Aside>

### 场景 3：下单 30 分钟未支付自动取消

**你的输入**：

```text
订单 30 分钟不付就自动取消并回补库存。
```

**产出形态**：

```text
## 到期时间从哪来
下单时算好 expire_at 落库，不依赖内存里的定时器
→ 重启不丢；改配置也不影响已经在计时的订单

## 取消与支付的竞态
用户在第 29 分 59 秒付款成功，取消任务同时开始执行
→ 取消写成条件更新：只有状态仍是待支付才能改成已取消
  影响行数为 0 就说明已经付掉了，直接结束，不算失败也不告警

## 扫描侧
按 expire_at 索引取到期单，单次有数量上限
→ 消费端挂过一段时间之后，恢复瞬间会有一大批同时到期；
  有上限才不会把数据库打满

## 取消与改期
用户申请延长支付时限 → 改 expire_at 就够了，不需要去撤销一个已投递的延迟消息
（这也是把到期时间放数据库、而不是放队列里的主要原因）
```

<Aside type="danger">
删除、回填、批量通知这类不可逆的副作用，要有明确授权、影响上限、先预演或抽样、审计记录，以及出错之后的回滚或补偿路径。它不会把"无限重试"或者"抛个异常出去"当成恢复方案——那两种做法只是把问题推给下一次执行。
</Aside>

## 排查"任务没执行"时它的查法

先看事实，再看代码——顺序反过来最容易白改一版。

```text
症状                     先看这里
从来没触发过             执行器有没有注册成功、控制台里这条任务是否真的创建了、时区
触发了但每个节点都跑      有没有选主/租约配置，日志里同一秒有几条 start
控制台看不到执行器        注册地址、鉴权、网络；客户端连上不等于服务端已下发
失败了但没重试            这个异常被归成了哪一类，退避配置在哪个环境生效
批任务漏了或重复          游标是否稳定排序、检查点写在事务内还是事务外
延迟任务没到点执行        到期时间来源、时钟与时区、投递记录、消费端是否活着
日志成功但业务没做完      事务边界是否包住了重试、后半段是否被静默吞掉
```

## 它怎么验，以及哪些结论不算数

```text
会按改动挑着跑的
  cron 在时区切换与错过窗口时的行为、长任务与下一次触发重叠、
  重启后的恢复、重复触发、并发实例、执行器注册失败、
  延迟任务的取消与改期、超时、重试打光、分片不均、断点续跑、参数升级、告警恢复

跑完也不能声称通过的
  集群选主        单节点验不出来
  控制台回调      本地起的不是完整链路
  网络分区        要靠故障注入
  真实重试        本地的"失败"通常是手造的
```

<Aside type="caution">
单节点验证证明不了集群行为，最终结论必须把证据边界说清楚。默认优先复用现有的检查、构建或跑一次真实主路径；只有你本轮明确要求，它才会去写测试代码。
</Aside>

## 常见坑

**多实例只加了锁，没加唯一约束。** 锁会在你最不希望的那一次失效，而那一次的表现是用户收到四条短信或者被扣了两次款。

**cron 只在开发环境配了。** 时区和保留天数这类值，测试和生产各有一份配置；只改一处的症状是"本地好的，上去差 8 小时"。

**批处理一次性把全表捞进内存。** 数据量小的时候看不出来，长到一定程度就是一次 OOM，而且往往在凌晨没人看的时候发生。

**把异常一律当成可重试。** 参数错、表不存在、余额不足这类重试一万次也不会好，只会把日志刷满、把告警淹掉。

**任务跑完没有任何可观测记录。** 判断标准很简单：出事之后你能不能说出它上一次跑是什么时候、处理了多少条、停在哪。答不出来就等于没做。

**在后台任务里忘了带租户或身份上下文。** 定时任务没有请求上下文，拿到的可能是上一个任务留下的值，也可能什么都没有然后按全量跑——参见 [tenant-management](/skills/skills-reference/medium/tenant-management/)。

## 最佳实践

- **先想"重复跑一次会怎样"。** 这一个问题能提前挡掉大半事故；答案是"会重复写数据"就先补幂等。
- **状态和进度写进数据，别只写日志。** 断点、执行记录、上次成功时间落库之后，恢复和排查都变成查询。
- **参数用具名类型。** 用宽松的键值结构承载任务参数，改一个字段名不会有任何编译错误，只会在凌晨静默失效。
- **时间相关的值都带单位和范围。** 批大小、超时、退避、保留期散成裸数字之后，没人敢改。
- **验证时把 cron 改快。** 每分钟跑一次能在十分钟里验完的东西，不值得等到明天凌晨。

<Aside type="note">
怎么算真的完成了：你能说出这个任务在几个节点上会触发几次、失败之后会怎样、重复触发会不会重复写数据、跑一半挂了从哪继续；并且这些结论里至少有一条是在真实调度器上跑出来的。
</Aside>
