通知看起来是最简单的功能：调个 SDK 把短信发出去。真正的成本全在后面——验证码能不能被穷举，事务回滚了但短信已经发出去了，供应商返回"已接受"被当成"已送达"，营销短信没有退订入口被投诉，同一条通知偶尔发两遍。

`sms-mail` 把这些前置成硬门槛：先把项目里真实的通知链路查清楚，再写任何供应商专属代码。它管的是通知渠道这一段——契约、适配、可靠性、验证码安全和验证边界。

## 什么时候用

| 你会这样说 | 对应场景 |
| --- | --- |
| "加个短信验证码登录" | 验证码生成、存储、校验、限流 |
| "注册成功要发一封邮件" | 事务型邮件，文本或 HTML |
| "把通知模板改成可配置的" | 模板键、变量约定、多语言与版本 |
| "换一家短信供应商" / "两家都要支持" | 多供应商适配与降级顺序 |
| "怎么知道短信到底发到了没" | 同步响应与异步回执的状态关联 |
| "用户退订了还在收到" | 退订、黑名单、偏好与静默时段 |
| "通知偶尔发两遍" | 幂等键、重试分类与死信 |

## 前置条件

写供应商代码之前，这几件事得有答案。

**真实链路是什么。** 项目里已经有统一通知服务、统一工厂或者一个 MQ 消费者吗，还是要直连 SDK/SMTP。走错入口的结果是仓库里出现两套平行封装，之后每个问题都要修两遍。

**模板由谁管。** 代码里、配置中心里，还是在供应商后台报备的。这决定了变量名怎么校验、改文案要不要发版。

**状态怎么回来。** 发送请求、供应商消息号、同步响应、异步回执、业务状态之间怎么关联。没想清楚的话，"这条短信发到了没"就永远只能靠猜。

<Aside type="danger">
在链路确认之前，不会把某个云厂商 SDK、某个 Mail 工具类或某个通用短信门面当成默认实现。这些库最容易被"大家好像都这么用"的惯性带进项目，结果和仓库里已有的通知入口形成两套并行封装，谁都不敢删。
</Aside>

## 使用示例

### 示例 1：短信验证码登录

你说：`加一个手机号 + 验证码的登录`

验证码不存明文，也不存能离线穷举的裸哈希——六位数字的空间只有一百万，普通哈希拖库之后几秒钟就跑完了：

```java
String code = randomDigits(6, SecureRandom.getInstanceStrong());
String hash = hmacSha256(serverPepper, purpose + ":" + phone + ":" + code);
redis.opsForValue().set(
        "otp:%s:%s".formatted(purpose, challengeId),   // 绑定用途 + 挑战 id
        new Otp(hash, 0),
        Duration.ofMinutes(5));                        // 短 TTL
```

校验成功后原子失效，尝试次数封顶，比较用定长时间：

```java
public VerifyResult verify(String challengeId, String code) {
    Otp otp = redis.opsForValue().get(key(challengeId));
    if (otp == null)          return VerifyResult.expired();
    if (otp.attempts() >= 5)  { redis.delete(key(challengeId)); return VerifyResult.locked(); }
    if (!constantTimeEquals(otp.hash(), hmac(code))) {
        redis.opsForValue().increment(attemptKey(challengeId));
        return VerifyResult.mismatch();
    }
    redis.delete(key(challengeId));     // 一次性消费，不允许复用
    return VerifyResult.ok();
}
```

四类限流各自一把键，共用一把等于没限：

```text
发送   手机号 + 用途    1 次 / 60s，10 次 / 天
校验   challengeId      5 次
重发   手机号           3 次 / 10 分钟
来源   IP               30 次 / 小时
```

```json
{ "code": 200, "data": { "challengeId": "c_9f31a2", "expiresIn": 300 } }
```

上面这个响应刻意不告诉调用方"这个号码已注册"——否则登录接口就成了会员名单查询工具。

### 示例 2：模板与出箱

你说：`注册成功发欢迎邮件，文案以后要能改，还要支持英文`

模板键保持稳定，供应商侧的模板号可以换；变量有明确约定，改文案不用发版：

```yaml
templates:
  USER_REGISTER_WELCOME:
    channel: EMAIL
    locale: [zh-CN, en-US]
    vendorTemplateId:
      vendorA: "SMS_2039"
      smtp: "welcome.html"
    variables:
      nickName:    { type: string, maxLength: 32, required: true }
      activateUrl: { type: url,    required: true }
```

发送不在业务事务里直接调 SDK，而是先落一张出箱表——事务回滚了通知就不会发出去：

```sql
CREATE TABLE notify_outbox (
  id            BIGINT       NOT NULL COMMENT '主键',
  request_id    VARCHAR(64)  NOT NULL COMMENT '幂等键',
  template_key  VARCHAR(64)  NOT NULL COMMENT '业务模板键',
  channel       VARCHAR(16)  NOT NULL COMMENT 'SMS/EMAIL/INBOX',
  recipient     VARCHAR(128) NOT NULL COMMENT '收件地址，入日志时脱敏',
  payload_json  JSON         NOT NULL COMMENT '模板变量',
  status        VARCHAR(16)  NOT NULL COMMENT 'PENDING/ACCEPTED/DELIVERED/FAILED/UNKNOWN',
  vendor        VARCHAR(32)  NULL     COMMENT '实际使用的供应商',
  vendor_msg_id VARCHAR(64)  NULL     COMMENT '供应商消息号',
  retry_count   INT          NOT NULL DEFAULT 0 COMMENT '已重试次数',
  next_retry_at DATETIME(3)  NULL     COMMENT '下次重试时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_request (request_id),
  KEY idx_retry (status, next_retry_at)
) COMMENT '通知出箱';
```

### 示例 3：多供应商与降级

你说：`主供应商偶尔超时，想加一家备用的`

适配器把差异全部消化在里面，业务层看不到任何 SDK 类型：

```java
public interface SmsVendor {
    String name();
    SendOutcome send(SmsRequest req);
}

public record SendOutcome(
        Status status,          // ACCEPTED / RETRYABLE / REJECTED_PERMANENT
        String vendorMsgId,
        String vendorCode,      // 原始错误码，只用于排障
        String message
) {}
```

```text
降级顺序（需要业务授权，不是"哪个通就用哪个"）
主  供应商A   超时 / 限流 / 5xx → RETRYABLE，退避后重投
备  供应商B   仅当 A 连续失败 N 次，且该模板已在 B 报备时启用
终  站内信     只做失败留痕；隐私内容不得从站内信改发短信或邮件
```

### 示例 4：回执状态机

你说：`后台要显示每条短信到底发到了没`

产出是一张明确的状态机，重点是不把"已接受"写成"已送达"：

```text
PENDING ──发送被接受──▶ ACCEPTED ──回执=成功──▶ DELIVERED
   │                        │
   │                        └──回执=失败──▶ FAILED
   ├──参数/模板/黑名单错误──▶ FAILED（不重试）
   └──超时/限流───────────▶ PENDING（退避重投，超上限 → FAILED）

通道没有回执能力时：停在 ACCEPTED，最终标 UNKNOWN，不伪装成 DELIVERED
```

回调入口要验签、防重放，并按供应商消息号幂等更新：

```java
@PostMapping("/api/v1/callbacks/sms/vendor-a")
public String callback(@RequestBody String raw,
                       @RequestHeader("X-Signature") String sig,
                       @RequestHeader("X-Timestamp") long ts) {
    if (Math.abs(System.currentTimeMillis() - ts) > 300_000) return "expired";
    if (!verifySignature(raw, ts, sig))                      return "invalid";
    receiptService.applyIdempotent(parse(raw));   // 按 vendorMsgId 去重
    return "ok";
}
```

重试的分类必须明确，盲重试会把一次投诉变成十次：

| 分类 | 例子 | 处理 |
| --- | --- | --- |
| 可重试 | 超时、限流、供应商 5xx | 指数退避 + 抖动 + 次数上限 |
| 不可重试 | 号码格式错、模板未报备、黑名单、已退订 | 直接 `FAILED`，进人工队列 |
| 状态未知 | 请求已发出但响应丢失 | 按 `request_id` 查询供应商，不直接重发 |

## 常见坑

**在事务里直接调 SDK。** 后面的步骤回滚了，短信已经发出去，用户拿到一个不存在的订单号。走出箱或事务后事件。

**把"已接受"当"已送达"。** 供应商返回 200 只说明它收下了请求，运营商拦截、空号、关机都发生在之后。

**验证码按手机号共用一把键。** 登录、改密、绑卡共用同一个验证码，等于一个场景拿到的码能用在另一个场景。

**盲目重试。** 号码格式错、模板没报备、用户已退订这些重试一万次也不会成功，只会把额度和投诉一起刷上去。

**HTML 邮件直接拼用户输入。** 邮件客户端的渲染差异极大，注入面比网页更难收口。

**退订只做了页面。** 退订状态没有进发送前的检查链路，用户点完照样收到，属于合规风险。

**只测发送成功。** 模板变量缺失、超长、多语言、非法地址、黑名单、静默时段、回执重放、并发发送——这些才是线上会遇到的。

<Aside type="caution">
没有沙箱或真实供应商账号时，只能说静态契约和 mock 路径通过，不能声称送达率、邮件域名信誉或回执链路已经验收。这条写进交付说明，比上线后被运营发现要省事得多。
</Aside>
