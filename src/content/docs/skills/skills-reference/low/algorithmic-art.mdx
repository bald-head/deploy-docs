大多数"帮我用代码画点好看的东西"的请求，最后都会变成一堆调不动参数的一次性脚本。`algorithmic-art` 的价值在于它把这件事拆成两个先后步骤：先确定这套生成美学在追求什么，再用 p5.js 把它实现成一个自包含的网页作品。顺序是固定的——先有语言，才有代码。

它还替你固定了三件工程结果：随机过程带 seed，同一个 seed 一定得到同一幅作品；参数集中成一组可调项，能在界面上实时改；作品外壳从内置模板起步，所以 seed 区域、重新生成、重置和下载这些控件不用每次重新发明。它不做业务界面、不做静态平面设计、不做产品定义、不做数据可视化，也不维护任务状态。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做个生成艺术" | 从一个概念或一句模糊的感觉出发生成作品 |
| "算法艺术" | 需要一套能命名的生成美学，而不是单张图 |
| "用 p5.js 写个粒子系统" | 粒子系统这类涌现行为 |
| "画个流场" | 噪声驱动的连续运动 |
| "做个能调参数的交互视觉" | 需要侧栏参数、重新生成和下载 |
| "同一个 seed 要能画出一样的图" | 需要可复现的生成过程 |

触发词概括起来是三组：生成艺术、算法艺术、p5.js。

## 什么时候不要用

- **业务界面、管理端页面、组件** → [ui-pc](/skills/skills-reference/high/ui-pc/) 或 [ui-app](/skills/skills-reference/high/ui-app/)。生成艺术的评价标准是美学，业务界面的标准是可用性，两套标准不能互换。
- **海报、封面这类静态平面作品** → [canvas-design](/skills/skills-reference/low/canvas-design/)。它是本 Skill 的静态孪生：流程同构，交付的是 PDF 或 PNG，而不是能跑的网页。
- **产品要做什么、验收是什么** → [product-manager](/skills/skills-reference/critical/product-manager/)。
- **业务图表、看板、指标可视化** → 由目标项目已有的图表栈和实现类 Skill 承担；只画结构和流程时用 [mermaid](/skills/skills-reference/low/mermaid/)。数据可视化明确被排除。
- **更新 TODO 状态、记录进度** → [update-status](/skills/skills-reference/medium/update-status/)。

不适用范围概括为四条：业务 UI、静态设计、产品定义、数据可视化。

## 前置条件

它没有声明 `gates`，但正文规定了四个真实输入条件：

1. **已经有一个 TODO 步骤指向算法艺术创作**。它只执行既有 TODO 里的这一步，不自己开任务。
2. **输出路径已经定下来**。优先用用户指定的路径，其次沿用仓库已有的文档目录约定；两者都没有时，会在写第一个文件之前先问你文档存储前缀，而不是自己挑一个目录。
3. **内置的作品外壳模板可读**。这是强制起点，不是可选参考。
4. **有浏览器能打开产物**。交付物依赖 p5.js CDN；环境不具备时会降级并说明边界。

<Aside type="note">
确认过的文档前缀只在当前任务内复用，不会被写成团队全局默认值。临时预览和调试文件不会混进最终交付目录——这一条在验收时值得实际看一眼目录。
</Aside>

## 怎么用

调用方式很轻：把概念、感觉或参考方向说清楚就行，不需要你先给算法、也不需要给参数表。它内部按固定顺序推进：

```text
用户请求 → 算法哲学 → p5.js 实现
```

### 1. 你提供概念，它负责不字面化

它会先判断你真正想表达什么，并把概念做成**嵌进算法里的引用**，而不是主题的字面图解——"关于海洋"就画一堆蓝色波浪，属于这一步的失败形态。所以描述气质、张力、节奏比列出视觉元素更有效。

### 2. 它先交一份美学说明，再动手写代码

第一份产物是一个说明文件：这套生成运动叫什么、它在追求什么、核心原则是什么。这份东西不是交付附赠的文档，它决定了后面的算法长什么样。你可以在这一步就否掉方向，成本最低。

### 3. 实现落在既有外壳里

界面结构、seed 区域和操作按钮属于不动的部分，算法、参数对象和参数控件才是每次真正新写的部分。这条分界让不同作品之间保持一致的交互形态，也让你能只盯着算法看。

<Aside type="caution">
可复现性是这个 Skill 的硬约束：随机必须带 seed，同一个 seed 必须画出同一幅作品。没有 seed 的生成艺术无法复现、无法对比参数改动，也没法把某个具体结果交出去——验收时先做这一项。
</Aside>

### 4. 收口

美学说明和作品文件写进同一个已确认的输出目录；需要提交进仓库时走 [git-commit](/skills/skills-reference/high/git-commit/)，未经授权不做 Git 操作。

## 与其他 Skill 的关系

它的相关列表只有 [canvas-design](/skills/skills-reference/low/canvas-design/)，而且是平铺的，没有声明前置或后续，所以它是一个**独立入口**：上游不强制某个规划 Skill，下游也不自动路由。

- **协作**：[canvas-design](/skills/skills-reference/low/canvas-design/) 负责同一概念的静态表达，两者共用"先定美学、后做实现"的结构和同一套落盘规则。
- **提交**：[git-commit](/skills/skills-reference/high/git-commit/)，在你明确授权之后。
- **状态**：[update-status](/skills/skills-reference/medium/update-status/) 回写 TODO，本 Skill 不代改。

```text
（既有 TODO 中的创作步骤）
        ↓
algorithmic-art → 美学说明 + 自包含网页作品
        ↓
git-commit（用户授权后）
        ↑
canvas-design（同一概念的静态表达）
```

## 产出与验收

你会拿到一份美学说明文件，加一个自包含的 HTML 作品（算法较大时会拆出独立的脚本文件）。除此之外不新增文档。

判断真的完成了：

- 直接用浏览器打开就能跑，不需要本地构建、不需要额外安装依赖；
- 同一个 seed 重新生成得到同一幅作品；
- 侧栏参数真的能改变输出，重新生成、重置、下载都可用；
- 作品外壳与内置模板一致，改动只落在算法和参数部分；
- 交付目录里只有最终产物，临时文件已清掉；
- 原 TODO 步骤的状态由 [update-status](/skills/skills-reference/medium/update-status/) 更新。
