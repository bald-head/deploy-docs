一个注解贴上去，代码看起来干净利落，实际有没有跑是另一回事。自调用绕过了代理，切面顺序把解密排在了幂等之后，限流计数没在集群里共享，脱敏只覆盖了接口响应而导出和日志照样明文——这几种的共同特征是**代码看起来完全正确，注解安静地什么也没做**。

`backend-annotations` 处理的就是这一类横切保护。它先在仓库里找到注解的真实定义和真实执行器，再决定怎么接、参数怎么填、失败怎么办，最后按一张矩阵证明它真的生效了。

它不设计安全策略（那是 [security-guard](/skills/skills-reference/high/security-guard/)），不设计数据权限模型（那是 [data-permission](/skills/skills-reference/high/data-permission/)），也不设计缓存与锁方案（那是 [redis-cache](/skills/skills-reference/medium/redis-cache/)）。它干的是"把已经定好的策略用注解接上去，并证明它在跑"。

## 什么时候用

| 你会这样说 | 对应场景 |
| --- | --- |
| "这个接口要加限流" | 接口防刷与流量保护 |
| "防止用户重复点提交" | 防重复提交与幂等 |
| "手机号身份证要脱敏" | 序列化层字段脱敏 |
| "这个字段要在库里加密" | 字段加密与密钥版本 |
| "接口传输要加密" | 接口级加解密 |
| "查询要自动带上数据范围" | 数据权限注解接入 |
| "注解加了但没生效" | 代理、切面顺序与执行器排查 |
| "两个注解顺序不对" | 多注解组合的执行顺序 |

## 什么时候不要用

- **设计授权、输入与数据安全的整体策略** → [security-guard](/skills/skills-reference/high/security-guard/)。策略归它，接入与验证归这里。
- **设计行级/字段级权限模型** → [data-permission](/skills/skills-reference/high/data-permission/)
- **设计缓存与分布式锁方案** → [redis-cache](/skills/skills-reference/medium/redis-cache/)。限流和幂等依赖的键与过期语义由它定。
- **定义接口契约与错误码** → [api-development](/skills/skills-reference/high/api-development/)
- **前端装饰器或表单校验** → [ui-pc](/skills/skills-reference/high/ui-pc/) / [ui-app](/skills/skills-reference/high/ui-app/)
- **业务逻辑本身** → [dev](/skills/skills-reference/high/dev/) 或对应业务 Skill
- **框架层面为什么慢** → [performance-doctor](/skills/skills-reference/medium/performance-doctor/)

## 前置条件

三条都在拦同一种错觉：贴了注解等于做完了。

**机制确实存在。** 仓库里有注解和切面这类横切机制，或者已经决定引入哪一套。否则就是凭名字猜一套不存在的 API。

**改的是横切保护，不是业务规则。** 状态转换、金额计算、库存扣减这类业务不变量不该藏进注解里——它们需要显式代码和显式测试。

**注解定义和执行器都找到了。** 找不到执行器，就说不清它什么时候跑、以什么顺序跑，也就没法验证。

<Aside type="caution">
仓库里确实没有目标机制时，它会先给方案，而不是直接产出一段看起来可编译的项目专属注解代码。凭名字虚构出来的注解类、枚举和包名，编译一跑就露馅，浪费的是你的时间。
</Aside>

## 使用示例

### 示例 1：给验证码接口加限流

你说：`发验证码的接口被刷了`

第一步永远是找到定义和执行器，而不是照抄旁边那个接口的写法：

```bash
rg -n "@interface RateLimiter" --type java
rg -n "RateLimiter\.class" --type java -g '*Aspect*' -g '*Interceptor*'
# → common/annotation/RateLimiter.java
# → common/aspect/RateLimiterAspect.java:41
```

第二步打开定义看默认值——这里最容易踩坑：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimiter {
    int       count();                          // 无默认值，必须显式给
    int       time()    default 60;             // 单位秒
    LimitType type()    default LimitType.DEFAULT;  // DEFAULT 按接口，不区分用户
    String    message() default "访问过于频繁";
}
```

注意那个 `DEFAULT`：它按接口维度限流，也就是说一个用户把额度用完，其他所有人都被挡在外面。发验证码要的是按手机号或 IP：

```java
@RateLimiter(count = 5, time = 60, type = LimitType.IP)
@PostMapping("/api/v1/auth/captcha")
public R<Void> sendCaptcha(@RequestBody @Valid CaptchaReq req) { ... }
```

```json
{ "code": 429, "message": "访问过于频繁，请稍后再试" }
```

### 示例 2："注解加了但没生效"

你说：`@Idempotent 加上了，批量导入还是重复写了`

产出是一个具体的绕过原因，加上改法：

```java
// 不生效：this.saveOne 走的是原始对象，代理根本没参与
public void batchImport(List<Row> rows) {
    for (Row r : rows) this.saveOne(r);
}
@Idempotent(key = "#r.bizNo")
public void saveOne(Row r) { ... }

// 生效：让调用经过容器里的代理对象
@Autowired @Lazy private ImportService self;
public void batchImport(List<Row> rows) {
    for (Row r : rows) self.saveOne(r);
}
```

同一类问题的其他形态：

```text
自调用           this.method()           代理未参与
final / private  方法无法被子类代理       CGLIB 织入失败，且通常没有报错
非容器对象       new 出来的实例           完全没有代理
@Async 线程      ThreadLocal 上下文丢失   主体、租户、traceId 全没了
多数据源         切面在数据源切换之后跑    条件注入到了错误的连接上
```

### 示例 3：多注解的执行顺序

你说：`解密和幂等好像顺序不对，密文被当成了幂等键`

产出是显式声明的顺序，加上一份实测的调用链：

```java
@Aspect @Order(10) public class DecryptAspect    { }   // 先解密
@Aspect @Order(20) public class RateLimitAspect  { }   // 再限流
@Aspect @Order(30) public class IdempotentAspect { }   // 再幂等
@Aspect @Order(40) public class DataScopeAspect  { }   // 数据范围最后进 SQL
```

```text
打点日志实测（一次成功请求）
DecryptAspect.before → RateLimitAspect.before → IdempotentAspect.before
  → @Transactional 开启 → DataScopeAspect.beforeQuery → SQL
  → 事务提交 → IdempotentAspect.afterReturning（写入成功态）
```

顺序错了会怎样：解密排在幂等之后，幂等键算的是密文；同一份明文两次加密得到不同密文，于是两次都放行。

### 示例 4：脱敏注解的覆盖面

你说：`手机号加了脱敏注解，但客服反馈导出的 Excel 里还是明文`

```java
@Sensitive(strategy = SensitiveStrategy.PHONE)
private String phone;         // 序列化时输出 138****8000
```

产出是一张出口清单——脱敏注解挂在序列化层，凡是不走那条序列化链路的出口都不受它保护：

```text
接口响应     ✓ 走 Jackson，注解生效
业务日志     ✓ 打印 DTO，不打 Entity
Excel 导出   ✗ 反射直取字段值，绕过序列化器  ← 你遇到的就是这条
MQ 消息      ✗ payload 直接塞了 Entity
异常堆栈     ✗ 参数被框架打进 WARN
对账文件     ✗ 自己拼的 CSV
```

### 示例 5：验证矩阵

限流类注解至少要跑这四组，其中后两组最常被跳过：

```bash
# 命中与超限
for i in $(seq 1 7); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://localhost:8080/api/v1/auth/captcha
done; echo
# → 200 200 200 200 200 429 429

# 跨实例是否共享计数
curl -s ... :8081/api/v1/auth/captcha    # 换一个实例，计数应该延续

# 依赖故障时的行为
docker stop redis-1 && curl -s -o /dev/null -w "%{http_code}\n" -X POST ... ; docker start redis-1
# fail-closed → 503；fail-open → 200。必须是明确选择，不能是意外结果
```

```text
验证矩阵（示例结论）
正常命中              ✓
超限拒绝              ✓ 第 6 次起 429
双实例共享计数        ✓ Redis 键一致，计数延续
Redis 故障            ✓ fail-closed，503 且日志有 WARN，无静默放行
自调用路径            ✓ 改为代理调用后生效
注解被误删            ✓ 测试会失败（断言的是行为，不是注解存在）
@Async 线程内         ✗ 上下文丢失，未覆盖  ← 写进未验证边界
```

## 七类横切能力速查

每一类要先确认什么、真实风险在哪：

| 能力 | 需要确认 | 关键风险 |
| --- | --- | --- |
| 限流 | 作用域、键、时间窗与算法、集群一致性、失败策略 | 错限用户、依赖故障放大、代理绕过 |
| 防重复 / 幂等 | 幂等键、有效期、请求体规范化、成功后状态 | 正常重试被误拒、同键不同请求 |
| 脱敏 | 序列化路径、角色场景、日志与导出覆盖 | 只保护了接口响应 |
| 字段加密 | 密钥版本、确定性与随机性、查询能力、迁移 | 加密后无法检索、轮换失败 |
| 接口加密 | 威胁模型、是否已有 TLS、签名与重放、客户端兼容 | 自研密码协议、边界画错 |
| 数据权限 | 注入点、表别名、上下文来源、缓存 | 条件漏加、跨租户、后台任务无上下文 |
| 审计 / 日志 | 记录内容、脱敏、失败是否记录、关联 ID | 记录了密钥、日志变成业务事务 |

## 常见坑

**照抄旁边的用法但不看定义。** 默认时间窗、默认作用域、默认失败策略往往和你以为的不一样，而这三个都会静默生效。

**把业务不变量塞进注解。** 状态转换和金额校验放在切面里，测试覆盖不到，改注解参数就能改变业务行为。

**静默吞异常。** 切面里 `catch (Exception e) {}` 之后，限流和权限都变成了装饰。

**单机验证通过就算完。** 限流计数没共享时，两个实例的额度各算一份，实际放行量翻倍。

**用表达式做复杂逻辑。** 键里写一长串 SpEL，运行期解析失败只会抛一个看不懂的异常，编译期什么都发现不了。

**只断言注解存在。** 测试写成"这个方法上有 `@RateLimiter`"，注解改了参数照样通过。要断言行为。

<Aside type="note">
最终交给你的是：注解定义与执行器的文件位置、选择理由、参数与执行顺序、失败策略是 fail-open 还是 fail-closed、代码位置、验证命令与结果，以及矩阵里哪几行没验证。指着源码能说清"这个注解由哪个执行器在什么时机处理、和旁边那个谁先谁后、依赖挂了它放行还是拦截"，才算真的接完。
</Aside>
