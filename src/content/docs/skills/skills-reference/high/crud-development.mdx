## 概述

增删改查是"看起来最简单、返工率最高"的一类功能。返工往往不是因为写错了 SQL，而是因为交付停在了半途：接口通了但没有页面，页面画了但连的是假数据，菜单出现了但后端没鉴权，或者页面只把接口返回的东西堆成一片字段，用户拿它办不了事。

`crud-development` 的定义就是不允许停在半途：一个功能要覆盖数据模型、库表迁移、访问层、业务规则、接口和真实页面联动，而且页面必须调真实后端接口、把真实响应渲染到用户看得见的查询、详情或操作状态里。菜单显示、权限 SQL、孤立接口、静态页面——这四样都不算完成证据。

它也不会先假设你的分层、ORM 或基类长什么样。写代码之前先建"适配档案"，把仓库真实的技术事实摸清楚。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做个用户管理" | 列表、详情、新增、编辑、删除的完整纵向交付 |
| "加个部门维护的页面" | 后端加页面一起做，页面接真实接口 |
| "这个列表要能按状态筛" | 查询条件、排序白名单、分页边界 |
| "批量删除做一下" | 批量上限、失败语义、归属校验 |
| "这些数据要能导出" | 导出分批与数据量验证 |
| "加个逻辑删除和恢复" | 软删除、唯一索引、状态冲突的响应 |
| "这张表要加审计字段" | 审计语义、字段命名和类型跟随仓库现有基线 |

触发面覆盖增删改查、列表加编辑、业务功能落地这几类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

先分清最容易混的一对：

| 你要做的事 | 归属 |

口头说"生成一个 CRUD"不构成生成器存在的证据。生成器不存在，或者你要的是完整业务，都走本页。

其他边界：

- **开发或维护生成器本身** → [code-generator](/skills/skills-reference/low/code-generator/)。它不承担业务规则与页面实现。
- **只要持久层与迁移** → [database-ops](/skills/skills-reference/high/database-ops/)；**表结构设计** → [database-design](/skills/skills-reference/high/database-design/)。

## 前置条件

三条门槛：

1. **需求和验收标准已经批准**。"做个用户管理"没说清能不能删、谁能删、删了还能不能恢复，这三件事最后都会变成返工。
2. **技术选型和库表设计已经做完**。它按已有结论实施，不在写代码的过程中顺手做选型。
3. **前后端架构和调用路径已经明确**。页面挂在哪个路由、走哪条接口、权限在哪一层判断——不定下来，页面就只能连假数据。

### 硬门禁：先建适配档案

取事实的优先级固定：当前 TODO 的功能 → 目标源码适用的仓库规则与构建依赖 → 相邻源码、配置、迁移和现有验证 → 最后才是 Skill 里的示例。证据链同样固定：规则 → 构建依赖 → 模块结构 → 相邻的同类实现 → 库表迁移 → 测试。

至少要记下这六项：

1. 语言、框架、ORM、代码生成器、映射器、校验器，以及响应和分页类型；
2. 目标模块实际怎么分层（不一定是三层，也可能是 Repository、DAO 或别的组合）；
3. 主键怎么生成，审计和租户字段叫什么，逻辑删除、乐观锁、字典、软删除各自的既有约定；
4. 查询、排序、分页、批量、导出、异常和权限各自的真实入口；
5. 迁移、索引、命名、字符集、时间与数值类型，以及回滚方式；
6. 至少一个同类的生产模块，以及它的单元、接口或集成测试。

<Aside type="danger">
任何一项没确认，它就用中性占位，不生成"看起来可以直接编译"的项目代码，也不声称已经遵循了项目规范。这条约束的意义在于：一份能编译但类名、基类和响应包装全是猜的代码，比空白更难清理。
</Aside>

## 怎么用

实施顺序九步，从领域一直到验证：

1. **领域与不变量**：状态、唯一性、必填、可改范围、删除语义、资源归属、幂等键。
2. **库表**：列、类型、默认值、索引、迁移与回滚；先确认现有表，再谈加字段。
3. **对象契约**：持久化对象只映射库表字段；入参做白名单校验；出参最小化敏感字段；空值、时间和大整数精度都显式处理。
4. **业务层**：权限判断、状态流转、唯一性和关联存在性都放在事务边界之内；批量动作有条数上限，且失败后可以重试。
5. **访问层**：先认清仓库现在用的是哪套持久化框架，跟随它的参数化、类型安全查询、分页和排序机制，不把某一种 ORM 当成跨项目默认。用户输入绝不拼进 SQL。
6. **接口层**：新增业务 JSON 接口走全 POST 加请求体基线，成功结果走项目统一响应包装；文件上传用 `multipart/form-data`，动作仍是 POST。已经完善的存量接口保持原方法、参数绑定和客户端契约，内部补强不触发机械改造。
7. **通用生产规则**：按已加载的规则实施类型、字面量、命名和源码文档要求；仓库例外必须有真实契约或生成器证据。
8. **页面联动**：有 Web 入口时交 [ui-pc](/skills/skills-reference/high/ui-pc/)，由它结合这套系统的性质、用户要完成的任务、已批准的设计稿和项目 UI 体系，把主工作流做出来。后台管理型的增删改查按适用范围组织路由与菜单上下文、查询区、主次操作、表格表单详情；不是这一类的系统，用与它自身性质匹配的结构。全部页面都要做权限、加载、空、错、成功和异常恢复，并适配宽屏、常用工作屏和窄窗口。
9. **测试与迁移**：先跑最小单元，再跑库表、接口或契约回归；记录命令、结果和未覆盖的边界。

<Aside type="caution">
第 5 步有一条硬红线：控制器、业务层和领域服务里不许直接写 SQL——`JdbcTemplate`、裸 JDBC、native 查询和 SQL 文本块，都算绕过访问层。复杂的 join、递归、聚合和窗口查询只能放进目标框架专门的持久化边界——MyBatis 项目放 Mapper XML 加具名方法，其他 ORM 用仓库已经采用的等价机制。MyBatis-Plus 只有在真的检测到之后才有额外要求：走项目自己的 Mapper 和 Lambda 形式的条件构造 API，不用以字符串写列名的那种写法。
</Aside>

### 新建 Java 表的默认基线

这几条是用户约束下的默认值，但字段名、类型和可空性仍以仓库现有基线为准：

- 新 Java 项目、且没有既有主键约定时，主键用 [snowflake-id](/skills/skills-reference/low/snowflake-id/) 提供的自实现生成器与配置类；不引 Yitter JAR，也不把 MyBatis-Plus 的 `ASSIGN_ID` 当默认方案。
- 表之间用逻辑外键字段加索引，配合业务层的存在性和归属校验；不新增数据库物理外键。已有的物理外键要迁移时单独评估，不偷偷删掉。
- 审计字段优先保留这几项语义：创建人及其所在部门、创建时间、最后更新人、更新时间，业务备注可选。
- 主键和关联标识经过 JSON、分页和前端传输时，要防住浏览器端大整数精度丢失。

### 查询、写入与异常的门禁

查询条件和排序字段走白名单；分页上限、深分页方案和导出分批按真实数据量验证。改和删都要带上稳定主键、版本号或幂等条件，并且核对这条记录是不是属于操作者；一批里有失败时，要事先说清是整批回滚、允许部分成功，还是走补偿。逻辑删除、唯一索引、并发更新、空更新和状态冲突各自要有明确响应。关联查询只依赖逻辑外键和业务层权限，不能凭客户端传来的关联标识越权读到别人的数据。

用户能看到的异常全部用简体中文，给可操作的建议，但不暴露 SQL、堆栈、包名和敏感字段；服务端日志保留关联 ID。

## 产出与验收

交付时列出：适配档案及其来源、领域与表与索引与审计契约、真实分层与接口映射、主键和逻辑外键方案、修改的文件、测试命令与结果、迁移回滚方案、未验证的边界。

判断真的完成了，这几条要全部为真：

- 构建、代码生成或编译、格式检查都过了；
- 新增、查询、详情、修改、逻辑删除与恢复、批量、导出的边界都验过；
- Web 入口符合系统性质、用户任务和已批准设计，接的是真实接口，权限和异常恢复正常，宽屏／常用工作屏／窄窗口都自适应；
- 库表里的菜单与按钮权限、默认角色授权，跟后端鉴权和 Web 入口三方一致；
- 真实请求返回的数据，在页面的查询、详情或操作状态里肉眼可见；
- 参数缺失、格式错误、重复键、越权、状态冲突都有中文异常；
- 分页与排序白名单、空结果、深分页、大整数、时间时区都验过；
- 业务代码里没有绕过访问层的 SQL；
- 主键并发唯一、逻辑外键不存在或跨租户的情形、审计字段、索引都验过；
- 迁移的前后兼容、回滚方案，以及"库里没有物理外键"这一条，都检查过。

<Aside type="note">
它不创建或更新 TODO、不改功能状态、不操作 Git，只把路由顺序、修改结论、验证结果和未覆盖边界交回 feature owner。当前功能的用户结果、菜单入口、验收或交付边界无法从 TODO、源码和直接来源确定时，它返回 `scope-change-detected`。
</Aside>
