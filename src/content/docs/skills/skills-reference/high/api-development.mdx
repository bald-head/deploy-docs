## 概述

接口能调通只是最低门槛。真正花时间的都在后面：字段改名之后已发布的客户端还能不能用、批量提交一半成功算什么结果、雪花 long 主键到了浏览器会不会掉精度、分页翻深了总数还要不要算。

`api-development` 的做法是先把契约定下来再写框架代码——消费者是谁、输入输出长什么样、错误怎么表达、权限和幂等边界在哪、兼容策略是什么。落地时它只用目标仓库确实存在的东西：检测到 Spring Web 才用对应的请求绑定与异常映射注解，检测到 Bean Validation 才用对应版本的约束注解（不混用 `javax` 与 `jakarta`），检测到 SpringDoc / OpenAPI 3 才按文档规则写模型。证据不齐时它只给候选设计和待验证项，不会虚构统一响应类型、注解、包名、分页类型、错误码或文档地址。

它管的是接口这一层：契约、校验、错误语义、文档。数据怎么存、页面怎么写、威胁怎么防，各有各的 Skill。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "加一个提交审批的接口" | 新增业务接口，要定请求、响应、错误和权限 |
| "这个参数怎么校验" | 结构、格式、集合元素、跨字段规则各自的落点 |
| "前端说返回的 id 对不上" | 大整数精度、序列化与跨层字段映射 |
| "批量删除要能一次传多个" | 空集合、重复项、部分成功、原子性、上限 |
| "改字段名会不会把老客户端搞坏" | 兼容性判断、版本、灰度与迁移方案 |
| "接口文档得能自动出" | 文档依赖与配置，文案来自真实代码而不是手写示例 |
| "重复点两次会创建两条" | 幂等键、重复提交、并发冲突、超时重试 |

触发面覆盖新增接口、改接口、定契约、补校验、错误语义和文档集成这几类说法，具体触发词由 Skill 自己的 frontmatter 维护。

- **客户端怎么消费这些接口** → [alova-client-usage](/skills/skills-reference/low/alova-client-usage/)、[alova-wormhole-usage](/skills/skills-reference/low/alova-wormhole-usage/)、[worma-guidelines](/skills/skills-reference/low/worma-guidelines/)。它们消费契约，不定义契约。
- **服务边界怎么切** → [architecture-design](/skills/skills-reference/high/architecture-design/)。

## 前置条件

三条门槛的共同目的是：不让契约靠猜。

1. **接口类型和网关策略已经从仓库事实或架构结论里定下来**。同一个标识放在路径、查询还是请求体，会连带影响网关、权限和日志，先定下来才谈方法选择。
2. **有相邻的生产接口可以参照，或者有明确的接口规范**。没有参照物时，命名、响应包装和错误映射只能编，编出来的第一版必然返工。
3. **认证授权策略已确认，或者明确不需要**。鉴权决定路径放不放行、失败用哪个状态码、越权的负向用例怎么写。

取事实的优先级是固定的：当前 TODO 的功能 → 目标源码适用的仓库规则与构建依赖 → 相邻源码、配置和现有验证 → 最后才是 Skill 里的示例。确认顺序同样固定：规则 → 依赖 → 配置 → 定义与初始化 → 生产调用 → 测试。

## 怎么用

七步执行流程：

1. **建立契约表**：消费者、入口、方法与动作、请求、响应、状态码与业务码、权限、幂等、兼容、SLA。
2. **搜索可复用契约**：同业务的请求/响应对象、分页、错误、转换器和相邻接口。不要只因为方法名不同，就复制出一份同构类型。
3. **选定契约档案**，并把证据和例外记下来。
4. **实现最小闭环**：请求绑定、校验、业务调用、响应映射、错误处理、文档。
5. **核对消费者**：前端类型、SDK、消息 Schema、网关、权限、序列化。只验证服务端能编译不算完成。
6. **验证正反路径**：成功、参数错误、资源不存在、重复、越权、并发、批量、超时、兼容。
7. **交付证据**：事实来源、变更文件、契约差异、测试命令、示例、未验证边界。

### 契约档案：先选一个，并写下为什么

这是最容易被误用的地方——把某一种风格当成所有项目的默认。四种档案的适用条件不同：

- **仓库兼容档案**（改存量项目时的默认）：保持与相邻接口和已发布客户端兼容。现状确实有缺陷时，先列影响、迁移和版本策略，不静默改动方法、字段名、状态码或响应包装。
- **标准 HTTP 档案**（没有专门约束时）：按读取、创建、替换、局部修改、删除的语义选方法，并明确安全性、幂等性与缓存行为。成功和失败的状态码要表达真实结果，不是所有响应都回 200。
- **本项目接口基线**（项目发起人已确认）：新增业务接口统一 `POST`，业务参数放进一个专用请求体对象；分页、筛选、详情标识、状态标识、批量标识和动作参数都不放进 query、path 或路径变量。JSON 成功结果走项目统一响应包装，不塞进 Header、路径或裸 `Map`。文件上传是唯一输入例外：用 `multipart/form-data` 加明确的文件对象，动作仍然是 `POST`。
- **全 POST 严格档案**：只有用户、规则文件或稳定的相邻源码明确采用时才启用。启用它不等于可以放弃标准 HTTP 语义——健康检查、文件流、回调地址、Webhook、缓存读取，以及需要向第三方兼容的接口，例外与否只能由真实契约说了算。

<Aside type="caution">
基线只作用于**本次明确新增**的业务接口。既有接口已经完善时保持原有方法、参数绑定和客户端契约；修实现、补校验、补权限、补租户、补审计都不触发机械改造。要动已经公开的契约，必须由批准需求划定范围，并同步处理兼容、客户端和迁移。
</Aside>

### 几条绕不开的约束

- 对外契约用稳定的业务语义，不把持久化实体、ORM 分页对象、内部异常或第三方原始响应直接暴露出去。
- 校验分两层：结构、格式、集合元素和跨字段规则在参数层；依赖数据库、权限、库存或状态机的判断留在业务层。
- 用户能看到的参数错误和业务错误用简体中文；服务端保留 cause 和关联证据，堆栈、SQL、路径、Token、密钥都不下发到客户端。
- 分页要明确页码或游标、稳定排序、最大页大小和总数成本；过滤与排序字段走白名单加参数化查询。
- 写接口的幂等键、重复提交、并发冲突和超时重试都要显式定义——HTTP 方法本身推不出业务幂等。
- 批量接口得把这些都说清：传空数组算什么、重复项怎么处理、要不要保证顺序、一半成功算成功还是整批回滚、单次最多多少条、失败之后能不能重试。
- 主键是雪花 long 而消费方是 JavaScript 时，按双方已确认的契约以字符串下发，否则越过安全整数范围的值会静默失真。
- 同一个属性在 Java 里、在 JSON 里、在数据库列上、在 Header 里各叫什么，要一层一层看过；任何一层都不能拿来推断另一层。
- 统一响应、分页、转换、权限、日志、防重和异常类只复用仓库里已经存在且有生产调用的实现，不按示例名称另起一套。

## 产出与验收

输出固定六段：已确认的协议、框架与相邻接口来源；选定的契约档案及依据；请求、响应、错误与兼容契约；实现或修改的文件；客户端、网关与文档的同步情况；测试命令与结果；迁移、回滚与未验证边界。

判断真的完成了，把这几件事逐条对上：

- 选定档案和实际实现对得上——方法、路径、动作、版本一致；
- 入参侧写明了来源、必填与否、默认值、空值、集合元素和跨字段规则；
- 出参侧不含持久化对象、内部异常和敏感字段；
- 全局错误契约那一侧对齐了 HTTP 状态、业务码和中文提示；
- 负向用例真的跑了：越权、跨租户、归属不符、重复提交、并发冲突；
- 边界用例真的跑了：翻页深度、排序白名单、过滤白名单、批量条数上限；
- 大整数、金额、日期时区、枚举、文件和空值的序列化两端一致；
- 文档由代码或 Schema 生成，里面没有凭据也没有编出来的示例；
- 已发布客户端的兼容判断、迁移步骤和回滚路径都写下来了；
- 契约或接口测试是真的执行过的，不是只跑了一遍静态扫描。

<Aside type="note">
它不创建或更新 TODO、不改功能状态、不操作 Git，只把路由顺序、修改或只读结论、验证结果和未覆盖边界交回 feature owner。当前功能的用户结果、菜单入口、验收或交付边界无法从 TODO、源码和直接来源确定时，它返回 `scope-change-detected`，而不是自己把范围撑大。
</Aside>
