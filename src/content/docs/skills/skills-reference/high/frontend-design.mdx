## 概述

一份"看起来没问题"的设计交到实现手上之后，写代码的人还要当场决定十几件事：没数据的时候这块显示什么、请求慢了给不给骨架屏、没权限时按钮是灰的还是不见、备注写了两千字怎么截、提交失败能不能重试。这些当场拍的决定，就是后面返工的来源——它们全都属于设计，只是没人写下来。

`frontend-design` 的产出不是稿子，是一份让实现不用猜的设计基线（DesignContract）：每个表面写清入口与用户任务、信息层级、真实数据形状、布局与断点规则、每个动作的行为与权限与后端契约、必须覆盖的状态、无障碍与动效边界，最后附上实现完成后必须真实渲染出来的验证清单。

它不写生产页面代码，也不选框架、组件库、请求层或桌面壳——那些属于技术决策。真实效果由 [ui-pc](/skills/skills-reference/high/ui-pc/) 和 [ui-app](/skills/skills-reference/high/ui-app/) 落地。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做一个订单列表和订单详情" | 新增界面的结构、交互与状态基线 |
| "这个页面要重构一下" | 已有界面的行为或结构要变，基线需要重定 |
| "这块交互我说不清该怎么定" | 关键交互存在歧义，先把契约定死再实现 |
| "客户想先看设计再开发" | 先审设计的交付模式 |
| "后端接口有了，前端怎么接" | 后端功能对应的入口、状态、权限反馈与恢复路径 |
| "这个图表组件能不能支持下钻" | 会实质改变布局、成本或验收的技术未知，走可行性探针 |

触发面覆盖界面设计、交互定义、状态与权限表达这一类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **已有界面只是不好看、不顺手，行为不变** → [frontend-polish](/skills/skills-reference/high/frontend-polish/)。分界很清楚：从零设计新界面、或者重构会改变行为的界面，归本 Skill；已有实现的视觉与手感打磨，归它。走错的代价是本来复用现有基线就能改完的事，被重新定了一遍基线。
- **要把设计写成页面代码** → [ui-pc](/skills/skills-reference/high/ui-pc/)（PC/管理端）或 [ui-app](/skills/skills-reference/high/ui-app/)（移动与跨端）。
- **产品目标或业务规则本身还不清** → [product-manager](/skills/skills-reference/critical/product-manager/)。设计不替产品做决定。
- **还在比几个方案，没收敛** → [brainstorm](/skills/skills-reference/medium/brainstorm/)。收敛之后再进本 Skill，否则会在设计阶段第二次发散。
- **要定具体技术、版本、组件库** → [tech-decision](/skills/skills-reference/high/tech-decision/)；**要定接口契约** → [api-development](/skills/skills-reference/high/api-development/)；**要定表结构** → [database-design](/skills/skills-reference/high/database-design/)。
- **只想审现有动效** → [review-animations](/skills/skills-reference/low/review-animations/)；**只想把模糊的动效描述换成准确术语** → [animation-vocabulary](/skills/skills-reference/low/animation-vocabulary/)。
- **要在 Penpot 里画出可点的原型** → [penpot-prototype](/skills/skills-reference/low/penpot-prototype/)。文字规格不等于原型，不能互相冒充。
- **要品牌视觉规范** → [brand-guidelines](/skills/skills-reference/low/brand-guidelines/)；**要海报或艺术图** → [canvas-design](/skills/skills-reference/low/canvas-design/)。
- **纯后端，且批准需求或架构边界能证明没有客户端** → 不为它创建设计任务。

## 前置条件

三条门槛，每条都在挡一种具体的失败。

1. **完整的产品定义已经消费过了，或者已经明确这次不需要产品构思。** 缺这一条，设计就会顺手替产品做决定——多出一个"批量导入"，或者把"不支持第三方登录"悄悄改成支持。
2. **批准的交付面确实包含 Web / App / Desktop。** 纯后端不需要设计任务；硬做一份，实现阶段没人会读。
3. **这不是已有页面的纯视觉精修。** 那种情况复用现有基线直接改更快。

进入之后还有一道事实门禁：先读用户约束、产品大纲、批准交付面、仓库规则、构建与锁文件、路由、设计 tokens、相邻的生产页面和真实内容，然后把手上的信息分成三档——**已确认事实**，用户、仓库或批准需求里有证据；**待确认假设**，缺了它，页面结构、交互、权限、数据形状或验收条件里至少有一项定不下来；**通用候选**，只在发散时借用，不能冒充这个项目已有的事实。

<Aside type="danger">
不能从示例反推项目：框架、组件库、主题数量、目标 viewport、用 Modal 还是 Drawer、桌面壳形态、页面结构、品牌——这些都必须从仓库或批准需求取证。技术可行性可以作为设计输入，但具体技术由 [tech-decision](/skills/skills-reference/high/tech-decision/) 冻结。
</Aside>

## 怎么用

### 1. 消费构思，不重复发散

规划里做过一次的候选、取舍和选中方向直接拿来用；在选中的那个方向里面再比一比信息层级、布局和交互表达，给出推荐做法、被淘汰的做法、各自适用的条件和风险。这一层取舍不允许改变用户结果、业务规则、权限或交付范围。真发现了新的实质方案空间，返回 `scope-change-detected`，交 [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/) 决定要不要回到产品构思——设计不自己扩范围。

能从需求、仓库、设计系统或平台事实查出来的，直接取证不问人。只有查不到、且会实质改变已选设计结果的决定才走 [grilling](/skills/skills-reference/medium/grilling/)，一次一个问题，带推荐答案和取舍。

### 2. 把基线写成实现能照着做的形状

字段不适用就省略，但下面这些一旦缺失，实现就得靠猜：

```yaml
designBaseline:
  productIntent:      # 角色、核心任务、可观察的成功结果、明确不做的事
  surfaces:
    - surfaceId:      # 页面/窗口标识与真实（或待创建）入口
      purpose:        # 这个表面帮谁完成什么
      informationHierarchy:      # 内容顺序与优先级
      realContentAndDataShape:   # 字段、列表、图表、单位、长文本的真实形状
      layoutAndResponsiveRules:  # 布局、断点、滚动与密度
      componentsAndActions:
        - actionId:   # 稳定动作 ID
          behavior:   # 触发、确认、反馈、恢复
          permission: # 真实权限语义
          backendContract:  # 接口/IPC/事件绑定，或标注待冻结
      states:         # default / loading / empty / error / success + 适用的交互态
      accessibility:  # 键盘与触控、焦点、语义、对比度、reduced preferences
      motion:         # 目的、触发、可中断、性能、reduced-motion；不适用则省略
  designSystem:       # 可复用的组件/tokens/字体/图表，以及确有必要的新增项及原因
  feasibilityProbe:   # 见下一节
  verification:       # 目标 viewport/设备、实现后必须真实渲染的状态、未闭合边界
```

基线可以直接写进已有设计文件、Issue、项目文档或那份唯一 TODO，不要求另起一份 Markdown。主题数量按项目实际需要，不固定两套。

### 3. 可行性未知用探针挂起，而不是回避

`feasibilityProbe` 只解决"会实质改变设计"的最小技术未知，它有五个状态，含义各不相同：

```text
not-required       没有会改变设计的未知
pending-g2         已挂起，交 architecture-design / tech-decision 取证
passed             证据到手，设计不变
fallback-selected  证据不支持，采用已批准的降级方向并递增设计版本
failed             未闭合状态——开发者不得现场改版
```

`pending-g2` 允许先交项目经理拆依赖图，但受影响的功能必须等状态变成 `passed` 或 `fallback-selected` 才能进入可执行队列。这一条的意义是：不确定的地方被显式挂着，而不是在实现阶段变成某个人的临时决定。

### 4. 后端有入口，页面就必须同时定

批准范围里的后端功能只要存在界面或交互入口，设计必须同时给出：它对应哪个表面、哪个入口、用户在那里完成什么任务；接口或 IPC 在哪一处被消费、返回的数据长什么形状、权限不足时给什么反馈；加载中、空、出错、成功这四种表现，加上这个平台上适用的交互态；提交、撤销、重试、重复操作和异常之后的恢复路径；以及实现完成后要跑一遍的真实主路径。

<Aside type="caution">
缺了对应页面设计，项目经理就不该把这个后端功能拆成"后端先做完、前端以后再说"的完整交付——那样勾上的格子不代表用户能用上任何东西。纯后端只有在批准需求或架构边界明确证明没有客户端时才裁剪。
</Aside>

### 5. 硬门禁：真实产品，不是模板

- **不出现没有依据的那一套**：紫蓝渐变、没有语义的玻璃效果、卡片里再套卡片、一排堆着的胶囊、鼠标划过就整体放大、没有理由的入场错峰、Hero 加三列卡片，还有伪造的指标、Logo、用户评价和空泛的"智能赋能"文案。层级该由真实任务、真实内容、信息密度、品牌和风险撑起来。
- **不重复说已经说过的话**：菜单、面包屑、页签或布局标题已经交代了这个界面是干什么的，内容区就不要再放一遍标题、用途副标题、逐页业务介绍、显而易见的操作说明或技术口径——管理页、工作台、驾驶舱一视同仁。就近说明只留给真实限制、风险、合规要求、不可逆影响、必须解释的空态与错误态，以及确实存在的上手成本。例外是那些本来就没有导航上下文的场景：独立全屏展示、登录页、首次引导、品牌空态，它们可以保留一个必要标题或一句简短的业务定位，但不写宣传口号。
- **客户可见文案面向用户任务**，不暴露 AUTHZ、RBAC、接口、WebSocket、IPC、事实源这类工程黑话。
- **状态、权限与退路**：关键动作至少要有默认、进行中、成功、失败四种表现，外加失败之后怎么回到可用状态；界面上隐藏或禁用不能替代后端强校验，`actionId -> 权限 -> 界面 -> 接口 -> 后端 -> 错误与审计 -> 验证` 这条链要能在后续阶段对齐。长文本、空数据、慢请求、重复提交、权限不足、数据过期——这六种情况实现阶段一定会遇到，基线里就该有答案，而不是留给写代码的人临场决定。
- **响应式、无障碍与动效**：屏幕尺寸、设备类型、输入方式和信息密度按真实使用场景取，不套 `1920x1080` 这类固定值，也不套某一套现成断点。键盘要有和触控等价的路径，焦点看得见，结构有语义，命中区够大，对比度够，弹层关掉之后焦点能回到原处。动效得有理由——给反馈、表达状态、或者维持空间上的连续性；可以中断，并且给出 reduced-motion 下的等价体验。

<Aside type="note">
需要打分时才动用视觉质量量规，而分数不能替代上面这些硬门禁，也不能替代真实渲染。没有真实页面、浏览器渲染、截图或真机证据时，能声称的只有"静态契约通过"。
</Aside>

## 与其他 Skill 的关系

上游是 [product-manager](/skills/skills-reference/critical/product-manager/)（产品目标与验收）和 [brainstorm](/skills/skills-reference/medium/brainstorm/)（方案发散与收敛）。下游是 [ui-pc](/skills/skills-reference/high/ui-pc/) 与 [ui-app](/skills/skills-reference/high/ui-app/) 的生产实现，以及后续由 [frontend-polish](/skills/skills-reference/high/frontend-polish/) 接手的打磨。协作方是 [review-animations](/skills/skills-reference/low/review-animations/) 和 [animation-vocabulary](/skills/skills-reference/low/animation-vocabulary/)——一个只审现状，一个只给术语，都不承担设计决策。

```text
product-manager（产品目标与验收）· brainstorm（方案收敛）
        ↓
frontend-design（设计基线 / DesignContract + 可行性探针）
        ↓                                    ↘
ui-pc · ui-app（真实页面 + 真实接口）          tech-decision / architecture-design
        ↓                                     （回答探针挂起的技术问题）
frontend-polish（已有实现的打磨）
```

设计结论直接更新项目既有设计文档，并由 [product-manager](/skills/skills-reference/critical/product-manager/) 或 [project-manager](/skills/skills-reference/high/project-manager/) 压缩进那份唯一 TODO。本 Skill 不维护 TODO、不编辑生产代码、不碰 Git。

## 产出与验收

交给项目经理和实现方的是这几样：每个表面对应哪条需求、哪个功能；用户流；真实内容；每一种状态；权限怎么表达；出错之后怎么恢复；各端之间有哪些差异。再加上设计系统里哪些资产可以直接拿来用、哪些必须新增（新增的连原因一起写）。最后是技术负责人必须回答的可行性问题，连同探针状态、要什么证据、以及不成立时走哪条降级方向；以及实现完成后必须真实渲染出来的状态和主路径验收。

判断这一步真的完成了：随便挑一个动作，能顺着它答出"谁在什么入口触发、需要什么权限、成功和失败分别看到什么、失败之后怎么退回来"；随便挑一个表面，能答出"没数据、加载中、出错、无权限时它长什么样"。答不上来的地方，就是实现阶段会被临时决定的地方。

<Aside type="danger">
设计稿、文字规格、Penpot 文件、静态截图——这四样都不能算生产页面通过。真正的完成要由实现 Skill 照着基线做出来、接上真实后端，然后在目标尺寸或真机上把关键状态一个一个渲染出来看过。基线写得再完整，它证明的也只是"这份输入可以直接实施"。
</Aside>
