## 概述

"能用"和"能交付"之间差着一层：1366 的屏幕上表格横向溢出、暗色主题下这块字看不清、删除按钮点下去直接就删了、空态只有一句"暂无数据"、Tab 过去看不见焦点在哪。单拿出来每一条都不算大问题，凑在一起就是"这产品做得糙"。

`frontend-polish` 处理的就是这一层，而且不重做设计。它先把范围和不能动的东西定下来，再按影响从高到低诊断出带位置、现象、影响和最小修复的问题清单，分成 P0 到 P3，然后修根因——缺 token 就补到主题层，同一个东西被复制了三遍就收敛回共享组件，而不是在出问题的那一处贴补丁。最后在真实渲染下复验：桌面与窄屏、三个主题、长文本、控件的各个状态、键盘与触控。

它只改视觉和交互。业务行为、接口契约、依赖清单都不动；发现问题其实出在前后端契约上，它会停下来报告，不顺手改掉。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这页看着有点乱，帮我收拾一下" | 已实现页面的信息层级与视觉一致性 |
| "1366 的屏幕上表格显示不全" | 断点与溢出 |
| "暗色模式下这块字看不清" | 三主题适配与对比度 |
| "点删除直接就删了，加个确认" | 危险操作的交互反馈 |
| "上线前再过一遍" | 交付前的最后打磨 |
| "用户说找不到那个按钮" | 用户反馈的可用性问题 |
| "Tab 过去看不见焦点" | 键盘可达与无障碍 |

触发面覆盖已有页面的视觉、交互、布局、响应式和无障碍这一类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **这个页面还不存在** → [frontend-design](/skills/skills-reference/high/frontend-design/)。分界就是"现在渲染得出来吗"：它从零定页面结构、交互、状态和约束，产出的是实现输入；本 Skill 改的是已经渲染出来的东西。
- **页面还在实现中，要写组件、路由、状态** → [ui-pc](/skills/skills-reference/high/ui-pc/)（PC 与管理端）、[ui-app](/skills/skills-reference/high/ui-app/)（跨端）。
- **只要一份动效审查结论，不改代码** → [review-animations](/skills/skills-reference/low/review-animations/)。它只读，产出 findings。
- **要把"弹一下""飘进来"翻成准确的动效术语** → [animation-vocabulary](/skills/skills-reference/low/animation-vocabulary/)。它不写代码，也不做审查。
- **慢到要靠指标才能说清（p95、首屏几秒、慢查询）** → [performance-doctor](/skills/skills-reference/medium/performance-doctor/)。本 Skill 只处理页面上看得见的那部分：无界动画、未销毁的监听、没优化的资源、布局抖动。
- **需求要变、要加功能** → [product-manager](/skills/skills-reference/critical/product-manager/)。行为一变，验证范围和 Review 范围都不一样了。
- **后端接口** → [api-development](/skills/skills-reference/high/api-development/)；**业务逻辑实现** → [dev](/skills/skills-reference/high/dev/)。

## 前置条件

1. **目标页面已经实现**——有源码路径，或者有能访问的路由。没有可渲染的对象，诊断只能靠猜，改完也没法复验。
2. **问题具体到一类**：视觉、交互、响应式、性能还是无障碍。"优化一下"换来的只会是一份泛泛清单。范围不清时它会先提最多 4 个和实际发现绑定的问题——这次处理单页还是整条路径、保留现在的视觉语言还是允许调布局层级、先解决哪几条 P1、哪些文案组件依赖必须不变。
3. **这一轮不改业务逻辑、不加新功能。** 一旦行为要变，就不是精修了，得回到产品流程。

<Aside type="danger">
没有真实渲染、截图或真机证据时，它只会报告静态检查通过，**不会声称视觉质量或跨端体验已经验收**。静态扫描只提供线索，一个页面通过也不能扩大成全项目通过。
</Aside>

## 怎么用

**1. 定范围。** 具体路由或组件、这一轮的目标、不可改动的内容（业务逻辑、接口契约、已确认的文案和信息架构），以及验证方式：启动命令、访问地址、测试账号。

**2. 先看有没有现成结论。** 覆盖当前 diff 的 [code-review](/skills/skills-reference/high/code-review/) findings 还新鲜时，不重复整页审查，只补 UI 专项缺口；没有 findings 才做一次页面级审查，范围固定为你指定的路由、状态和 viewport。

**3. 按影响从高到低诊断。**

```text
① 主任务是否一眼可辨、信息层级、错误恢复、权限反馈、数据丢失风险
② 真实内容与控件各状态（默认 / 悬停 / focus-visible / 按下 / 禁用 / 加载 /
   空 / 错误 / 成功）、键盘与触控路径、无障碍、三主题、窄屏与缩放
③ token 是否散成了硬编码、排版角色是否稳定、色彩对比、图标与组件一致性
④ 动效有没有目的、能不能中断、reduced preferences 有没有等价体验、性能成本
⑤ 去 AI 指纹
```

每条 finding 写成同一个格式：位置 / 现象 / 影响 / 最小修复 / 验证方式。

**4. 分级，按级别处理。**

```text
P0  阻塞核心任务、状态误导、数据损失，或者没有可用的恢复路径
P1  发布前必修：明显错位与溢出、主题切换异常、断点问题、
    缺失的加载与错误态、WCAG AA 与权限反馈问题
P2  影响效率、理解、一致性与维护成本，但存在可行绕过
P3  不阻塞任务的视觉、文案、动效与代码清理细节
```

**5. 修根因，不贴补丁。** 同语义的颜色、间距、圆角、阴影出现多个值，是 token 层的问题；已经有共享组件却复制了按钮、弹层、表格、反馈或请求逻辑，是复用的问题；同类页面的导航、保存、披露方式或术语不一致，是页面流的问题。修复落在对应层级，用项目已有的组件库和命名，不引新依赖，也不在同一个项目里混用两套弹层——默认收敛到 Modal/Dialog，复杂详情走隐藏菜单的路由页。

**6. 删掉不该在那儿的东西。** 管理端和工作台里：菜单已经显示了、页面里还重复一遍的标题，"点击按钮进行操作"这类说明，"本页面用于管理用户信息"这类介绍，空洞的欢迎语和口号；以及没有语义的装饰——紫蓝渐变、玻璃拟态、无目的的悬停放大、连续装饰动画、卡片套卡片。要保留的例外是：独立全屏页、登录页和引导页的必要标题；会影响用户决策的限制说明和风险提示；不可逆操作前的明确警告；真实存在的使用成本与前提条件。

**7. 一次有界复验。** 核心用户路径与真实接口（在范围内时）、桌面与窄屏及项目实际支持的 viewport、三主题、长文本、空与错误与加载与成功与禁用与权限这几种状态、鼠标键盘触控与 reduced preferences，再加上受影响范围的现有类型与构建命令，以及控制台检查。这些合并成一次跑完；第二轮只确认 findings 关闭，最多确认一次。

<Aside type="caution">
默认不新增或修改测试源码、fixture、快照或 benchmark。只有你本轮明确要求写测试时才会动测试代码——覆盖率、仓库惯例和 CI 门禁都不构成授权。无法用 Review 和真实渲染证明的高风险交互，会被记成未验证边界。
</Aside>

## 与其他 Skill 的关系

上游是"页面从哪来"：[frontend-design](/skills/skills-reference/high/frontend-design/) 定基线，[ui-pc](/skills/skills-reference/high/ui-pc/) 和 [ui-app](/skills/skills-reference/high/ui-app/) 把它实现出来，之后才轮到这里。下游是两种复查：[review-animations](/skills/skills-reference/low/review-animations/) 做动效专项的只读审查，[code-review](/skills/skills-reference/high/code-review/) 对同一个 diff 做一次缺陷 Review。协作方向上，指标级性能交给 [performance-doctor](/skills/skills-reference/medium/performance-doctor/)，需要重新回到设计判断时回 `frontend-design`。

```text
frontend-design（页面结构 / 状态 / 约束基线）
      ↓
ui-pc · ui-app（把页面真的实现出来）
      ↓
frontend-polish（诊断 → 分级 → 修根因 → 真实渲染复验）
      ├─ animation-vocabulary（先把动效说清楚再改）
      └─ performance-doctor（问题要靠指标才能说清时）
      ↓
review-animations（动效专项）· code-review（一次回归 Review）
```

## 产出与验收

交付的是一份能对账的清单：这次的优化范围、按 P0 到 P3 列出的问题及修复情况、实际改动的文件、四类验证结果（功能、视觉、交互、性能）、未验证范围（需要后端、特定设备或真实用户数据的部分），以及建议后续处理的遗留项。

判断真的完成了：诊断阶段列出的 findings 逐条关闭或明确降级；三个主题和窄屏都真的看过；受影响范围的类型检查与构建跑过，控制台没有新错误；业务行为和接口契约没有被动过；剩下没验证的部分写进报告，而不是留白。

<Aside type="note">
删减类的修改（合并重复容器、去掉冗余文案和控件）要记下删减理由，并确认能力和权限入口没有跟着消失。删掉一个按钮很容易，删掉的同时让某个角色再也进不去那个功能，是这类修改最典型的事故。
</Aside>
