## 概述

`git-workflow` 管的是"提交之外"的那一半 Git：分支和 Tag 的增删移动、把一条分支并进另一条、rebase、冲突处理、stash、cherry-pick、revert，以及历史与差异查询。写提交信息、精确暂存、普通提交和功能分支推送不在这里——那是 [git-commit](/skills/skills-reference/high/git-commit/) 的职责。

它的默认姿态是：先看真实状态再动手，改写历史和影响远端的写入一律先拦住。理由很直接——本地一次失败的合并可以重来，远端一次覆盖会让别人的提交消失。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "把 feature 合到 develop" | 分支合并，含冲突处理和范围匹配的验证 |
| "从 main 开个新分支" | 起点、命名规则、未提交改动检查 |
| "冲突了，帮我看看" | 逐文件读双方意图，给最小合并结果 |
| "把我这条分支跟主干对齐" | rebase 或合并主干，并记录可恢复引用 |
| "手上的改动先放一放" | stash 的包含范围、恢复目标与潜在冲突 |
| "把那个提交挪过来" | cherry-pick：先看内容和依赖，确认不会重复应用 |
| "这一行是谁什么时候改的" | 历史与差异查询 |
| "这个改动要撤掉" | 已共享提交走 revert，未共享的先说明影响 |

触发面覆盖分支、Tag、合并、rebase、冲突、stash、cherry-pick 和 revert 这几类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **写提交信息、暂存、普通提交、功能分支推送** → [git-commit](/skills/skills-reference/high/git-commit/)。你说"合完顺手提交"时，本 Skill 先把合并与冲突处理做完，再把提交那一步交出去。
- **只想读源码，不想动 Git 状态** → [github-code-interpreter](/skills/skills-reference/low/github-code-interpreter/)。它是只读分析，不改工作树。
- **写代码** → [dev](/skills/skills-reference/high/dev/) 或对应领域 Skill。
- **产品定义** → [product-manager](/skills/skills-reference/critical/product-manager/)。

## 前置条件

两条门槛：

1. **你要处理的确实属于这一层**：分支与 Tag、把一条分支并进另一条、rebase、暂存工作区、挑单个提交、撤销改动或查历史。
2. **不是普通提交和推送。** 这条不是形式主义：提交信息规范、暂存范围和推送授权是 `git-commit` 的门禁，两件事混在一起做就会绕过它。

动手之前它一定先看状态、当前分支、上游和仓库规则，不假设分支名、remote 名或分支策略。已经有 TODO 时，它只把操作、冲突、验证和恢复条件交回唯一 owner，不自己回写状态。

## 破坏性操作会被真的拦住

这是本页最需要先看的一节。下面这些命令由 Runtime Hook 在工具调用层**直接拒绝**，不是"建议不要用"：

| 被拒绝的命令 | 拦截理由 |
| --- | --- |
| `git reset --hard` | 会丢弃工作区或提交状态 |
| `git clean` 同时带强制标志和 `-d` / `-x` / `--ignored` | 会批量删除未跟踪或被忽略的文件 |
| `git checkout .` / `git restore .`（以及 `*`、`:/` 形式） | 会批量丢弃当前工作区修改 |
| 推送时带 `--force` / `-f` / `--force-with-lease` / `--force-if-includes` | 强制覆盖远端 ref |
| 推送时带 `--delete`，或用空 source refspec | 删除远端 ref |
| 推送时带 `--mirror` / `--prune` | 镜像推送、远端 ref 剪枝 |
| 以 `+` 开头的 refspec | 强制更新远端 ref |

注意 `--force-with-lease` 也在名单里：lease 语义确实更安全，但它仍然是非 fast-forward 覆盖。被拒绝时正确的反应是把命令和后果讲清楚、让你自己在终端里执行，**不是换一种写法绕过去**——用 `sh -c` 之类再包一层同样会被解析出来。

<Aside type="danger">
提交信息里的 AI 协作者署名是另一条独立硬拦截：`Co-Authored-By: Claude`、任何指向 Anthropic / OpenAI / AI 的协作者行、`Generated by Claude/Codex/AI`、`<noreply@anthropic.com>`，只要出现一个，提交动作就被直接拒绝。这条由 Hook 强制执行，不是风格建议。
</Aside>

删除本地分支不在 Hook 名单里，但本 Skill 自己的规则要求：删之前确认已经合并，或者你明确接受丢失风险。删远端分支或 Tag 属于远端写入，本地删除的授权顶替不了它。

### 确实需要时：一次性精确授权

Hook 拒绝之后仍然必须做时，门禁要求先用只读命令解析并摆出这些事实：规范化后的绝对 Git 根；remote 名及其目标 URL 或仓库身份；精确的 source ref 与 destination ref；远端当前的 `oldOID`；计划写入的 `newOID`（删除时明确写成 delete）；为什么是非 fast-forward 或删除；会影响哪些协作者和发布；怎么恢复。

授权必须同时覆盖仓库根 + remote + 目标 ref + `oldOID` + `newOID`（或 delete）。"可以强推""你处理一下远端"，以及之前给过的逐功能推送授权，都不够。

执行前还要立刻重读目标 ref 的远端 OID：和授权时的 `oldOID` 不一致，授权自动失效并重新确认；remote、ref、源提交或命令范围变了，同样失效；一次执行完成或失败，授权即被消费，不能拿去用在下一个 ref 或重试后的新状态上。获准做非 fast-forward 更新时优先用绑定精确 ref 与 `oldOID` 的 lease 语义，不退化成无条件强推；获准删除时只删已确认的那一个完整 ref，不用通配、批量前缀或镜像删除。

## 怎么用

### 只读检查先跑

```bash
git status --short --branch
git branch --show-current
git remote -v
git log --oneline -10
```

查历史和差异：

```bash
git log --follow -- path/to/file
git show <commit>
git diff <base>...<target>
```

### 分支与 Tag

新建之前确认起点和命名规则，切走之前检查未提交改动。首选 `git switch`，但服从仓库现有的工具和版本。

Tag 要多留一步：新建或移动之前确认目标 OID、annotated 还是 lightweight、以及签名规则。推一个新 Tag 算单个 ref 的独立写入，要用精确的 `refs/tags/<tag>:refs/tags/<tag>` 并回读远端 OID，普通功能分支的推送授权不覆盖它。把一个远端已有的 Tag 指到别处，性质上就是覆盖，得重新走一次性精确授权。

### 分支合并

先确认目标和来源，`fetch` 之后看提交图和差异——不使用会隐式选择合并或 rebase 策略的裸 `git pull`。需要产生新提交时优先用 `--no-commit` 把结果收敛下来，再交给 `git-commit` 复核并落提交；仓库明确要求保留 merge commit 时，把这条策略记下来。遇到冲突就逐文件理解双方意图，不机械选一侧，然后跑与冲突范围匹配的验证。

### rebase

只在你明确要求，或仓库规范规定时才做；分支已经推出去、别人可能基于它工作时，默认不动它的历史。这个操作会把提交重新建一遍，所以动手前先把原 HEAD、upstream 和可用于回到原点的引用记下来，结束后核对提交顺序、内容和工作区状态。之后如果还要强制推送，那一步仍然单独走上面那道授权门禁。

### 暂存工作区与挑单个提交

stash 之前说清这次装进去的是哪些改动，取回来之前先看目标分支和可能的冲突；stash 列表不会被自动清空。

cherry-pick 之前先看那个提交改了什么、依赖什么，并确认它没有被应用过。默认用 `--no-commit` 落到工作区，冲突处理、Review 和验证之后再交给 `git-commit`。只有当你或仓库规则要求保留每个原提交各自的边界和信息时，才用会直接建提交的形式，并逐个核对真实 OID 与内容。

### 冲突处理

列出冲突文件 → 读完整上下文和相邻调用链 → 识别双方真实意图 → 用最小结果收敛 → 检查残留标记 → 跑验证并说明还剩哪些风险。

<Aside type="caution">
各种 `--abort`（`merge`、`rebase`、`cherry-pick`、`revert`）都会把你在冲突里已经做完的那部分一起丢掉。所以它会先摆出当前处在哪个操作中、具体哪些文件会被丢弃，再等你授权。做不完又没拿到 abort 授权时，它保留真实的 in-progress 状态和恢复命令，不把工作树伪装成干净的。
</Aside>

### 回滚

别人已经拿到的提交，优先用 `git revert --no-commit`：先核对反向变更、冲突和受影响的调用链，再交给 `git-commit` 落一个新提交。还没推出去的提交要改写时，先讲清影响面。把本地改动直接扔掉是破坏性动作，得先列出具体文件再取得授权。

有一种情况特别容易混：把已经推送的历史"退回去"，实际上就是在覆盖远端 ref。普通的回滚授权只够创建一个新的 revert 提交，不包含这一种。

## 与其他 Skill 的关系

**上游（before）**：没有硬性前置。

**下游（after）**：[git-commit](/skills/skills-reference/high/git-commit/)——提交信息、精确暂存、普通提交与功能分支推送。

```text
git-workflow（状态 → 分支/Tag、分支合并、rebase、stash、cherry-pick、冲突处理 → 验证）
  → git-commit（提交信息、暂存、普通提交、功能分支推送）

远端覆盖或删除：
  git-workflow 摆出 repoRoot / remote / ref / oldOID / newOID
    → 你逐项授权 → 执行前回读远端 OID → 一次执行即消费授权
```

## 产出与验收

每次操作它汇报五件事：执行了哪些 Git 操作；操作前后的分支和状态；冲突文件及各自的解决方式；验证结果；是否需要交给 `git-commit`。涉及远端覆盖或删除时，额外给出获授权的仓库根 / remote / ref / `oldOID` / `newOID`、执行前的 OID 复核结果、一次性授权的消费情况，以及远端最终 OID。

判断真的完成了：工作树状态是真实的（还在 in-progress 就说 in-progress）；每个冲突文件都有解决说明，而不是一句"已解决"；验证是跑过的，不是"应该没问题"；需要提交的部分已经明确移交出去。
