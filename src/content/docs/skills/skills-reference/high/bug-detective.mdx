## 概述

故障排查最常见的失败模式不是找不到原因，而是太早找到一个"看起来对"的原因：看到 500 就说是空指针，看到空列表就说是权限过滤掉了。状态码、异常名和经验模式只够生成假设，撑不起结论。

`bug-detective` 的顺序是反过来的：先证明"在哪个环境、什么时间、什么输入下发生了什么"，再解释为什么。它默认只读——你说"查一下"，它不会顺手改代码、装依赖、重启服务或写数据库。结论也拆成三段给你：事实、推断、未知项，并附一个置信度。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这个接口一直 500" | 有明确状态码和入口，需要沿真实调用链取证 |
| "点了保存没反应" | 前端可感知异常，先固定现象和最小复现路径 |
| "昨天还好的，今天就不行" | 需要版本、部署和时间窗对照 |
| "日志里一堆异常，看不出哪来的" | 按请求 ID 或时间窗把日志、堆栈和追踪对齐 |
| "本地能跑，CI 里退出码非零" | 命令、Hook、子进程与跨平台执行链的失败层级定位 |
| "库里明明有这条数据，接口查不出来" | 对比应用实际执行的查询与数据库原始事实 |
| "这个字段传上去就丢了" | 契约偏差：封装、序列化、精度、对象转换 |

触发面覆盖崩溃、结果不对、退出码非零和数据不一致这几类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **你要的是修复，不是结论** → [universal-development](/skills/skills-reference/low/universal-development/) 或对应领域 Skill。诊断成立之后才谈实现，它自己不改代码。
- **功能是对的，只是慢** → [performance-doctor](/skills/skills-reference/medium/performance-doctor/)。两者要的证据不同：一个看逻辑走到哪条分支，一个看指标分布。
- **要落地异常契约、错误码、日志** → [error-handler](/skills/skills-reference/medium/error-handler/)。它定位原因，error-handler 实现错误响应。
- **预防性地过一遍改动** → [code-review](/skills/skills-reference/high/code-review/)。一个查已经发生的故障，一个查还没发生的缺陷。
- **其实是需求变了** → [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。这条最容易走错：Issue 上标着 bug，读下来发现是新规则或验收变化。这时它会停止诊断，交回产品变更流程。
- **架构取舍或产品定义** → [architecture-design](/skills/skills-reference/high/architecture-design/)、[product-manager](/skills/skills-reference/critical/product-manager/)。

## 前置条件

三条门槛：

1. **有明确的现象和复现路径**。"偶尔有点问题"既证伪不了任何假设，也验证不了修复。
2. **日志、源码或运行环境至少能碰到一个**。三样都拿不到时，它只能给取证计划，不能给根因。
3. **确认这是故障，不是新需求**。判断错了就会把"从来没实现过"当成"实现坏了"，之后收集的证据全是无效的。

信息不全时它先从仓库和运行证据补齐，只问真正卡住的那一个问题。

<Aside type="danger">
只读是默认档。新增日志、改配置、执行写操作、调用有副作用的接口，都已经越过只读诊断，需要单独授权。数据库只在任务范围和权限明确时只读访问；没有授权或安全连接方式时它停止直连，改为给出脱敏查询建议，由你在受控环境执行。

证据引用一律脱敏：密钥、Token、Cookie、连接串、密码和完整敏感记录都不会原样出现在输出里，也不会从配置里复制凭据打印出来或嵌进命令。
</Aside>

## 怎么用

描述现象就够了，不需要先替它下结论。诊断分六步，顺序不能跳：

1. **固定现象与范围**。记下期望、实际、环境与版本、时间窗口、输入、身份或租户上下文、可见的状态码或退出码，以及最小复现步骤。命令类问题额外要分清交互 Shell 和真正的执行器，并固定配置来源、真实命令、工作目录和运行时路径。
2. **复现，或转入取证模式**。优先做最小、可重复、无副作用的复现。不能安全复现时不假装成功，改用同时间窗的日志、追踪、监控、已有测试结果和版本差异，并在结论里写明"未现场复现"。一次只改一个变量。
3. **建立时间线与调用链**。从外部入口往里核对实际路径，以源码、运行配置和日志中真实存在的组件为准，不套固定分层模板。
4. **提出并证伪假设**。每个假设都要写支持证据、冲突证据和下一项最小检查，优先做能区分多个假设的那一项。单条 ERROR、一次空查询或一个状态码都不足以宣告根因。
5. **必要时只读核对数据**。先从迁移、实体、查询构造和实际 SQL 确认表与过滤语义，再用受限条件、少量字段、有限行数去查，比对"应用真正执行的查询"和"库里的原始事实"，不绕过授权、租户和安全边界。
6. **给出证据化结论**。根因或最可能原因、置信度（高/中/低）、影响范围、已排除项、仍需验证项，分别写清楚。可以提修复方向，但只读模式下明确标注"未实施"。

取证层级也是固定的，从直接到间接：原始输入与实际输出 → 同一请求或时间窗的日志与分布式追踪 → 当前部署版本对应的源码与运行配置 → 外部依赖响应、队列/缓存状态、只读数据库事实 → 文档与历史 issue。靠后的层级只能用来提假设，不能推翻更直接的运行证据。

<Aside type="caution">
几条"只能定位到这一层"的硬边界：只有非零退出码而拿不到实际命令、stderr、超时/信号或执行器证据时，它只说清失败发生在哪一层，不把路径、Shell 或脚本逻辑写成确定根因；日志和源码版本对不上时，先确认部署版本或构建产物再归因。
</Aside>

按主题它会拉不同的取证清单：命令、Hook、子进程、计划任务、跨平台执行和非零退出码走命令诊断那份；日志、堆栈、请求 ID、链路追踪和慢请求走日志与追踪那份；数据存在性、SQL、租户、逻辑删除和执行计划走只读数据库那份；封装重载、大整数精度、租户过滤、逻辑删除和对象转换丢字段走契约陷阱那份。最后这份值得单独记住——这几类问题都能编译通过、日志干净，现象却只表现为"数据莫名不对"。

## 与其他 Skill 的关系

**上游（before）**：没有硬性前置。现象描述本身就是入口。

**下游（after）**：[universal-development](/skills/skills-reference/low/universal-development/)（实施修复）、[code-review](/skills/skills-reference/high/code-review/)（改完过一次）

**协作（complement）**：[performance-doctor](/skills/skills-reference/medium/performance-doctor/)、[error-handler](/skills/skills-reference/medium/error-handler/)

```text
现象（异常 / 结果不对 / 退出码非零 / 数据不一致）
  → bug-detective（固定现象 → 复现或取证 → 调用链 → 证伪 → 只读核对 → 结论）
      ├─ performance-doctor（"不是错，是慢"）
      └─ error-handler（错误契约与日志要一起改）
            → universal-development / 领域 Skill（实施修复）
                  → code-review（一次回归 Review）
```

一条实际会走到的路线：从 Gitea 或 GitHub 的 Issue 进来时，Issue 编号、标签、正文和评论都只算现象线索，仍然要回到目标版本的源码、日志、测试或受限数据去证明原因。

## 产出与验收

交付格式是固定的四段：

- **诊断结论**：现象与复现、根因或候选原因、置信度。
- **关键证据**：每条标明来源与时间，并写清它支持了什么或排除了什么。
- **已排除与未知项**：两类分开列。
- **建议**：修复方向、验证方式，以及本次变更是"无（只读诊断）"还是已获授权的变更摘要。

判断真的完成了：能把"什么输入在什么环境、什么时间产生了什么结果""哪条证据排除了哪个假设""根因证据是什么""置信度为什么是这一档""还差哪一项证据"这五件事连起来讲完。凡是用"应该、一般、常见"填空的地方，就是还没查完的地方；没有复现或同时间窗证据时，结论只能写成候选原因，不能升级成确定根因。

<Aside type="note">
它不创建或更新 TODO、不改功能状态、不操作 Git。当前请求已经有 TODO 时，它只把诊断证据、结论和风险交回给 owner，不开平行任务。顺带发现性能、安全、架构或数据修复问题时同样只完成定位，后续分别交给对应 Skill。
</Aside>
