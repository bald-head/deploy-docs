## 概述

需求送到你手上时，通常已经被包装成了一个功能名："加个批量导出""做个仪表盘""再来个审批流"。`product-discovery` 做的第一件事就是把包装拆开：谁、在什么时候、卡在哪儿、卡住之后损失了什么、现在拿什么顶着。功能名在这里降级成候选解法之一，不再是研究对象。

拆完之后它做三件事：把手上的材料分成"看见的行为""用户说的话""我们猜的"，各自标出来源和覆盖范围；挑一个真正缺的入口往下走（做访谈、建机会树、识别风险、设计实验、给一堆反馈排序）；最后交出一份能让下一个人接着干的结论。

它的结论只停在"值得做 / 先验证 / 证据不够"这一层。把结论升级成完整的产品定义和验收，是 [product-manager](/skills/skills-reference/critical/product-manager/) 的事；写成 PRD、OKR、路线图是 [product-execution](/skills/skills-reference/high/product-execution/) 的事。三个 `product-*` Skill 都能被单独叫起来，但整条产品流程的编排入口一直是 `product-manager`。

<Aside type="caution">
它对"什么算证据"卡得很紧：搜索结果摘要、竞品官网文案、模型自己的推理，都不算用户证据。访谈了 5 个人也不能写成"市场普遍需要"。没有数据时它不会给你一个好看的 RICE 分数——那一栏会写"缺什么才能算"。
</Aside>

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "这个功能到底有没有人真的要" | 把功能请求还原成机会，再看证据够不够 |
| "帮我做一轮用户研究" | 访谈准备、原话整理、痛点与现有替代方案 |
| "先做个市场调研" | 收集外部材料，并且把事实和推断分开摆 |
| "帮我把这个目标拆成机会树" | 一个目标 → 多个机会 → 多个解法 → 各自的实验 |
| "这几十条反馈先做哪个" | 分诊排序，并记下哪些被淘汰、为什么 |
| "用最小成本怎么验证这个假设" | 实验设计，优先看真实行为而不是问卷态度 |
| "这个方向风险在哪" | 价值、能不能用、做不做得出来、生意能不能持续 |
| "帮我写个访谈提纲" | 不带诱导的问法，问最近一次真实经历 |

## 什么时候不要用

- **要什么已经很清楚，只差人动手** → 先让 [product-manager](/skills/skills-reference/critical/product-manager/) 把定义收口，再交给 [dev](/skills/skills-reference/high/dev/) 或 [universal-development](/skills/skills-reference/low/universal-development/) 实现。
- **要一份完整的 PRD、OKR、路线图或 Backlog** → [product-execution](/skills/skills-reference/high/product-execution/)。发现结论是它的原料，不是它的替代品。
- **卡住的是市场、竞争、商业模式、定价** → [product-strategy](/skills/skills-reference/high/product-strategy/)。这里提供用户侧的证据，市场层的取舍在那边做。
- **要定客户画像、渠道、发布与增长动作** → [go-to-market](/skills/skills-reference/low/go-to-market/)。验证在前，怎么卖在后。
- **要算样本量、跑显著性、解读实验数据、写指标口径和 SQL** → [product-analytics](/skills/skills-reference/medium/product-analytics/)。这里负责把实验设计出来，统计推断不在这里做。
- **连有哪些可能的做法都还没想过** → 先用 [brainstorm](/skills/skills-reference/medium/brainstorm/) 铺开，但它给的仍然只是候选，得回到这里用证据筛。
- **要真的原型和可用性证据** → [frontend-design](/skills/skills-reference/high/frontend-design/)；**要比技术方案、做技术 Spike** → [tech-decision](/skills/skills-reference/high/tech-decision/)。
- **项目已经批了，要开始约人、跑真实流量、上原型、安排回滚** → [project-manager](/skills/skills-reference/high/project-manager/) 接手，再由 [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 管任务、验证与提交节奏。

## 使用示例

### 场景 1：一个功能请求被拆回问题

**你的输入**：

```text
运营一直催着要"批量导出订单"，做不做？
```

**你会拿到的产出**：

```text
## 先把请求还原
请求的是   一个批量导出按钮
真实场景   每月 1-3 号对账，把上月订单核进财务的模板
期望结果   财务那边能一次收全，不用来回补数
现在怎么办 在列表里逐条复制，一次 200 多条，约 40 分钟，容易错行
错了之后   财务退回重核，平均多花半天

## 手上的证据分三类
| 类型 | 内容 | 来源 | 覆盖/缺口 |
| 看见的行为 | 上月 1-3 号列表页翻页次数是平时的 6 倍 | 埋点 | 只有一个月 |
| 用户说的话 | "每次都要复制到手抽筋" | 运营群 3 条消息 | 都来自同一个人 |
| 我们猜的 | 财务模板字段固定 | 提出人：小李 | 需要看一次真实模板 |

## 候选解法（导出只是其中一个）
A 批量导出        改动小，但字段对不上仍要手工调
B 对账视图        直接按财务模板出数，改动中等
C 财务系统直连    一次解决，依赖对方排期

## 现在最该验证的
假设：财务模板的字段在最近 6 个月里没变过。
成立 → B 的价值远高于 A；不成立 → 先做 A，别急着做视图。
验证方式：要三份不同月份的真实模板，比字段。半天能出结论。

## 还不知道的
只有一个人在提这件事。其他 4 个运营是不是也这样对账，没问过。
```

它没有回答"做不做"，而是把这个决定需要的两个事实指出来了——这是这个 Skill 正常的产出形态。

### 场景 2：没有任何数据，它只给研究计划

**你的输入**：

```text
我想验证"中小商家愿意为自动对账付费"，但我们没有用户、没有埋点。
```

**你会拿到的产出**：

```text
## 这一轮只能交研究计划
原因：没有可读的行为数据、没有可联系的用户、没有历史成交记录。
在这种情况下给出的任何转化率、付费意愿百分比都是编的。

## 这次研究要支持哪个决策
"下个季度要不要投 2 人做对账模块"——只回答这一个问题。
明确不研究：定价区间、竞品功能矩阵、渠道选择。

## 访谈提纲（12 个人，两类各 6）
问最近一次，不问会不会买：
1. 上个月对账是哪天做的？从打开什么开始？
2. 这件事花了多久？中间有没有返工？
3. 上一次出错是什么情况？后来怎么处理的？
4. 现在有没有为这件事付过钱（人力、外包、软件都算）？
禁止出现的问法："如果有一个能自动对账的工具，你会用吗？"

## 找人渠道与授权状态
渠道：现有客服工单里提到对账的联系人
状态：未获授权联系 —— 需要谁批、按什么话术邀约，请先确认

## 什么信号算"愿意付费"
不算：说"挺有用的""可以考虑"
算：  报出现在为此花的钱 / 愿意先付定金 / 主动问什么时候能用

## 明确留空的
Persona 的年龄、职级、公司规模区间——没有依据，不填。
```

<Aside type="danger">
凡是要碰到真人和真数据的动作——约访、录音、收集个人信息、查生产库、对真实用户上 Fake Door 或价格测试——它默认只输出方案，等你确认授权、知情同意、数据留存与删除、退款与回滚责任之后才动。缺任何一项，它停在计划。
</Aside>

### 场景 3：一堆反馈要排序，它会先选打分方式

**你的输入**：

```text
这是最近攒的 37 条用户反馈，帮我排个优先级，用 RICE。
```

**你会拿到的回应**：

```text
## 先说打分方式为什么要换
RICE 需要四个数：覆盖多少人、影响多大、多有信心、多少工作量。
这 37 条里能拿到"覆盖多少人"的只有 6 条（有埋点或工单量）。
剩下 31 条硬凑 RICE，结果是四个编出来的数相乘——精确的假象。

## 这次的处理
6 条有量的     走 RICE，附上每个数的来源和量表定义
19 条有方向没量 走影响 × 成本的粗排，并标"不确定"
8 条           归到 3 个主题，先合并再决定要不要单独看
4 条           影响低成本高，直接淘汰，并记下淘汰理由

## 合并出来的三个主题
主题 1  对账相关（11 条）—— 这才是真正要研究的机会
主题 2  导出格式（7 条）  —— 疑似主题 1 的表象
主题 3  权限太粗（5 条）  —— 与当前季度目标不一致，记录后延后

## 两条分数很接近的
主题 1 与主题 2 的粗排分只差不到一档。
不假装这个差距代表真实优先级——它们更可能是同一个问题，
先花半天确认主题 2 是不是主题 1 的表象，再决定排序。
```

<Aside type="tip">
"影响低、成本高"的项直接淘汰并写下理由，比排到队尾更诚实。排到队尾的东西一年后还在队尾，但每次评审都要重新讨论一遍。
</Aside>

### 场景 4：一张写满了的实验卡

**你的输入**：

```text
想用 Fake Door 试试对账功能有没有人点。
```

**你会拿到的产出**：

```text
假设      在月初对账那几天，运营看到入口会点进来了解
方法      在订单列表加一个入口，点开是"即将上线 + 留邮箱"
对象      上月有过 100 条以上订单的账号（约 210 个），排除内部账号
主指标    入口曝光到留邮箱的转化
护栏      投诉或误解为已上线的反馈 ≥ 3 条即撤
成功阈值  待校准 —— 我们没有同类入口的历史转化可参照，
          先跑 7 天拿到基线，再定这个数
授权      需要产品负责人确认：向真实用户展示未上线功能的披露文案
数据      只收邮箱，明确保留期与删除方式，不与订单数据关联落库
运行责任  谁上线、谁盯数、谁能一键撤
停止条件  达到护栏 / 满 14 天 / 出现误解投诉
过了怎么办 进入机会树，作为主题 1 的解法之一继续设计
没过怎么办 不等于没需求 —— 先查是入口没被看见，还是问题不够痛
```

阈值那一行写"待校准"而不是随手填个 5%，是刻意的。填一个没有依据的百分比，实验结束后就没人能说清算不算成功。

## 与其他 Skill 的关系

**编排它的**：[product-manager](/skills/skills-reference/critical/product-manager/) 在跑完整产品流程时会调它来补研究证据。

**先它一步**：[brainstorm](/skills/skills-reference/medium/brainstorm/) 铺开候选做法，[grilling](/skills/skills-reference/medium/grilling/) 在"到底要研究什么、支持哪个决策"都说不清时先问明白。

**平行的专项**：市场与商业模式看 [product-strategy](/skills/skills-reference/high/product-strategy/)，文档与排期看 [product-execution](/skills/skills-reference/high/product-execution/)，统计与指标口径看 [product-analytics](/skills/skills-reference/medium/product-analytics/)，客户画像与渠道看 [go-to-market](/skills/skills-reference/low/go-to-market/)。

**协作**：[frontend-design](/skills/skills-reference/high/frontend-design/) 出真实的原型与可用性证据，[tech-decision](/skills/skills-reference/high/tech-decision/) 冻结技术方案。

**接手它的**：[project-manager](/skills/skills-reference/high/project-manager/) 承接批准后的真实交付，[task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 维护 TODO 与验证节奏。

```text
   brainstorm / grilling
            ↓
   product-discovery ── 证据 → 机会 → 假设 → 实验
            ↓                    ↘
   product-manager（收口批准）    product-strategy / product-analytics
            ↓                    product-execution（要 PRD 时）
   project-manager → task-todo-workflow
```

## 常见坑

**把"用户说想要"当成需求。** 用户说的话是一类证据，但它记录的是意愿，不是行为。它会把这两类分开摆，就是为了让你不要把第二栏当第一栏用。

**样本太小就写结论。** 访谈 5 个人得到的是 5 个人的情况。想说"普遍"，先说清这 5 个人代表谁、漏掉了谁。

**用竞品文案当用户证据。** 竞品页面上写的是竞品想让你相信的事，不是客户真实遇到的事。同理，模型的推测也不能进证据表。

**Persona 的空格用想象补齐。** 年龄、收入、爱好补上去之后，整张卡看起来专业了，但后续所有推理都建在这几个编出来的数上。

**为了得到漂亮分数选打分框架。** 正确顺序是先看手上有什么证据，再决定用哪种排序方式。反过来做，分数就只是一次自我说服。

**逼着人走完整套流程。** 你只问了一个局部问题，它就该只回答那一个。如果发现自己被要求先做完六个入口才能得到一句话，那是用错了。

**把研究结论当成批准。** 研究说值得做，不等于立项、不等于技术可行、不等于可以发布。这几件事各有各的责任人。

## 最佳实践

- **每次研究只挂一个决策。** 开头写清"这次要支持哪个决定"，以及"这次明确不研究什么"。没有这两行，研究会变成永远收集不完的资料。
- **访谈问最近一次，别问以后。** "上个月你是怎么做的"能拿到行为，"你会不会用"只能拿到客气话。
- **让每个数字带上出处。** 有来源写来源，没来源写"待校准"或直接留空，别用一个百分比占位。
- **把没覆盖到的人写出来。** 哪几类用户没访到、哪种场景没看到，这一栏往往比结论本身更能防止后面翻车。
- **拿到输出先自查两句。** 下一步要验证什么、谁在什么授权下验证；还有哪些群体和偏差没覆盖。这两句答不上来，这份发现就还没做完。
