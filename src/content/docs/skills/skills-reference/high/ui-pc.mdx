## 概述

`ui-pc` 干的是"把已经定下来的设计和契约落成真实页面"这件事。它的起点从来不是空白画布：仓库里已经有一套组件库、路由约定、请求层、认证链和设计令牌，新页面必须长在这套东西上，而不是在旁边再造一套。所以它做的第一件事永远是查——依赖里装的到底是哪个组件库、路由从哪来、相邻的生产页面怎么写、真实的 props 和事件名叫什么。

它对"完成"的判断线比通常想象的高。接口能返回数据、字段能在页面上显示，只是起点；权限、加载与空与错与成功、宽屏到窄窗口的自适应、键盘与焦点、并发下旧响应会不会盖掉新状态，都算在同一个功能里，缺一样就不算交付完。

它不定设计基线，不写后端接口，不维护任务状态，也不碰 Git。它把改了哪些文件、跑了哪些验证、还有哪些边界没验证，交回给功能 owner。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做个用户列表页" | 查询、分页、表格、批量操作的后台列表 |
| "加个订单详情页" | 详情用什么承载，以及怎么实现 |
| "做个数据看板" | 指标层级、时间范围、异常与下钻 |
| "审批流那几个页面要改" | 流程系统页面：阶段、状态、责任人、待办 |
| "菜单里加一项，进去是个新页" | 顶级业务入口对应真实路由视图 |
| "这个字段要加到表格和编辑弹窗里" | 已有交付面上的增量实现 |

触发面覆盖 PC 与管理端界面、Web 页面、桌面端这几类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **移动端、H5、小程序** → [ui-app](/skills/skills-reference/high/ui-app/)。平台事实完全不同——安全区、键盘顶起、条件编译、真机权限——把这边的结构和验证方式搬过去会整块返工。
- **还没有设计结论** → [frontend-design](/skills/skills-reference/high/frontend-design/)。它输出可实施的设计基线；本 Skill 消费基线，不替你做设计决定。
- **已有页面的打磨、精修、只读审查** → [frontend-polish](/skills/skills-reference/high/frontend-polish/)。分开是为了避免两个 Skill 对同一个页面各审一遍。
- **跨组件共享状态、Store、本地持久化** → [store-pc](/skills/skills-reference/medium/store-pc/)。本 Skill 负责界面和页面局部状态；持久化的版本、迁移、登出清理归它。
- **后端接口本身** → [api-development](/skills/skills-reference/high/api-development/)。
- **页面业务流程的真实浏览器回归** → [real-browser-automation](/skills/skills-reference/medium/real-browser-automation/)。本 Skill 实现页面，它跑流程。
- **原型、品牌取值、艺术 sketch** → [penpot-prototype](/skills/skills-reference/low/penpot-prototype/)、[brand-guidelines](/skills/skills-reference/low/brand-guidelines/)、[algorithmic-art](/skills/skills-reference/low/algorithmic-art/)。三者的产出都不是生产页面。
- **没有专业 Skill 覆盖的零碎改动** → [universal-development](/skills/skills-reference/low/universal-development/)。反过来不成立：业务页面不走兜底。

## 前置条件

三条门槛，都是为了让"页面长在真实事实上"这件事成立。

1. **UI/UX 结论已经在手，或者明确复用现有设计系统。** 它不做设计发散。缺这一步，页面结构会退化成一套通用模板——而结构本该由系统性质、用户角色、信息密度和主要输入方式决定：管理端与运营场景优先扫描、查询、比较和批量；驾驶舱优先指标层级、时间范围、异常和下钻；流程系统优先阶段、状态、责任人和待办；编辑器类优先工作区和即时反馈。
2. **框架和组件库已经从仓库事实确认下来。** 依赖、组件定义、相邻生产调用三处对齐才算确认。从组件名猜 API 是最贵的错误；而为了一个页面混装第二套组件体系之后，主题和交互就再也统一不回来。没有既定 UI 基线、或者确实要换框架，选型属于规划阶段的 [tech-decision](/skills/skills-reference/high/tech-decision/)，不在写页面时临时决定。
3. **后端契约已经明确，或者同步在做。** 字段名、枚举、分页、排序、null 与默认值、单位、时区、错误语义都得来自真实后端或既有调用。从表格列名反推 API 字段做出来的页面，联调时基本要重写一遍。

<Aside type="danger">
没有目标仓库、跑不起来、或者手上只有一份静态页面时，它只给静态契约和最小示例，**不会声称页面已经跑通或视觉已经通过**。同样，mock、fixture、静态页面和孤立的前端构建都不能用来关闭一个 `featureId`。
</Aside>

## 怎么用

### 1. Preflight：先把项目找准

用 `rg --files` 定位构建文件、锁文件、TypeScript 配置、入口、路由、全局样式、令牌和可用脚本——不要假设它们都在 `src/` 下。再从依赖和入口确认框架与版本、渲染模式、目标浏览器、CSS 方案、组件库、图标、国际化、状态管理和请求层。然后搜出布局、表格、表单、Dialog、空态、错误态、Loading、权限和 motion 令牌的既有实现，以及至少一个相邻的生产用例，核对真实导入、props、事件、slot 和命名。

只有当缺失的信息会实质改变结构、公共行为、安全、数据或成本时才停下来问；普通实现细节照相邻生产代码办。

### 2. 把契约和状态定死，再动手

固定字段集合用具名类型，不用 `Record<string, unknown>` 或页面内临时键值约定糊过去。超出 JavaScript 安全整数范围的 ID 按契约走字符串；金额、比例、容量和时间保住单位与精度，不在展示层悄悄改业务含义。

状态矩阵按适用范围建齐：default、hover、`focus-visible`、pressed 与 dragging、disabled、pending 与 loading、empty、error、success 与 undo。每个状态都要有能操作的反馈、恢复路径和稳定布局；判定为不适用的，得有任务或平台上的理由。

<Aside type="caution">
两条最容易被跳过的边界。

**权限**：前端路由、按钮、指令和 Store 里的权限只负责界面体验，服务端仍要校验每一次读写。按钮看不见不等于可以继续请求、预取或缓存未授权数据；租户、Token、角色一律复用项目认证链。

**并发**：筛选、分页和联想请求必须用项目既有的取消、请求序号或查询库机制，旧响应不能盖掉新状态。提交、删除和批量操作要防重复触发；乐观更新必须有回滚或重新拉取的路径。
</Aside>

### 3. 落到工程结构里

布局壳负责导航、面包屑、页签容器和全局加载，业务页面不再重复实现一遍。菜单、面包屑或布局标题已经说明页面用途时，内容区不要再写一遍页面标题、用途副标题和显而易见的操作说明——直接进入当前任务、状态、操作和数据。只有限制、风险、不可逆影响或复杂的空态错态需要解释时，才在对应操作旁边放一句简短提示。

多个业务模块不要堆进一个巨型页面文件。可复用的表格、筛选器、图表、弹窗和状态块进模块组件，页面文件只编排数据、布局和主要动作；API client、契约类型、Store、格式化工具和 storage 留在项目既有边界里，页面内不复制请求封装、Token、租户或原生 storage 调用。请求层确认是 alova 时按 [alova-client-usage](/skills/skills-reference/low/alova-client-usage/) 接入，页面只消费具名契约和已有的 Method 与 Hook。

<Aside type="note">
遇到"某个类型、格式化或业务口径会被两个以上页面、系统层或功能复用，但项目记忆里没记过它的 Owner 和复用边界"这种情况，正确做法是把后端 DTO、真实响应和既有实现交给 [project-details](/skills/skills-reference/high/project-details/)，由它原位补进 `PROJECT-MEMORY.md`。不要用页面里的 `Number(...)`、临时枚举字典、重复组件或一行注释把缺口掩过去。
</Aside>

### 4. 图表按既有栈实施

仓库已经有图表封装时沿用它，连主题、resize、tooltip、空态、导出和数据转换约定一起沿用。没有既有栈时，比较具名候选、绑定版本与入口与验证与退出路径，是 `tech-decision` 在规划阶段的事，本 Skill 不在写页面时临时选库。图表自身必须封装指标口径、单位、tooltip、legend、加载与空与错、resize、销毁和主题适配；复杂聚合、阈值、时间窗口和联动逻辑要注释原因与边界。地图、3D、大量点和大屏动效先确认性能、降级和浏览器边界——装饰不能盖掉指标口径、更新时间、下钻和导出。

### 5. 验证

跑目标仓库里受影响范围的现有 formatter、类型检查、编译或构建命令。项目已启用国际化时，全部启用语言的固定文案键和插值参数要一起核对，运行时切换沿用既有加载链——只认出了 i18n 工具却留着硬编码文案，不算完成。

能启动的话，把目标尺寸、窄窗口、主题、缩放、长文本和关键状态合并成一次真实浏览器主路径，顺带看键盘、焦点、reduced preferences 和资源清理。同一份 diff 只做一次完整 [code-review](/skills/skills-reference/high/code-review/)，修完只核对 findings 和受影响的那几条命令。默认不新增也不修改测试代码，除非你这一轮明确要求。

## 产出与验收

留在仓库里的是真实的路由、页面与模块组件、具名契约类型，以及接进项目既有请求、认证和权限链的调用——不是一份实现报告。普通页面不产出设计规格、评分表、测试手册或完成收据。

交回给功能 owner 的是四样：用户能感知到的变化、实际改动的文件、验证命令与结果、剩余风险。

判断真的完成了：能把"从哪个菜单进得去、真实接口和权限对上了没有、各个状态和恢复路径都走过没有、宽屏和窄窗口分别看过没有、跑了哪些命令、还有什么只能等真实环境验"这几件事连起来讲完。契约、权限、租户、并发、可访问性或真实组件 API 里任何一条硬门禁没过，就不能声明 ready。

<Aside type="note">
本 Skill 不创建也不更新 TODO、不改功能状态、不操作 Git。只有不改变已批准行为和业务契约的缺陷修复或纯技术维护才能跳过产品流程；实施过程中出现业务变化会立即停下来。
</Aside>
