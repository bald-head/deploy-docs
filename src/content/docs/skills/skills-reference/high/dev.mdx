## 概述

一个功能分层写完再各层分别验证，最后会得到一堆能编译、但连不起来的东西：接口没有调用方、页面拿的是 mock、菜单出现了但权限没配、迁移脚本躺在那里没人跑。`dev` 是纵向编排 Skill——把一个功能的数据、接口、后端、客户端、权限和集成在同一遍实现里做完，共用一次验证和一次 Review。

它只消费已经批准的 TODO 当前项，而且必须是当前实例原子领取到的那一项：Owner、功能点、菜单入口、来源锚点、用户结果、依赖、并行写集、交付面、稳定验收和验证档位都从这里读。开工前它会做来源复核——回到锚点指向的 PRD、设计、架构和技术决策章节，输出"某章节 → 一致 / 已变化"。发现用户结果、范围、契约、权限、数据边界、验收或交付面变了，它返回范围变化并停下，而不是顺手把新需求做进去。

它不替代专业能力。数据库、接口契约、认证权限、缓存这些有专门 Skill 的部分，`dev` 负责编排和收口，不负责重写它们的规则。

## 优先级：dev 在哪一层

这套 Skill 的实现层有明确的三级优先级，不是三个平级选项：

```text
专业 Skill（crud-development、api-development、database-design、
            ui-pc、ui-app、satoken-core、data-permission…）
      ↓  任务落在这些交付面上时，优先用它们
dev   ← 已批准 TODO 里的通用纵向功能（非 CRUD、非单一专业领域）
      ↓  只有扫完整个 Skill 清单仍然没有任何一个适用
universal-development   ← 最低优先级兜底
```

所以判断顺序是从上往下：先看有没有专业 Skill 覆盖，再看是不是 `dev` 能编排的纵向功能，最后才轮到兜底。`dev` 和 [universal-development](/skills/skills-reference/low/universal-development/) 不是"两种风格"——只要 `dev` 适用，就不该选兜底。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "开始做这个功能" | 实施已领取的通用纵向功能 |
| "接着上次的做" | 续作同一个进行中项，先重做来源复核 |
| "这个要前后端都通" | 跨数据、接口、后端、客户端和权限的纵向交付 |
| "先把项目骨架搭起来" | 实施 TODO 里的共享骨架技术项 |
| "骨架好了，做第一个功能" | 全新项目里的首个纵向功能 |
| "顺手修个 bug" | 不改变已批准行为的纯技术维护，走快速路径 |

触发面覆盖纵向开发、完整功能实现、跨层交付和继续开发这一类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。在 Claude Code 里可以直接按名字调用（`/dev`）；Codex 走自己的原生发现。

## 什么时候不要用

- **标准增删改查** → [crud-development](/skills/skills-reference/high/crud-development/)。任务本来就是 CRUD 时它更直接。
- **接口契约、校验、错误语义、文档** → [api-development](/skills/skills-reference/high/api-development/)。`dev` 会调用它，但不代替它定契约。
- **认证会话、数据权限、缓存这类专业领域** → [satoken-core](/skills/skills-reference/medium/satoken-core/)、[data-permission](/skills/skills-reference/high/data-permission/)、[redis-cache](/skills/skills-reference/medium/redis-cache/)。
- **规划、写 TODO、定产品** → [project-manager](/skills/skills-reference/high/project-manager/)、[product-manager](/skills/skills-reference/critical/product-manager/)。`dev` 只消费已批准的 TODO，不自行启动新需求。
- **回写状态、统计进度** → [update-status](/skills/skills-reference/medium/update-status/)、[progress](/skills/skills-reference/medium/progress/)。它只把执行事实交回去。
- **审查已写好的代码** → [code-review](/skills/skills-reference/high/code-review/)。
- **远程服务器部署** → [server-docker-deployment](/skills/skills-reference/medium/server-docker-deployment/)。`dev` 管本地开发环境。
- **连 dev 都不适用的最小路径** → [universal-development](/skills/skills-reference/low/universal-development/)。

## 前置条件

**唯一 TODO 里有当前实例原子领取到的进行中项。** 没有领取成功就不写生产代码。一个功能只能有一个执行实例，一个实例同时只能有一个进行中项；B 依赖 A 时，A 必须已经完成才能领 B——A 正在做不算依赖满足。这套约束存在的原因很实际：共享 checkout 里两个实例改同一片路径，最后谁也说不清哪个改动属于哪个功能。

**这个功能已经完成技术选型，流程阶段是 `business-development`。** 需求、方案、确认、任务拆分和代码生成阶段只能补齐各自的阶段产物，不能提前写业务生产代码。选型没冻结就动手，等于让实现去替你做技术决策。

**任务不属于明确的 CRUD 或某个专业领域。** 属于的话上面那张优先级图已经给出答案。

## 怎么用

**1. 明确目标。** 读当前项的全部字段，确认 runtime instance 和它的执行实例一致，消费项目记忆摘要，再按锚点回读需求、设计、架构和技术决策的相关章节，输出来源复核结论。首次领取、继续做、换了 runtime 或设备、上下文压缩恢复、交接之后，这一步都不能省。范围限定在当前功能、它的直接调用链和相邻模块之内，逐项检查：真实 Owner、可复用入口、字段与接口与 ORM、权限与租户、UI 与 i18n、部署与配置、领域不变量，并把每一条落成复用、扩展或不适用的实现决策。已经有 Owner 的东西不允许静默新建一个平行实现。

**2. 发现仓库事实。** 从包清单、构建配置、脚本和 CI 里确认语言、框架、模块边界、源码根、数据存储、接口风格、权限模型、错误处理和可用的验证命令。共享 checkout 里其他实例的改动视为受保护现场——只按自己的写集过滤和核对，不覆盖、不格式化、不暂存、不夹带别人的文件。发现必须越界时先阻塞，由主 Agent 调整写集或改成串行。

**3. 局部复用检查。** 默认只搜当前功能的写集、直接调用链、同模块相邻实现，以及目标文件已经 import 或调用的公共组件；出现 import 关系、重复签名或相同契约，而且都指向同一个共享 Owner 时，才扩到那个公共目录。业务职责、输入输出、错误语义和未来变化方向都稳定一致时优先复用；只是语法相似、业务规则不同、还没有第二个真实消费者，或者抽取会引入跨域依赖时，保持局部实现。不为每个功能扫全仓，也不为了形式上去重而扩大抽象。

**4. 设计最小变更。** 已有映射到本功能的确认技术结论时直接复用；只有泛化的技术栈名称、根本没有映射，或者新证据改变了适配性时，先回到技术选型。现有技术胜出也要先写下具体选择，再标记为复用现有——"复用现有"本身不是一个选型结论。

**5. 实施顺序。** 先改最小的数据与契约层，再实现核心业务逻辑和错误处理，接上权限、事务、幂等和观测。然后是关键的一步：当前功能的后端真实接口做完之后，立刻实现它的入口层和全部批准客户端——页面、真实接口接入、权限，以及加载、空、错、成功四种状态。禁止先批量做完多个功能的后端再集中补前端。功能带菜单或按钮入口时，菜单记录、按钮权限、默认角色授权和回滚必须和业务数据迁移在同一个功能里完成。

**6. 按验证档位自验。** `Evidence-only` 优先复用现有定向检查、类型或编译或构建，或者跑一次真实主路径，同时跑目标仓库已有的 formatter（`git diff --check` 不能代替它）。`Test-first` 只在你本轮明确授权写测试时才路由 [test-development](/skills/skills-reference/medium/test-development/)。`Regression-required` 先留下可复现的失败或等价基线，再取修复后证据。风险档位本身不构成写测试代码的授权，证据不足时对应验收只能标成未验证。

**7. 真实运行验证。** 基础框架完成之后，每个功能交付都要另外跑一次真实运行：先读项目的 compose、部署和环境配置，探测已有的本地容器、进程和可达的远程中间件，有可用实例就复用，不再起同类新实例。用仓库已有命令启动前后端，等到实际健康检查或端口就绪，保留脱敏日志。只编译不启动不能关闭这一步。然后通过 [real-browser-automation](/skills/skills-reference/medium/real-browser-automation/) 或仓库已有的等价真实调用，覆盖这个功能的新入口、真实接口、权限和至少一条主路径的四种状态。

**8. 一次 Review 收口。** 先核对本实例的实际改动全部落在声明的写集内，再对当前完整功能的 diff 执行一次 [code-review](/skills/skills-reference/high/code-review/)，关闭严重和重要 findings。共享 checkout 里其他实例的改动不算进本次自验和 Review。

<Aside type="caution">
排障时同一个方法最多试三次，每次都必须带来新观察、扩大有效事实范围，或者改变一个可证伪的假设。反复跑同一条命令没有信息增量，不算换了方法。连续同根因失败、依赖或写集冲突、验收漂移、越界、或者达不到所需证据等级时，立刻交回主 Agent，由它决定调整写集、串行化、重分配还是向你升级。
</Aside>

<Aside type="danger">
它不预设三层架构、纯后端形态、固定的模块划分、包名、表前缀、字典、菜单或管理后台路径——这些都要从相邻源码确认之后才启用。未授权时不建表、不改生产数据、不装依赖、不提交、不推送。不把字段名后缀直接当成业务语义。声称代码生成成功之前，必须已经审查过实际生成的文件并跑过验证。
</Aside>

## 三种运行模式

| 模式 | 什么时候是它 |
| --- | --- |
| existing | 已有仓库里保护现有改动、复用生产模式，完成一个纵向功能 |
| bootstrap | 实施 TODO 里的共享骨架技术项，按其中的架构、技术、环境、仓库和验收完成共享骨架 |
| greenfield | 共享骨架完成之后，做 TODO 指定的第一个纵向功能；构建与锁文件、源码入口、环境配置骨架和迁移基线都直接消费已有的 |

greenfield 有一条容易忽略的边界：编码阶段不重新选栈。它消费的是已经定下来的技术绑定；没有源码事实时读批准需求、设计、架构基线、部署目标和组织标准，而不是从 Skill 示例里挑一套。共享骨架也要作为技术项写进唯一 TODO，把它的架构结论、技术选择、环境、仓库形态、真实调用方和验收都写清——它不创建假菜单，也不冒充业务功能。

## 与其他 Skill 的关系

**上游（before）**：[tech-decision](/skills/skills-reference/high/tech-decision/)（选型先冻结）、[project-manager](/skills/skills-reference/high/project-manager/)（规划与 TODO 先落盘）。

**下游（after）**：[code-review](/skills/skills-reference/high/code-review/)（同一 diff 一次完整 Review）、[update-status](/skills/skills-reference/medium/update-status/)（Review 通过后按事实回写）。

**协作（complement）**：[api-development](/skills/skills-reference/high/api-development/)、[database-ops](/skills/skills-reference/high/database-ops/)、[ui-pc](/skills/skills-reference/high/ui-pc/)、[project-details](/skills/skills-reference/high/project-details/)。

**替代（alternative）**：[crud-development](/skills/skills-reference/high/crud-development/)（明确是标准 CRUD 时）、[universal-development](/skills/skills-reference/low/universal-development/)（确实没有任何适用专业 Skill 时）。

```text
product-manager → architecture-design → tech-decision → project-manager
                                                              ↓ 已批准 TODO
                                          update-status（原子领取 → 进行中）
                                                              ↓
   dev（来源复核 → 仓库事实 → 复用检查 → 最小变更 → 纵向实施 → 自验 → 真实运行）
        ├─ api-development / database-ops / ui-pc / satoken-core…（专业交付面）
        └─ 发现范围变化 → 停止 → change-impact-analysis
                                                              ↓ 完整功能 diff
                                                    code-review（一次）
                                                              ↓
                                        update-status（完成摘要 → 写完成）
                                                              ↓
                                        git-commit（授权后提交推送并核验）
```

它是流程状态机里 `business-development` 阶段的 Owner。批准范围内的生产面全部收敛之后，把开发产物和完成边界写回流程，推进到 `code-review`；流程走到 `test-run` 时只跑已批准的现有检查、测试和真实路径，把每条验收的证据记下来再推进到 `user-acceptance`——编译成功不能当成用户验收。

## 产出与验收

最终回复只讲四件事：完成结果、来源复核与关键文件、实际跑过的验证、剩余风险。数据迁移与回滚、公共接口与 Schema、发布运维步骤、外部交接，这些本身就是交付物——随实现同步维护，和生产代码进同一个功能提交，不是"之后再补的文档"。

它把大约 95% 的执行与上下文预算花在代码读取、实现、排障、验证和一次 Review 上，TODO 和辅助文档合计不超过 5%。默认不生成过程报告，也不生成大型上下文 JSON。复杂业务、事务、并发、权限、安全、兼容、迁移、异步和公共契约，只要是新增或改动的，都要留有效的源码注释；自解释的简单表达式不逐行注释。

判断一个功能真的做完了：批准范围里的生产者、数据、后端和全部客户端一一对应且用的是真实契约；页面调用真实后端接口并把真实响应呈现在查询、详情或操作状态里；带入口的功能，菜单记录、按钮权限和默认角色授权都到位；每条验收都有匹配声明档位的新鲜证据；真实启动与主路径验证留下了证据；一次 Review 的严重与重要 findings 全部关闭。

<Aside type="note">
以下几种东西单独存在都不能关闭功能：静态页面、mock 与 fixture、孤立的 Controller、只注册了菜单权限、只完成了单端构建。"前端菜单已经出现了"也不算权限交付。
</Aside>
