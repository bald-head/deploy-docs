## 概述

`project-manager` 是 **High 优先级** Skill，负责将完整的产品定义、UI/UX 设计、系统架构和技术选型结论转化为可执行的功能 TODO。按功能点与菜单/入口建立当前开发者覆盖全部交付面的唯一 TODO 文件。

**核心职责**：
- 将上游结论压缩为来源锚点
- 建立完整功能覆盖（requirement → capability → journey → menu → feature → acceptance）
- Epic + Feature 拆分（纵向完整功能，非技术阶段）
- 依赖 DAG 与并行写集规划
- 规划档位分配（Lite/Standard/High-risk + Goal/Build）
- 生成当前开发者唯一 Markdown TODO

<Aside type="caution">
项目计划必须覆盖项目文档承诺的全部功能。流程精简只删除重复回读、状态对象、证据对象和摘要计算，不减少规划或交付内容。
</Aside>

**中文**：

**English**：

### Gates（前置条件）

1. **流程状态机已推进到 task-breakdown**
2. **technical-confirmation 已确认**
3. **存在完整的产品定义、设计、架构和技术结论**

### Not For（不适用场景）

- 产品定义
- 需求分析
- 代码实现
- TODO 状态机

## 来源锚点（持久规划记忆）

规划不能只留下一个 PRD 文件名。每个可执行 Feature 必须把原始要求压缩为 TODO 内的**来源锚点**：

```markdown
来源锚点：
- 文档: `<PRD/CR/design path#section>`
- 用户结果: <结果>
- 范围: <必须/不做/禁止替代>
- 数据/权限边界: <边界>
- 关键状态: <状态>
- 设计约束: <约束>
- 技术结论: <selected decision/rollback>
```

**锚点作用**：
- 导航记忆：首次领取或恢复 Feature 时回读原始章节
- 冲突检测：原文与锚点冲突时触发 change-impact-analysis
- 上下文恢复：压缩、换 runtime、换设备、交接时的恢复点

<Aside type="note">
锚点只保存短摘要，不复制上游正文。无关文档不重复读取，但不能以摘要、聊天记录或 checkbox 替代原文复核。
</Aside>

## 规划档位与自主边界

### 规划档位 (Planning Level)

| 档位 | 适用场景 | 保留内容 | 理由示例 |
|------|---------|---------|---------|
| **Lite** | 范围明确、低风险、复用既有技术且不改变业务行为 | Owner、入口/调用方、稳定 AC、全部真实交付面、最小验证、一次 Review | 纯文案修改、配置调整、重命名 |
| **Standard** | 新增业务行为、页面/API/数据或跨层联动 | 完整产品、UI/UX、架构、逐 Feature 技术选择、TODO、验证、Review | 新增用户注册功能 |
| **High-risk** | 权限/租户、迁移/删除、公开契约、并发/幂等、资金、跨仓/外部集成、难回滚、核心架构 | Standard + 风险/回滚矩阵、独立方案复核、Regression-required、人工门禁、发布检查 | 多租户隔离、支付集成 |

### 自主模式 (Mode)

| 模式 | 说明 | 授权范围 |
|------|------|---------|
| **Goal** | 目标、并行写集、迭代预算、验证和回滚都明确时连续推进 | 可自主完成规划和实施 |
| **Plan** | 仍需需求、方案、迁移/发布或不可逆动作批准 | 只保留在规划输出，不进入可领取 TODO；批准后转 Goal/Build |
| **Build** | 已批准方案和 TODO 的直接续作 | 直接消费方案，不重复要求多方案或确认 |

<Aside type="tip">
向下游只传一条紧凑结论：`Planning level + mode / Why / Kept / Trimmed / Escalate when`
</Aside>

   ```markdown
     - 用户/调用方: 新用户
     - 目标: 展示注册表单，验证输入，调用注册 API
     - 验收:
       - AC-001: 注册表单展示正确
       - AC-002: 表单验证有效（邮箱格式、密码强度）
       - AC-003: 提交后调用 API 并显示结果
     - 依赖: `USER-REG-API`
     - 并行写集: `src/pages/register.vue`, `src/api/auth.ts`
     - 交付面: web
     - 验证: Evidence-only
     - 规划: Standard + Build；理由：新增页面和 UI 交互
   ```

### 场景 3：依赖 DAG 与并行写集

**用户输入**：
```
前端三个页面可以并行开发吗？
```

**project-manager 分析**：

```markdown
## 依赖分析

### Feature A: USER-LOGIN-PAGE
- 依赖: `USER-LOGIN-API`
- 并行写集: `src/pages/login.vue`, `src/api/auth.ts`
- 状态: 可并行（假设 USER-LOGIN-API 已完成）

### Feature B: USER-PROFILE-PAGE
- 依赖: `USER-INFO-API`
- 并行写集: `src/pages/profile.vue`, `src/api/user.ts`
- 状态: 可并行（与 A 写集互斥）

### Feature C: USER-SETTINGS-PAGE
- 依赖: `USER-SETTINGS-API`
- 并行写集: `src/pages/settings.vue`, `src/api/user.ts`
- 状态: **不可与 B 并行**（共享 `src/api/user.ts`）

## 并行策略

**可并行**:
- A 和 B 可以并行（写集互斥）
- A 和 C 可以并行（写集互斥）

**不可并行**:
- B 和 C 不可并行（共享 `src/api/user.ts`）

## 推荐执行顺序

1. 并行: A + B
2. 串行: C (等待 B 完成)
```

<Aside type="caution">
无法证明互斥时按串行规划，不猜测安全。独占资源键包括：数据库迁移序列、公共契约、共享配置、端口、账号、Git index/ref。
</Aside>

## 工作原理

### 一次性完整规划

新项目或尚未规划的新功能必须完成：

1. **product-manager**: 研究、brainstorm、完整产品定义、能力/旅程/菜单/验收映射
2. **frontend-design**: 全部适用 Web/App/Desktop 页面与交互设计
3. **architecture-design**: 模块、数据所有权、依赖、部署、仓库、安全、可靠性和恢复边界
4. **tech-decision**: 逐个业务 Feature 比较具名候选并选定具体技术/组合、采用方式、版本、配置、生产路径、兼容、迁移和回滚
5. **project-manager**: 把全部结论变成可执行 Feature DAG 和唯一 TODO

<Aside type="note">
这些活动必须完整完成一次。每个业务 Feature 都要能映射到已确认的具名技术结论；`reuse-existing` 只能作为选中技术的采用方式，不能以"沿用现有项目"跳过比较。
</Aside>

### 项目覆盖盘点

首次建计划必须建立完整覆盖：

```text
项目要求 → capability → journey → menu/entry → feature → acceptance → technology → delivery surfaces
```

**覆盖规则**：
- 每个文档承诺能力、角色旅程、菜单/入口和验收至少映射一个 Feature
- 每个 Feature/Epic 使用稳定 ID（大写字母开头、只含大写字母/数字/连字符）
- 每个 Feature 的验收按稳定 `AC-001`、`AC-002` 编号
- 每个 Feature 必须回溯到项目要求，不能按模板增加或删除范围
- 每个 Feature 必须包含来源锚点并能回读到对应原始章节
- 每个业务 Feature 必须已有 `tech-decision` 的具名技术结论
- 纯后端功能必须写真实调用方

### Epic + Feature 拆分

**平铺 Feature 结构**（普通目标）：

```markdown
- [ ] `FEATURE-ID` 功能名称；Owner: `<developer-id>`
  - 来源: 项目文档章节或需求 ID
  - 来源锚点: ...
  - 菜单/入口: ...
  - 用户/调用方: ...
  - 目标: ...
  - 验收: AC-001, AC-002
  - 依赖: Feature ID 或无
  - 并行写集: ...
  - 交付面: data / api / backend / web / app / desktop / permission / integration
  - 验证: Evidence-only / Test-first / Regression-required
  - 规划: <Lite|Standard|High-risk> + <Goal|Build>；理由与升级条件
  - 结果: 完成时的一条合并摘要
```

**Epic 聚合结构**（大型目标）：

```markdown
- [ ] `EPIC-ID` 【Epic 名称】；Owner: `<developer-id>`；菜单/入口: `menu.*`
  - 目标: Epic 整体目标
  - [ ] `FEATURE-ID-1` 【子功能 1】；Owner: `<developer-id>`
    - 来源: ...
    - 来源锚点: ...
    - ... (完整 Feature 字段)
  - [ ] `FEATURE-ID-2` 【子功能 2】；Owner: `<developer-id>`
    - ... (完整 Feature 字段)
```

<Aside type="caution">
数据、契约、后端、前端、权限、联调、Review 和 Git **不能拆成独立 Feature checkbox**。后端存在页面入口时，对应客户端和真实接口必须在同一 Feature 完成。
</Aside>

### 完整完成屏障

Feature 只有满足以下条件后，才可由状态机在 commit 前准备 `[x]`：

1. ✅ 全部适用生产代码和数据/迁移完成
2. ✅ API、权限、错误、并发和失败恢复与验收一致
3. ✅ Web/App/Desktop 等批准客户端完成真实接入和关键状态
4. ✅ 外部集成的生产者、消费者、认证、幂等和补偿闭环
5. ✅ 每个构建根一个最有判别力的现有检查，另加一次 `git diff --check`
6. ✅ 每条 AC 都有与声明档位匹配的新鲜证据且没有 `unverified`
7. ✅ 当前完整 diff 的一次 Review 无未关闭严重/重要 finding
8. ✅ 预先准备的 `[x]`、业务改动和必要契约已进入同一次授权 commit&push，且核验一致

**High-risk 额外要求**：
- 能回读风险/回滚边界
- 实现前独立方案复核
- Regression-required 证据
- 适用发布检查

<Aside type="note">
静态页面、mock、原型、孤立接口、迁移文件、文档或构建通过都不能单独关闭功能。测试源码仅在用户本轮明确要求时新增。
</Aside>

```bash
git config user.name  # → alice-chen

# 优先级 2: 系统登录用户名
whoami  # → alice

# 优先级 3: 环境变量
echo $AGENT_DEVELOPER_NAME  # → alice-chen
```

### TODO 路径规则

```text
当前开发者: alice-chen
TODO 路径: docs/alice-chen/tasks/todo/<原文件名>.md

其他开发者: bob-zhang
TODO 路径: docs/bob-zhang/tasks/todo/<原文件名>.md (只读)
```

**隔离规则**：
- 当前开发者计划只写入 `docs/<developer-id>/tasks/todo/<原文件名>.md`
- 该目录只能有一份活动 TODO
- 其他开发者的 Feature 保持在其各自 TODO 中，不复制、不合并、不代勾选
- 同一 Git identity 下的主 Agent/subagent 共享一份 TODO

## 最佳实践

### 1. 来源锚点必须完整

```markdown
<!-- 错误: 只有文件名 -->
来源锚点: prd.md

<!-- 正确: 完整锚点 -->
来源锚点: `docs/prd.md#用户注册`；用户结果：用户可以通过邮箱注册；范围：邮箱+密码，不支持第三方；数据边界：用户表；技术结论：Spring Boot + BCrypt
```

### 2. Feature 必须纵向完整

```markdown
<!-- 错误: 按技术层拆分 -->
- [ ] USER-REG-DB 数据库表
- [ ] USER-REG-API 后端 API
- [ ] USER-REG-PAGE 前端页面

<!-- 正确: 纵向完整功能 -->
- [ ] USER-REG 用户注册功能
  - 交付面: data / api / backend / web
  - 写集: UserEntity.java, AuthController.java, register.vue
```

### 3. 依赖必须精确

```markdown
<!-- 错误: 模糊依赖 -->
依赖: 后端 API

<!-- 正确: 精确 Feature ID -->
依赖: `USER-LOGIN-API`
```

### 4. 并行写集必须互斥

```markdown
<!-- 可并行: 写集互斥 -->
Feature A: src/pages/login.vue
Feature B: src/pages/register.vue

<!-- 不可并行: 共享文件 -->
Feature A: src/api/user.ts
Feature B: src/api/user.ts  # 冲突！
```

### 5. Epic 只在必要时使用

```markdown
<!-- 不需要 Epic: 只有 1 个 Feature -->
- [ ] USER-LOGIN 用户登录

<!-- 需要 Epic: 2+ 个独立可验收的子功能 -->
- [ ] ORDER-GOVERNANCE 【订单治理】
  - [ ] ORDER-QUERY 订单查询
  - [ ] ORDER-EXPORT 订单导出
  - [ ] ORDER-RECOVERY 异常恢复
```
