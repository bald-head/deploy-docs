## 概述

一份少了三个菜单入口的计划，看起来比真实计划轻，代价在两周后——那三个入口是文档里答应过的，只是没人想起来。

`project-manager` 是规划那一遍的收口环节，不是起点。上游的产品定义、适用的页面与交互设计、架构与数据归属、每个业务功能的技术选择都真的完成过一次之后，它做三件事：沿着"项目要求 → 能力 → 角色旅程 → 菜单/入口 → 功能 → 验收 → 技术结论 → 交付面"把文档答应过的东西数一遍；把数出来的结果写成纵向完整的条目，带上依赖、并行写集、交付面和稳定的验收编号；全部落进当前开发者那一份 TODO。

它自己不做决定——不定义产品、不选技术、不写代码、不做 Review、不碰 Git。它做的是把已经批准的结论翻译成一份能连续执行的队列。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "产品、设计、架构、技术都确认了，生成 TODO" | 一次完整规划落盘，覆盖全部交付面 |
| "这个大目标怎么拆" | Epic 下挂纵向完整的子项，不按前端/后端/联调切阶段 |
| "这几个页面能一起做吗" | 依赖关系加写集互斥判断，给出能并行到什么程度 |
| "先做哪个" | 一个依赖成立的执行顺序，前置没完成的不会排在前面 |
| "这个改动很小，也要走完整流程吗" | 按真实风险给规划档位，小改动不套大流程 |
| "整份计划重排一遍" | 整体重建；只加一项不用它 |

触发面覆盖一次性建计划、拆分大目标、并行判断和整体重排这一类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **要定义产品做什么、验收长什么样** → [product-manager](/skills/skills-reference/critical/product-manager/)。产品事实是它的产出，本 Skill 只消费。
- **要划模块边界与数据归属** → [architecture-design](/skills/skills-reference/high/architecture-design/)；**要选技术** → [tech-decision](/skills/skills-reference/high/tech-decision/)。
- **要建文件、推进阶段、判断现在能不能开工** → [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/)。它管文件在哪、当前处在哪一段；本 Skill 管往里写什么内容。
- **只想加一个功能或一步** → [add-todo](/skills/skills-reference/medium/add-todo/)。它会先查重，也不会把正在做的条目重排一遍。
- **只想回写状态** → [update-status](/skills/skills-reference/medium/update-status/)；**只想看统计** → [progress](/skills/skills-reference/medium/progress/)；**只想知道该做哪一项** → [next](/skills/skills-reference/medium/next/)。
- **已批准的范围真的发生了变化** → [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。它只更新受影响的条目和依赖，比重跑一次完整规划安全得多。
- **要写产品文档、划版本范围** → [product-execution](/skills/skills-reference/high/product-execution/)。本 Skill 只产出工程 TODO 与交付面拆解。
- **要写代码** → [dev](/skills/skills-reference/high/dev/)。

## 前置条件

上游四样东西要真的齐：完整的产品定义、适用的 UI/UX 设计、架构与数据归属结论、每个业务功能的技术选择。流程上对应的是状态机已经走到 `task-breakdown`，且技术方案确认过。

这个门槛不是形式主义，每一条缺失都有具体后果：

- 缺产品定义 → 拆出来的条目会漏菜单和权限，等到联调才发现；
- 缺架构与数据归属 → 并行写集划不出来，"能不能一起做"只能靠猜；
- 缺技术结论 → 条目里的"验证"一栏没法填，实施时还要停下来补一次选型。

还有一条容易被绕过：上游只要还有会改变用户结果、范围、规则、权限、数据边界或验收的未决项，就不建 TODO。先交 [grilling](/skills/skills-reference/medium/grilling/) 一次一个问题拿到决定，再由 product-manager 形成完整事实。已经达到清晰度门槛的结论直接消费，不重复确认。

<Aside type="note">
每个业务功能都要能指到一条具名的技术结论。"沿用现有项目技术栈"不能当作跳过比较的理由——它是比较之后选中的一种采用方式，前提是这次比较真的做过。
</Aside>

## 怎么用

### 先数覆盖，再写条目

数的方向很重要：从项目文档往下数，不是从"一般系统都有什么"往里凑。后者会凭空多出一个"数据字典管理"，同时漏掉文档里写过的"导出记录留痕"。数完的结果长这样：

```text
覆盖盘点
能力 4 项      → 功能 9 个
角色旅程 3 条  → 全部有入口覆盖
菜单/入口 6 个 → 6 个已映射
验收 23 条     → 23 条已编号并挂到具体功能
纯后端 2 个    → 已写明真实调用方（定时任务 / 对外接口）
未覆盖 0
```

功能和 Epic 用稳定 ID，验收用稳定编号（`AC-001`、`AC-002` 这种），后面的 Review、状态回写和影响面分析才能指着同一个东西说话。ID 一变，所有引用它的地方就断了。

### 一条条目的实际形态

```markdown
- [ ] `ORDER-EXPORT` 订单批量导出；Owner：`<developer-id>`
  - 来源：docs/product-spec.md#批量导出
  - 来源锚点：用户结果=运营按当前筛选导出 CSV；范围=5 万行上限、不做定时导出；
    权限边界=导出权限点；技术结论=<选定方案 + 回滚要点>
  - 菜单/入口：订单管理 → 订单列表 → 工具栏"导出"
  - 用户/调用方：运营角色（持有导出权限点）
  - 目标：把手工对账导出从 25 分钟压到 3 分钟内
  - 验收：`AC-001` 行数与列表一致；`AC-002` 超限明确拒绝；`AC-003` 无权限不可见
  - 依赖：`ORDER-LIST-FILTER`
  - 并行写集：`admin/order/export`、`core/task`、`web/src/views/order`
  - 交付面：data / api / backend / web / permission
  - 验证：Regression-required
  - 规划：Standard + Build；理由=新增业务行为且跨层；升级=一旦动到脱敏规则
  - 结果：待完成
```

来源锚点只放摘要，不把上游正文抄一份进来——那等于在 TODO 里维护第二份需求文档，两份很快就会不一致。反过来，真要动范围时也不能只看锚点：摘要、聊天记录和 checkbox 都不能替代回原文核对一遍。

<Aside type="caution">
有一种拆法一定不会出现：把数据、契约、后端、前端、权限、联调、Review、Git 各拆成一个 checkbox。那样每一格勾上都不代表用户能用上任何东西，而"全都勾上了但功能不能用"正是这套流程最想避免的状态。后端功能只要有页面入口，页面和真实接口就和后端在同一条里完成。
</Aside>

### Epic 只在一条装不下时才用

普通目标直接平铺一条。只有大到能拆成两个以上"各自可用、可验收、可验证、可回退、写集能独立声明"的纵向子项时，才加一层 Epic，子项写成它下面两空格缩进的直接子列表。Epic 只保存 Owner、来源、整体目标和菜单入口汇总，不可领取，也不保存依赖、写集、验收、验证、档位、结果或 Git 状态；全部直接子项完成后由状态机汇总。不支持三层或更深的任务树。

### 能不能并行，按这个顺序判断

```text
1. 依赖走通了吗？前置没完成 → 直接串行，不用看写集
2. 写集有交集吗？有一个目录重叠 → 串行
3. 有共享的独占资源吗？迁移序号、对外契约、共享配置、端口、账号、Git 索引与引用 → 串行
4. 三条都过 → 可以并行；契约、迁移、集成、Review、TODO 收口和 Git 仍由主 Agent 串行收
```

<Aside type="caution">
互斥证明不出来时，结论是串行，不是"看起来应该没事"。文件路径之外还有一类东西天生只能一个人动，它们不出现在写集里但同样会撞——两个执行者各写一个迁移文件、序号一样，谁先合谁后合就成了运气问题。
</Aside>

### 规划档位：同一份计划，三种深度

`Lite` 给范围明确、低风险、复用既有技术且不改变业务行为的改动；即便如此，Owner、入口与调用方、稳定验收、全部真实交付面、一次最小验证和一次 Review 都还在。`Standard` 给新增业务行为、涉及页面/接口/数据或跨层联动的改动。`High-risk` 给权限与租户、数据迁移或删除、对外契约、并发幂等、资金、跨仓与外部集成、难回滚、动核心架构的改动——在 Standard 之上再加风险与回滚矩阵、实现前的独立方案复核、回归证据、人工门禁和发布前检查。改按钮文案是 Lite，加一个注册功能是 Standard，接支付或上多租户隔离是 High-risk。

档位后面还跟一个自主模式：`Goal` 表示目标、写集、预算、验证和回滚都清楚，可以连续推进；`Build` 表示方案和条目都已批准，直接实施；`Plan` 表示还有需求、方案、迁移或发布没批，只能留在规划输出里，不进可领取队列。`Plan` 最容易被跳过，而一个没批准的迁移方案一旦进了可领取队列，下一个执行者就会当成既定事实去做。

## 与其他 Skill 的关系

它站在规划链的末端：[product-manager](/skills/skills-reference/critical/product-manager/) 先给出产品定义与验收，[frontend-design](/skills/skills-reference/high/frontend-design/) 给页面与交互基线，[architecture-design](/skills/skills-reference/high/architecture-design/) 给模块与数据归属，[tech-decision](/skills/skills-reference/high/tech-decision/) 逐个功能定技术；[task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 把流程推到拆分那一段，本 Skill 才动笔。写完之后交 [dev](/skills/skills-reference/high/dev/) 实施，[project-details](/skills/skills-reference/high/project-details/) 提供的复用地图会约束规划范围——已经有 Owner 的公共能力不该再规划一遍。

```text
product-manager（产品定义与验收）
architecture-design（边界）· frontend-design（UI/UX）· tech-decision（逐功能技术）
        ↓
task-todo-workflow（推进到拆分段）
        ↓
project-manager（覆盖盘点 → 条目/Epic → 依赖与写集 → 唯一 TODO）
        ↓
next（挑一项）→ dev（实施）→ code-review → git-commit
        ↕
add-todo（追加）· update-status（回写状态）· progress（只读统计）
        ↕
change-impact-analysis（已批准范围真的变了）· project-details（长期约定）
```

反例最能说明分工：用 `add-todo` 一条条把整个项目加进去，不会做覆盖盘点，于是"文档里答应过但没人想起来"的那几项永远不在计划里；反过来，为了加一个小功能重跑一次完整规划，会把正在做的条目重排一遍，正在执行的实例会读到和自己手上不一样的计划。

## 产出与验收

产出只有一份文件和它的可核对性：唯一 TODO 的路径；项目全部承诺能力与功能、菜单入口的覆盖结果（包含未覆盖为 0 的结论）；当前项、下一个 ready 项、依赖与阻塞；每条的目标、菜单、验收、依赖和全部交付面；以及已完成条目的真实性边界——哪些是真的验证过的，哪些只是代码在那里。

判断这份计划真的可执行：随便挑一条，能顺着它的来源锚点回读到原始章节；它的依赖都指向同一份文件里已定义的 ID 且整张依赖图无环；它的写集和所有正在进行的条目两两互斥；它的验收编号能在 Review 和结果摘要里沿用同一个编号。四条里有一条答不上来，这条就还不能开工。

<Aside type="note">
条目里的完成屏障比"代码写完了"严得多：生产代码与数据/迁移都落了，接口、权限、错误、并发与失败恢复和验收对得上，批准过的客户端真的接进去且关键状态都在，外部集成闭环，每个构建根跑过一个最有判别力的现有检查外加一次 `git diff --check`，每条验收都有匹配档位的新鲜证据且没有一条停在未验证，当前完整 diff 过了一次 Review 没有未关闭的严重或重要 finding，最后连同勾选进同一次授权提交并核验远端。单独的静态页面、mock、原型、孤立接口、迁移文件、文档或"构建通过了"都不能关闭一条功能。
</Aside>
