## 概述

`ui-app` 落地的是"同一份产品在几个客户端上都真的能用"这件事。它先把仓库到底是什么搞清楚——uni-app、React Native/Expo、Flutter 还是原生——再决定读哪套规则。只有依赖和源码共同证实是 uni-app，它才会用那一套路由、分包、tabBar、条件编译和安全区 API；不是的话就沿用仓库现有方案，不把一个框架的写法套到另一个上面去。

它对"完成"的判断线值得先说清楚：H5 跑通、模拟器跑通、静态检查全绿，都不等于全平台完成。相机与相册、系统权限弹窗、原生 tabBar 与状态栏、安全区、键盘顶起、返回手势、弱网和后台恢复，只有真机能证明；设备拿不到就把它们写成未验证边界，而不是顺势推断成通过。

视觉上它只从 Apple 那边取 clarity、response、deference、depth 和 craft 这几个原则，不复制 iOS 的导航、chrome 和字体——目标平台自己的导航习惯、品牌和输入方式保留原样。设计基线、后端接口、任务状态和 Git 都不在它手里。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "做个登录页，App 和小程序都要" | 一份实现覆盖多个客户端 |
| "加个商品列表页" | 列表、分页、下拉刷新、触控交互 |
| "H5 上这个页要改一下" | H5 客户端页面实现 |
| "小程序里再加一个页" | 页面文件加路由与分包配置 |
| "上传头像要能走相册" | 系统权限、上传与对象存储回写 |
| "底部按钮被手势条挡住了" | 安全区与固定操作区 |
| "这个页返回不回去" | 导航栈、返回路径与无历史兜底 |

触发面覆盖移动端与跨端客户端、小程序、H5 这几类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **PC 与管理端界面** → [ui-pc](/skills/skills-reference/high/ui-pc/)。PC 的表格不能直接压缩到手机上：按任务换成分组列表、渐进详情、搜索筛选和批量操作的移动等价路径，这是两套不同的结构决定。
- **还没有设计结论** → [frontend-design](/skills/skills-reference/high/frontend-design/)。它输出可实施的设计基线；本 Skill 消费基线，不替你做设计决定。
- **已有页面的打磨、精修、只读审查** → [frontend-polish](/skills/skills-reference/high/frontend-polish/)。分开是为了避免两个 Skill 对同一个页面各审一遍。
- **只读审查现有动效和 motion 系统** → [review-animations](/skills/skills-reference/low/review-animations/)；只是想知道某个动效叫什么 → [animation-vocabulary](/skills/skills-reference/low/animation-vocabulary/)。
- **后端接口本身** → [api-development](/skills/skills-reference/high/api-development/)。
- **产品定义与验收标准** → [product-manager](/skills/skills-reference/critical/product-manager/)。会改变产品流程、导航、权限、文案或平台行为的决定，要交回设计或项目 owner，不在实现阶段替他们定。

## 前置条件

1. **UI/UX 结论已经在手，或者明确复用现有设计系统。** 它不做设计发散。缺这一步，页面很容易滑向固定 Hero 加宫格卡片、紫蓝渐变、无语义玻璃、卡片套卡片这类模板化结果——而这些恰恰是它要避开的风险模式。
2. **目标平台和框架已经确认。** 路由、分包、条件编译和导航 API 在 uni-app、React Native/Expo、Flutter 之间完全不通用，框架猜错，写出来的代码连编译都过不去。而且"要交付哪几个平台"直接决定了后面的验证矩阵有多长。
3. **导航和平台能力需求已经明确。** tabBar 根页面、普通子页面、替换当前栈是三种不同的跳转语义，选错的表现是返回按钮点了没反应，或者栈越走越深。相机、相册、通知这类系统权限要在请求前说明用途、被拒后给恢复路径——都不是页面写完再补的东西。

<Aside type="danger">
不能用 H5、模拟器、静态检查、fixture 或者单张截图，冒充真机、真实后端、弱网、系统权限或整个客户端的验收。当前范围内已经发现的 P0/P1 还没关掉时不能声明完成；碰不到的设备和外部能力必须明确列成未验证边界。
</Aside>

## 怎么用

### 1. 先摸清仓库，再决定读哪套规则

搜索根从你指定的范围、Git 根、workspace 配置和仓库规则确认，不默认应用就在根目录或 `src/`。按存在情况找构建清单和入口：`package.json` 与锁文件、`pages.json` 或 `pages.config.*`、`manifest.json`、`App.vue`、Metro 与 Expo 配置、`pubspec.yaml` 与 `lib/main.dart`，或者原生方案对应的清单。再定位组件、令牌、Store、请求与上传封装和验证脚本，并且至少读一个同技术栈的相邻生产页面，核对真实导入、组件 API、安全区处理、Loading、错误恢复和返回方式。

确认是 uni-app 之后，才按当前主题读它的三份专属参考：路由与分包与 tabBar 与安全区、请求与状态与 Long ID 与对象存储、三端构建与真机边界。不是 uni-app 就沿用仓库现有的 React Native/Expo、Flutter 或原生规范。请求层确认是 alova 时按 [alova-client-usage](/skills/skills-reference/low/alova-client-usage/) 接入，不在页面里重造一层封装。

### 2. 实现页面与交互

一个页面围绕一个核心任务和一个清晰的主动作组织。八态按适用范围查齐：default、hover（只在真有指针时）、`focus-visible`、pressed 与 dragging、disabled、pending 与 loading、empty，以及 error 与 success 这两种结果态——两者同时存在时分别验证。非根页面必须有真的走得通的返回路径，并且在没有历史栈时有兜底页面，不能让返回按钮点了没反应。

安全区、键盘顶起、滚动、横竖屏、长文本、动态字体、触控命中区、取消与重试、防重复提交和无障碍，都按真实平台处理。详情呈现沿用项目既有约定，缺约定时优先 Modal/Dialog，复杂内容走项目认可的独立详情路由——不要在同一个产品里混用几个同职责的容器。请求、认证、租户、刷新、加密、上传和错误封装一律复用既有实现；账号、权限和跨页面状态进共享层，页面输入和一次性 UI 状态留在局部。

页面涉及图表时先沿用仓库已有的图表库或跨端封装，不为一个页面混装第二套。没有既有选择时，选型是规划阶段 [tech-decision](/skills/skills-reference/high/tech-decision/) 的事——目标平台、包体、渲染后端、触控 tooltip、resize、主题和卸载销毁都要先验证过，本 Skill 不在写页面时临时选库。小屏上按可读性减少系列和装饰密度，复杂指标口径、阈值、时间窗口和联动逻辑写注释。

<Aside type="caution">
全局 Loading 只能有一个所有者。它必须走项目既有的并发计数或令牌机制——否则先返回的那个请求会把另一个还在飞的请求的遮罩提前关掉。骨架、局部 Loading 或按钮 pending 已经表达了进度时，不要再叠一层全屏遮罩。
</Aside>

### 3. 数据契约上最容易出血的几处

- **业务主键**：可能超过 JavaScript 安全整数的 ID，在路由、Store、类型和比较里全链路走字符串，不对它们调用 `Number()` 或 `parseInt()`。精度一旦在前端丢掉就找不回来了。
- **时间**：用项目统一的工具，并且明确兼容 10 位秒、13 位毫秒、纯数字字符串、ISO 和后端 SQL 日期格式；无效值给统一占位，不把原始时间戳直接显示给用户。
- **业务状态**：走集中的枚举或常量，不在模板、条件、路由和 API 映射里散落魔法数字和字符串。
- **对象存储**：业务提交只回写存储定位（`configId` 加 `objectKey`，或 `bucket` 加 `objectKey`），临时 URL 只用于展示和下载。删除、下载、迁移和幂等判断都用定位，不用会过期的 URL。
- **身份变化**：退出登录、切租户和权限变化必须清掉或失效所属状态，防止跨账号、跨租户残留。

### 4. 验证按改动范围选，不一律拉满

先读 `package.json`，只跑真实存在的脚本，不假设包管理器和脚本名。

| 改了什么 | 至少要验到哪 |
| --- | --- |
| 类型、Store、API 类型 | 类型检查 |
| 页面、组件、样式 | 类型检查 + H5 构建 |
| 路由配置、布局、条件编译 | H5 + 对应的 App 或小程序构建 |
| 上传、相机、权限、安全区 | 构建 + 真机人工验收 |
| 请求、认证、Long ID | 已有合约测试 + 类型检查 + 关键流程核对 |

能跑起来就走一条真实主路径，把与改动直接相关的 viewport、长文本、主题、安全区、键盘与触控、空与错与加载合并进同一批检查。同一份 diff 只做一次完整 [code-review](/skills/skills-reference/high/code-review/)，修完只关闭 findings 并重跑受影响的那几条命令。默认不新增也不修改测试代码，除非你这一轮明确要求。

<Aside type="caution">
uni-app 构建在部分 macOS 环境上会报 `EMFILE: too many open files, watch`。确认是文件监听上限而不是代码错误之后，可以在单次构建里开轮询降级绕过去——但首次失败和降级方式都要照实记进结果，既不能把环境问题写成代码失败，也不能把降级后的结果写成一次干净通过。
</Aside>

## 与其他 Skill 的关系

**上游（before）**：[frontend-design](/skills/skills-reference/high/frontend-design/)、[api-development](/skills/skills-reference/high/api-development/)——一个给页面结构、交互和状态结论，一个给字段、枚举和错误语义。

**下游（after）**：[frontend-polish](/skills/skills-reference/high/frontend-polish/)、[code-review](/skills/skills-reference/high/code-review/)。

**协作（complement）**：[review-animations](/skills/skills-reference/low/review-animations/)、[animation-vocabulary](/skills/skills-reference/low/animation-vocabulary/)。

```text
frontend-design（页面、交互、状态、验收结论）
api-development（字段、枚举、权限、错误语义）
        ↓
   ui-app（框架识别 → 导航与安全区 → 八态 → 数据契约 → 构建与真机）
        ├─ alova-client-usage（请求层确认是 alova 时）
        └─ tech-decision（缺图表栈时，在规划阶段选型）
              ↓
        code-review（一次完整 Review）→ frontend-polish（后续打磨）
```

同一个功能同时有客户端和管理端交付面时，两端分别由本 Skill 和 [ui-pc](/skills/skills-reference/high/ui-pc/) 完成，契约与收口留给功能 owner。

## 产出与验收

留在仓库里的是真实的页面文件、组件、路由配置和接进既有封装的调用。路由配置有一点要留神：`pages.json` 这类文件在不少项目里是生成产物，要改的是生成源，直接改产物下次构建就被覆盖回去了。

交回给功能 owner 的是四样：用户能看到的变化、实际改动的文件、验证命令与结果，以及没验到的平台、设备、权限和弱网边界。

判断真的完成了：说得出"哪个平台的哪个入口进得去、真实接口和权限对上了没有、八态和返回路径走过没有、跑了哪些构建、哪些只能真机验而现在还没验"。单端构建证明不了全平台完成；布局或全局组件这类改动还可以进一步在产物里搜稳定 class 或组件注册名，确认它真的进了包。

设备拿不到、又确实需要别人接手验收时，只在里程碑上做一次最小人工交接：版本或安装包、步骤、预期、证据，以及失败怎么回流。普通开发任务在最终回复里写清未验证边界就够，不为它另建报告或评分文档。

<Aside type="note">
本 Skill 不创建也不更新 TODO、不改功能状态、不操作 Git。只有不改变已批准行为和业务契约的缺陷修复或纯技术维护才能跳过产品流程；实施过程中出现业务变化会立即停下来。
</Aside>
