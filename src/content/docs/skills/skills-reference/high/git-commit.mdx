## 概述

提交这件事真正容易出错的地方不是提交信息，而是范围。index 里可能已经躺着不属于这次任务的 staged 路径；同一个文件里可能混着任务开始前的旧 hunk；父目录下可能藏着一个独立子仓库，被父仓库显示成一个未跟踪目录；push 完终端打印了成功，远端 ref 其实没动。

`git-commit` 把这些都当成必须先证明的事实：逐路径解析真实 Git 根，把任务 hunk 和旧 hunk 分开，只暂存本次范围内的精确路径，commit 之后回读最终提交正文和提交树，push 之后回读本地 `HEAD`、`@{upstream}` 和目标 remote ref 三个 OID——三者完全一致才算推上去了。任何一步证明不了，它返回一个 Git barrier，写清文件和恢复条件，而不是绕过去。

它只做普通的精确暂存、commit 和明确授权后的 push。分支、合并、rebase、stash、历史改写和冲突处理都属于 [git-workflow](/skills/skills-reference/high/git-workflow/)。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "把这些改动提交了" | 精确暂存加一次 commit |
| "提交，顺便推上去" | commit 之后执行已授权的 push |
| "只推一下，别再动代码" | 复用已核验的现有 commit，只做 push |
| "这个功能做完了，走交付" | 流程走到 Git 交付阶段的收口 |
| "三个仓库一起提" | 多个 Git 根分别形成提交与推送 |
| "帮我写条提交信息" | 只生成文本，不执行——这一种它不会动手 |

触发面覆盖提交、推送、逐功能交付这一类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。在 Claude Code 里可以直接按名字调用（`/git-commit`）；Codex 走自己的原生发现，说清"把这次改动提交"或"提交完推到哪个分支"就行。

## 什么时候不要用

- **建分支、切分支、合并、rebase、解冲突、stash、改历史** → [git-workflow](/skills/skills-reference/high/git-workflow/)。这是最常混的一条：本 Skill 只在当前分支上做普通提交和推送，任何会改写历史或强制更新远端的动作都不在它的授权里。
- **写代码、修 bug** → [dev](/skills/skills-reference/high/dev/)、[universal-development](/skills/skills-reference/low/universal-development/)。
- **审查这次改动** → [code-review](/skills/skills-reference/high/code-review/)。它消费 Review 结论，不代替 Review。
- **部署与发布流水线** → [server-docker-deployment](/skills/skills-reference/medium/server-docker-deployment/)。推到远端不等于发布。
- **回写 TODO 状态** → [update-status](/skills/skills-reference/medium/update-status/)。两者常常配合：状态 hunk 和业务改动进同一个提交，但状态由那一边写。

## 前置条件

**用户已经明确授权。** 提交和推送都改变共享状态，push 尤其不可静默回退。授权不延续到下一次：这一轮批准的是这一轮的提交。项目给了逐功能持续 commit&push 授权时，它也只在已确认的 featureId、仓库、分支、remote 和目标 ref 这个包络内复用，不扩展到别的仓库、别的 ref，也不包括 force、删除远端、改写历史或执行发布。

**没有未关闭的严重或重要 Review finding。** 带着已知严重缺陷推上远端，后面要么改历史要么再补一笔，代价比先修掉高得多。

**目标文件范围明确。** 范围来自当前 diff 和任务事实。范围说不清的时候它不会用一条递归暂存兜过去——那正是夹带别人改动的主要来源。

## 变更日志

每个真实代码、Skill、配置或文档变更包都要更新仓库已有的 `CHANGELOG.md`（或等价日志路径），并与业务改动和必要的 TODO 收口放进同一提交。没有现成日志时，只在第一次真实变更中创建；不创建只有日志或状态的空提交。日志记录用户可见影响、兼容注意和恢复信息，不写 TODO 状态、执行实例、命令流水或伪造 commit OID。分支合并的 fast-forward 继承来源日志，产生 merge commit 时只记录本次合并新增影响，具体由 [git-workflow](/skills/skills-reference/high/git-workflow/) 负责。

## 怎么用

**1. 解析仓库拓扑。** 对每个目标路径分别解析规范化的绝对 Git 根，不是在父目录跑一次 `git status` 了事：识别 `.git` 目录、`.git` 文件、worktree、submodule，以及父目录里的独立子仓库。父仓库把独立子仓库显示成未跟踪或已忽略目录时，不从父仓库递归暂存；多个 Git 根各自形成自己的提交、推送和同步结果。

**2. 建任务基线，把旧 hunk 摘出去。** 任务开始前就 dirty 的文件必须区分用户旧改动和本次改动；未跟踪文件逐个核对归属；删除、重命名、生成物、锁文件、迁移和配置逐项确认属于当前功能。同一文件里混着旧 hunk 和任务 hunk 时只暂存任务专属的那部分。无法可靠隔离时它停下来报 barrier——不整文件暂存，也不用 `reset`、`restore --staged` 或 stash 替你清理 index。

**3. 核对 staged 范围。** `git diff --cached --name-status` 和完整 `git diff --cached` 都要看：每条 staged 路径都在这次审查过的范围内，没夹带构建产物、依赖目录、本地缓存、无关删除、旧 hunk 或别的仓库的文件。

**4. 提交后立刻复核，再决定要不要 push。** commit 完成、push 之前读最终提交正文和 `git diff-tree` 列出的全部提交路径。`pre-commit`、`prepare-commit-msg`、`commit-msg` 这类 Hook 会改 index、工作区和提交信息，所以以最终提交树和最终正文为准重新核验；路径或内容超出已审查范围就不 push。

**5. push 用单一显式 refspec**，例如 `HEAD:<完整 destination ref>`，不用裸 `git push`、`--all` 或 `--tags`；不默认 remote 叫 `origin`，也不因为分支同名就猜远端目标。已配置 upstream 时用它真实的 remote 和 remote branch；没配置时先从仓库规则、branch 配置和用户已确认的目标里选定；remote 不止一个、目标不明确或当前是 detached HEAD 时停下来交给你或 `git-workflow`。

**6. push 后回读三个 OID。** 本地 `HEAD`、`@{upstream}`、目标 remote/ref 的实际值，再看当前分支与 upstream 的 ahead/behind。三者完全一致且 push 命令成功，才把这个仓库记为已推送。没有 upstream、远端查询失败、remote ref 不一致或分支仍然 ahead/behind 时进入 barrier——终端出现"成功"不作为同步依据。

## 提交信息的三条硬规则

**中文表达真实变更。** 标题、正文段落和正文 bullet 用中文。能保留英文的只有 Conventional Commit 的类型和可选的 scope、`BREAKING CHANGE` / `Refs` / `Closes` 这类业务脚注关键字，还有路径、命令、包名、类名、字段名、API 名、远端名和 Issue 编号这些技术标识。不生成英文标题或英文正文。

**不带任何 AI 协作者署名。** `Co-Authored-By`、`Generated by Claude/Codex/AI` 或等价的生成器署名、把 Anthropic 或 OpenAI 写成协作者与生成器脚注、把 reviewer 或机器人伪装成共同作者，全部禁止。这条不靠自觉：提交命令里出现这类署名会被直接拦下，重试同一条命令仍然拒绝。业务名称、技术名词或文件内容里合法出现的 "AI" 不受影响；`Reviewed-by`、`Signed-off-by` 只有仓库明确要求且身份事实可证明时才保留，不从示例里虚构。

**拆分看能不能独立构建和回退。** 单文件、单一小修复、纯样式或纯文档改动只用一行标题就够。接口行为变化、状态流转、数据结构调整、迁移，或者一条跨多个文件的修复链路，要用标题加正文 bullet，每条写真实行为、兼容影响或关键实现，不写"优化代码"这种空话。跨层强依赖的纵向 feature 保持在同一个逻辑提交里——生产代码、必要的 Schema、API、迁移与回滚文档，以及那份唯一 TODO 的状态 hunk，不拆成两笔；跨 Git 根仍然分别提交。详细的类型与格式约定见 Skill 自带的约定式提交参考，但仓库已有规则优先。

<Aside type="danger">
会丢弃工作区或改写远端的 Git 命令由 Runtime Hook 直接拦下，不是"建议不要用"：`git reset --hard`、`git clean` 的 `-f` 配 `-d`/`-x`、`git checkout .` 与 `git restore .` 这类批量丢弃，以及 `git push` 上的 `--force`（含 `--force-with-lease`）、`--delete`、`--mirror`、`--prune` 和 `+refspec`。不要试图绕过它。确实需要改写历史或删除远端 ref 时，交给 `git-workflow`，并取得精确到仓库、remote、ref 和 oldOID 的一次性授权。删除分支之类的操作不在普通提交授权里，也不在只读 Git 命令的自动放行名单里，会单独走一次确认。
</Aside>

<Aside type="caution">
amend 的边界很窄：只有"这次提交还没 push、改的只是提交信息本身、而且当前授权明确覆盖了这个修正"时才能做。已经推送的提交，即使提交信息不合规也不能自动 amend、force push 或删除远端提交——只能如实报告已推送这个事实，再按你的选择保留历史、追加一笔修正提交，或者交给 `git-workflow` 执行精确的历史改写。
</Aside>

<Aside type="note">
配置、部署和认证接入文件里的用户名、密码、Token 和服务凭据，不因为内外网或明文形态被误报成泄密而阻断提交。你已经要求提交或提交并推送，且文件在本次精确 staged 范围内时，这些内容已经包含在 Git 交付授权里：它不会再要一次凭据专项确认，也不会为了通过检查去脱敏、删除或排除文件。文件不属于本次范围时仍然必须停止夹带；新增或修改带凭据的 remote 需要独立授权，不能借提交授权静默改写。
</Aside>

## 多仓与 submodule

一个 feature 跨多个仓库时，先把全部仓库的范围、Review、staged 与提交树、remote/ref 和权限预检做完，再按契约兼容关系确定推送顺序。目标路径属于 submodule 时顺序是固定的：从最深层 submodule 到最外层父仓完成 Review 和本地提交，确认父仓 index 中该路径确实是 `160000` gitlink 且精确指向已审查的子仓 commit，任何远端写入之前先复核全部相关子仓与父仓的 staged 路径和提交树；push 同样从最深子仓往外，子仓 commit 在目标 remote ref 可达并核验 OID 之后，才允许推指向它的父仓 gitlink。普通的嵌套独立仓库不生成也不更新父仓 gitlink。

部分仓库推成功、其余失败时，只保留真实的已推送与阻塞事实：不 reset、不删远端、不 amend，保留已经成功的远端状态；修好认证、网络或 upstream 之后只重试没同步的仓库；已推状态造成不兼容而需要回滚或改写历史时转交 `git-workflow`。不会用一笔"证据提交"把部分失败盖过去。

## 与其他 Skill 的关系

**上游（before）**：[code-review](/skills/skills-reference/high/code-review/)、[test-development](/skills/skills-reference/medium/test-development/)——先有一次 Review 结论，严重与重要 finding 全部关闭。

**下游（after）**：[git-workflow](/skills/skills-reference/high/git-workflow/)——需要分支、历史或高风险远端写入时接手。

**协作（complement）**：[update-status](/skills/skills-reference/medium/update-status/)——当前功能仍是进行中状态时，先按它的完成摘要契约把结果写齐、在锁内准备好已完成标记，再和业务改动一起进同一个提交。

```text
dev / crud-development（实现收敛）
      ↓
code-review（一次审查，严重/重要 finding 关闭）
      ↓
update-status（写完成摘要，锁内准备 TODO 状态 hunk）
      ↓
git-commit（精确暂存 → commit → 复核提交树 → 授权后 push → 三方 OID 核验）
      ├─ OID 一致 → 交付成立，回读远端 TODO，领取下一个 Ready 功能
      └─ 无法证明范围 / 无 upstream / OID 不一致 → Git barrier
            → git-workflow（分支、历史改写、远端删除等高风险操作）
```

它是流程状态机里 Git 交付阶段的 Owner，进入这一阶段前要确认需求、方案、开发、Review、测试和验收都已完成；核验 local、upstream、remote 和远端 TODO 一致之后才推进到完成，未授权 push 或远端不一致时停在当前阶段并写下恢复条件。

## 产出与验收

逐仓报告：Git 根、提交标题与 hash、目标 branch 与 remote ref、push 结果、三个 OID 是否一致，以及剩余工作树内容或真实阻塞。跨多仓时还会逐仓记录审查过、暂存过、提交过的路径范围，以及未提交、未推送或需要回滚的恢复条件。没有有效变更时它明确说明，不创建空提交。

判断真的完成了：你能说出每个仓库推到了哪个 ref、三个 OID 一致、提交树里没有任何一条路径超出本次范围、提交信息里没有 AI 署名。这四件事里缺一件，交付都还没成立——本地看起来干净不算。

以下情况它会停下来要一个新决定，而不是自己选一个：暂存范围或旧 hunk 的归属证明不了；需要 amend、历史改写、force 或删除远端；出现新 remote、目标 remote/ref 有歧义或和仓库分支策略冲突；拆分方式会改变你要求的交付原子性；submodule 与父仓 gitlink 该不该更新没有证据。
