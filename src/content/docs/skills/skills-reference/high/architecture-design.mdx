## 概述

产品定义回答的是"产品由哪些能力、旅程和入口构成"。`architecture-design` 回答紧接着的那个问题：这些能力受哪些系统、数据、仓库和部署边界约束。

它做七件事：把边界按业务能力和数据所有权划出来（不按技术分层）；定死谁可以调谁、通过什么调、跨边界失败和超时怎么算；给每份主数据指定唯一写入者；冻结环境矩阵与仓库矩阵；至少比较两个能真正落地的候选；给出带回滚点的演进路径；说清每条关键假设怎么验证。

它不选具体技术——语言、框架、数据库、请求层、生成器、桌面壳和基础设施由 [tech-decision](/skills/skills-reference/high/tech-decision/) 逐 Feature 选定并冻结。它也不建表、不写接口实现、不动任务状态。产品侧的稳定标识（`capabilityId`、`journeyId`、`menuId`、`featureId`、`requirementIds`、`dependsOn`）在这里只能被引用，不能被删除、合并或静默改写；发现冲突交 [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/) 定向处理。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "产品定义好了，边界怎么划" | 模块职责、数据归属、允许的调用方向 |
| "这块要不要拆成独立服务" | 真实候选的对比，加一条带回滚点的演进路径 |
| "这个功能应该放哪儿" | 从业务能力和数据所有权给出归属判断，附理由 |
| "这几个仓库怎么分" | 冻结下来的仓库矩阵：`repoId` 与逻辑 `root` |
| "环境怎么划、谁能晋级到谁" | 环境矩阵：用途、隔离、配置来源、晋级关系与人工门禁 |
| "A 模块能不能直接调 B" | 依赖方向规则，以及跨边界调用的失败与超时语义 |
| "现在是单体，以后要不要服务化" | 演进切片、兼容层、观察窗、删除旧路径的门禁 |

触发面覆盖架构设计、模块与边界划分、数据归属、依赖治理、部署单元和仓库拆分这一类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **选语言、框架、数据库、请求库、生成器、桌面壳** → [tech-decision](/skills/skills-reference/high/tech-decision/)。这里定"怎么分边界"，它定"用什么实现"，而且是逐 Feature 选完就冻结。
- **建表、加索引、写迁移** → [database-design](/skills/skills-reference/high/database-design/)。这里只定数据归谁、谁能写。
- **接口路径、参数校验、错误码、分页契约** → [api-development](/skills/skills-reference/high/api-development/)。
- **页面结构与交互** → [frontend-design](/skills/skills-reference/high/frontend-design/) 定基线，[ui-pc](/skills/skills-reference/high/ui-pc/) 与 [ui-app](/skills/skills-reference/high/ui-app/) 落地。
- **把已确认的结论画成图** → [archify](/skills/skills-reference/medium/archify/) 或 [mermaid](/skills/skills-reference/low/mermaid/)。它们负责画，不负责决策。
- **Agent 架构与治理** → [agent-optimizer](/skills/skills-reference/low/agent-optimizer/)。这里管业务系统的边界。
- **已定方案的实际构建与部署** → [server-docker-deployment](/skills/skills-reference/medium/server-docker-deployment/)。
- **建或改 TODO** → [project-manager](/skills/skills-reference/high/project-manager/) 或 [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/)。这里不创建平行 TODO，也不自行改任务状态。
- **写代码** → [dev](/skills/skills-reference/high/dev/) 或对应领域 Skill。

## 前置条件

1. **完整产品定义已经在手上**：有哪些能力、谁在用、入口长什么样。缺了会改变边界的事实就明确阻塞，不用模板补齐——模板补出来的边界，等真需求到了还要重划一遍。
2. **有页面的部分，适用的 UI/UX 基线也要先有。** 页面结构会真实影响接口划分和模块归属，倒过来做等于让边界跟着后补的页面改。
3. **这一轮真的需要定系统边界、模块职责或数据所有权。** 上游档位是 `Lite`、并且模块、数据归属、部署和仓库边界都没变时，只回读并引用既有架构，不生成新设计。

上游自主模式是 `Plan` 时，这里只冻结待批准的架构，不把 Feature 送进可执行队列；批准之后才由项目经理记录后续模式。

<Aside type="caution">
没有目标仓库的全新项目也能做，但事实基线换成另一套：已批准需求、交付面、目标运行与部署环境、组织技术标准，以及容量、安全、成本、运维约束。这种情况下设计出来的模块和拓扑必须标成"选定方案"，不能写成"现有模块"——两者混在一起，后面接手的人会以为代码已经存在了。同样不能从 Skill 里的示例反推技术栈。
</Aside>

## 怎么用

事实优先级是固定的：你当前给的约束 → 目标仓库里的规则和文档 → 构建文件与依赖清单 → 源码、配置、迁移、测试和部署脚本 → 最后才是 Skill 里的示例。产出会把已确认事实（附来源）、待确认假设（附验证方式）和通用建议分开写，不让候选方案冒充现状。

**先问约束，不先画图。** 用户是谁、核心用例是哪几条、要撑多少并发和多长延迟、可用性目标、合规要求、成本上限、团队会什么、什么时候要上、部署到哪、有什么不能动。跳过这一步直接画框图，画出来的东西通常撑不住真实的部署环境。

**画现状，未知就写未知。** 入口、模块、数据存储、外部系统、异步链路、部署拓扑。已有项目靠读代码，新项目这一步本来就是空的。这里最容易犯的错是拿模板补全，把"应该有的组件"画成"已经有的组件"——之后所有人都会被这张图骗。

**划边界。** 按业务能力、事务边界、数据所有权、变化频率和团队归属划：

```text
✗ 按技术层分（看起来整齐，其实没有边界）
   controller / service / mapper / entity
   → 任何一个需求都横穿四个"模块"，等于没分

✓ 按业务能力分（每个模块能独立说清自己负责什么）
   auth    认证、会话与授权        主数据：用户、角色、权限项
   org     组织、部门、岗位        主数据：部门、岗位
   audit   操作与访问日志          主数据：日志表（只写不改）
```

划完自检四句：这个模块的数据谁写；上一个需求要不要同时改两个模块才能交付（要，说明边界划错了）；它和隔壁的变化频率差得多不多；有没有哪个模块只是"放不下的东西的集合"。命名从业务能力来，沿用仓库已有的习惯，不套用示例里的名字。分层也不是默认要加——多一层就多一次转换、多一批 DTO、多一处要同步改的地方，只有职责真的不同、依赖真的需要反转，或者测试确实因此变简单，才值得加。`common` 里只放稳定且真正跨域的契约。

**把依赖方向写成能被检查的规则。**

```text
允许
  admin-web → auth（公开接口）
  org       → auth（只读用户基本信息，公开接口）
  audit     ← 全部模块（通过事件，不直接调用）

禁止
  auth → org        （会形成环）
  任何模块 → 别人的 mapper、内部包或数据表
  audit → 任何模块  （审计不能反向依赖业务）

跨边界语义
  org → auth 查用户：超时 500ms，失败降级为只显示 ID，不重试
  业务 → audit 写日志：异步事件，至少一次投递，用日志 ID 去重
```

最后那两行最容易被省掉，也是线上出问题时最贵的部分。同步调用要写清超时、幂等、熔断、错误怎么往外传，以及重试——重试只允许用在安全操作上，而且要带退避。异步事件要写清投递语义、顺序、去重与重放、死信怎么处理、Schema 怎么演进，以及可观测上靠什么串起来。

**定数据归属。** 每份主数据只能有一个写入者——定不下来，后面必然出现两处各写一半然后互相覆盖。一致性要求、幂等、历史与审计、初始化数据、迁移和回滚在这一步一起定。

**冻结两张矩阵。** 环境矩阵是这个项目全部真实环境的唯一集合，每个环境至少写清：干什么用、运行和部署边界在哪、配置从哪来、数据与外部依赖怎么隔离、从哪个环境晋级上来、有没有人工门禁——不能从固定的 dev/test/prod 模板反推，那样会漏掉预发或客户现场。仓库矩阵在这里只冻结 `repoId`、逻辑 `root` 和单仓/多仓边界，provider、remote、目标分支、direct-push 还是 PR、分支与集成策略、required checks 和批准策略由 `tech-decision` 按组织事实补齐。晋级图和仓库嵌套关系必须无环、无路径重叠、无所有权歧义。共享契约里只存逻辑 `root`，每台机器在运行时把 `repoId` 解析到自己那份 clone 的 Git 根，绝不把本机绝对路径写回团队契约。

**比候选、给演进、说验证。** 至少两个能真正落地的候选摆出来比——只给一个方案不叫设计，叫偏好。演进路径要有最小可交付切片、需要时的兼容层与双写回填、灰度开关、观察窗、回滚点，以及删除旧路径的门禁；没有回滚点的架构变更等于赌一次。验证靠依赖检查、架构测试、契约测试、空库迁移演练、负载与故障测试，或者上线后的可观测数据；验证不了的目标明确标成风险，不用"高可用"这种形容词代替指标。

### 拆不拆服务

```text
有人提议拆服务，先问这一刀解决什么
├─ "以后可能要扩展"              → 不拆。这是预感，不是理由
├─ 某个模块负载和其他差一个量级    → 可能值得拆（先证明独立扩缩的收益）
├─ 某个模块挂了不该拖垮其他        → 可能值得拆（先确认现在真的会拖垮）
├─ 数据所有权本来就该分开          → 先在单体里把边界划清，再看要不要拆
└─ 两个团队互相堵住对方发布        → 组织问题，拆能解，但先找更便宜的解法
```

拆之前还有一笔账：本来一次数据库事务能完成的事，拆完就变成跨服务一致性问题。这笔账不算，"跨服务强一致"就会被当成免费的。真要处理，优先把边界划到不需要跨服务事务，其次用 Saga、补偿或 Outbox 这类能验证的机制。缓存、搜索、消息队列、工作流引擎和对象存储同理——有真实需求和依赖证据才进方案，每加一个都要有人运维它。

### Java 业务系统的数据基线

新建 Java 业务数据在这里属于架构约束输入，具体实施仍走 `tech-decision` 和对应实施 Skill：新项目的关系型主库首选 PostgreSQL，已有系统一律沿用仓库里真实在用的那个，除非有独立迁移决策证明收益和兼容路径；主键默认用 [snowflake-id](/skills/skills-reference/low/snowflake-id/) 提供的 `IdWorkerOptions` 加 `IdWorker#nextId()`，不引 Yitter JAR，不把 MyBatis-Plus 的 `ASSIGN_ID` 当新项目默认，也不用自增；关联统一用逻辑外键字段加必要索引，完整性靠服务层和事务校验，不新增物理外键；创建部门、创建人、更新人、创建与更新时间、备注这几项语义默认保留，字段名优先沿用仓库已有的叫法；租户、逻辑删除、乐观锁、版本、状态和分区是可选能力，要从需求和仓库事实启用，不因为"以后可能要"默认加上。

<Aside type="caution">
凡是涉及具体框架 API、基类、统一响应包装、Mapper/Repository 写法和转换工具的结论，都必须先在目标仓库里找到证据。这类东西各项目差异极大，照通用示例写出来的代码往往编译不过，或者绕过了项目已有的封装。Skill 自带的条件化详细参考按当前主题按需读取（它不是废弃稿），但里面的包名、类名、字段、配置键、版本和数量必须过完事实链才能用。
</Aside>

## 与其他 Skill 的关系

"用户导出这个功能怎么做"这一句里其实塞了四层问题，分别归四个 Owner：放哪个模块、数据谁写、能不能调 auth，归这里；用哪个导出库、要不要引消息队列，归 [tech-decision](/skills/skills-reference/high/tech-decision/)（逐 Feature，选完冻结）；导出记录表怎么建、索引怎么加、迁移怎么回滚，归 [database-design](/skills/skills-reference/high/database-design/)；接口路径、校验、错误码、分页契约，归 [api-development](/skills/skills-reference/high/api-development/)。判断标准是"这个决定变了，谁要跟着重做"：边界变了，选型、表结构和接口可能全要重做；选型变了，边界通常不动。所以顺序是边界先冻结，其余后接。

```text
product-manager（产品定义）+ frontend-design（UI/UX 基线）
        ↓
architecture-design（边界 / 数据归属 / 依赖 / 环境与仓库矩阵）
        ↓
tech-decision（逐 Feature 选型并冻结）
        ↓
database-design · api-development · 各领域实现 Skill
        ↓
project-manager（把结论压进唯一 TODO）→ dev
        ↕
project-details（稳定事实原位归并）· change-impact-analysis（边界真的变了）
```

动手之前会先消费 `PROJECT-MEMORY.md` 里的 Quick facts、Reuse map、Boundaries 和契约与部署事实，已有 Owner 与边界优先复用或扩展；这一轮确认的新稳定架构事实当轮就地归并回去，由 [project-details](/skills/skills-reference/high/project-details/) 维护，不另存副本。

## 产出与验收

一份完整结论包含：范围与目标；已确认事实及来源；待确认假设及验证方式；现状与问题；候选方案与取舍；推荐边界与依赖规则；数据所有权与一致性；环境矩阵与晋级边界；仓库矩阵的 `repoId` 与 `root`；交给 `tech-decision` 的具体技术关注点；演进步骤、回滚点与验收证据；未覆盖边界与风险。非功能面这几项一项都不能缺：认证授权、敏感数据处理、容量、性能预算、可用性目标、备份与恢复、日志指标与追踪、配置与密钥、部署回滚、数据迁移、运维所有权。

判断真的完成了：每份主数据都有唯一写入者；依赖规则写成了能被工具卡住的形式；环境矩阵是项目真实环境而不是模板；仓库矩阵里只有逻辑 `root`；至少两个候选被真的比较过；演进有回滚点；验证不了的假设标成了风险，而不是留一个好看的数字；产品侧标识一个都没被改写。结论更新进项目既有架构文档，交 [project-manager](/skills/skills-reference/high/project-manager/) 压进唯一 TODO，阶段推进到技术确认。

<Aside type="note">
没拿到实现授权时，它只输出设计，不动代码、不跑迁移、不碰部署和远程系统。架构、环境或仓库矩阵后来变化时，先让 [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/) 找出受影响的 Feature 与依赖，再由项目经理在原处更新 TODO——不能让已经不满足新边界的旧实现继续挂着"完成"。
</Aside>
