## 概述

一个功能做了三天，中间换过一台机器、被压缩过一次上下文。第四天回来，怎么知道上次停在哪、当时为什么把范围定成那样？

`task-todo-workflow` 就是管这件事的。它为当前开发者维护一份 Markdown 文件，规划、执行状态和完成结果全部原位写在里面，不另开第二个状态源。这份文件里只有两样东西：一段固定顺序的阶段记录（从接需求一直到交付），和一份功能队列——队列里每个能开工的条目都带着一小段指回原始文档的"来源锚点"。

新项目、还没规划过的新功能，必须先经过它把阶段记录建起来，再进入产品、设计或实现环节。反过来做的代价很具体：方案还没定就写了两千行，然后方案改了。

<Aside type="caution">
状态机是先建起来、再往里填内容的，不是等方案都写完了回头补一份。原因很实际：换设备、上下文被压缩、或者隔三天回来，没有它就只能靠回忆重建"上次到哪了"。
</Aside>

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "我要做一个用户权限系统" | 第一次入口：建文件、定 Owner、开阶段记录 |
| "接着上次那个订单导出做" | 读出停在哪个阶段、哪一项还在做、锚点指向哪一节 |
| "这个需求确认了，往下走" | 阶段推进并留下确认证据，不是一句"已确认" |
| "等 DBA 开数据库账号" | 阶段挂上阻塞原因和恢复条件，恢复时不用重新解释 |
| "我们项目没有代码生成器" | 该阶段标成不适用并写明事实原因，不静默跳过 |
| "换了台机器接着做" | 同一 Git 身份指向同一份文件，按锚点回读原文再往下 |

触发面覆盖 TODO 维护、阶段推进、跨会话续作这一类说法，中英文都收；具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **要定义产品做什么** → [product-manager](/skills/skills-reference/critical/product-manager/)。它产出需求与验收；本 Skill 只管这些结论落进哪一份文件、现在处在哪个阶段。
- **要划模块边界与数据归属** → [architecture-design](/skills/skills-reference/high/architecture-design/)；**要选技术** → [tech-decision](/skills/skills-reference/high/tech-decision/)。
- **上游结论已经齐了，要一次把功能条目写进去** → [project-manager](/skills/skills-reference/high/project-manager/)。分工是"谁拿笔"：这边管文件在哪、现在能不能开工，那边管往里写什么内容。
- **已经在做了，只想再加一个功能** → [add-todo](/skills/skills-reference/medium/add-todo/)。它会先查重，不重建整份计划。
- **只想按事实回写某一项的状态** → [update-status](/skills/skills-reference/medium/update-status/)；**只想统计整体做到了多少** → [progress](/skills/skills-reference/medium/progress/)（只读）；**只想知道该做哪一项** → [next](/skills/skills-reference/medium/next/)。
- **要写代码** → [dev](/skills/skills-reference/high/dev/) 或 [universal-development](/skills/skills-reference/low/universal-development/)。
- **一句话问答、看一眼日志、跑一条命令** → 直接做。不跨会话的事不需要持久状态，硬套一套阶段只会让流程变重。

## 前置条件

两条门槛。

**一、这件事值得有持久状态。** 要么是新项目、尚未规划的新功能第一次进来，要么是当前开发者已有的那份 TODO 需要维护。都不满足还硬开阶段记录，得到的是一份没人会回来看的文件。

**二、开发者身份能解析出来。** 文件路径是按身份分的，身份定不下来就不知道往哪写，也没法判断哪些条目不属于你。解析顺序是：当前仓库的 Git `user.name`，规范化成小写、目录安全的 `<developer-id>`；Git identity 不可用时退到系统登录用户名；仍不可用才要求显式设置 `AGENT_DEVELOPER_NAME`。任何示例用户名都不是默认值。

身份定下来，路径也就定了：

```text
docs/<developer-id>/tasks/todo/<原文件名>.md    ← 你的唯一活动 TODO，可写
docs/<别人的 id>/tasks/todo/*.md                ← 只读：看得到进度，不勾、不合、不接管
```

迁移已有文件时保留原文件名里的日期或业务前缀，不要改成通用的 `TODO.md`——前缀往往是"这份计划属于哪件事"的唯一线索。你自己的目录里只允许有一份活动 `.md`：出现第二份时先停下来合并，而不是接着往其中一份写。两份并存的时候，"这个功能到底做完没有"就有了两个答案，而两个答案等于没有答案。

<Aside type="caution">
仓库里可能还留着老位置的文件：`docs/tasks/todo/`、`tasks/todo/`、写成单数的 `docs/<developer-id>/task/todo/`，或者更早的 Workflow / Context 目录。这些只作只读的历史兼容——发现后把内容迁进你自己的复数 `tasks/todo/` 主目录，不能继续当活动状态源用。
</Aside>

## 怎么用

说清你要做什么就行——"做一个 XX 系统"、"接着上次那个功能做"、"这个方案定了"。阶段顺序是固定的，每一段的 Owner 也是固定的：

```text
需求录入        记录入口信息，定 Owner 与文件路径
需求分析        product-manager：需求与完整产品定义
需求确认        必须拿到真实确认才能过
技术方案        architecture-design / frontend-design / tech-decision
方案确认        同样必须拿到真实确认才能过
任务拆分        project-manager：把结论写成功能队列
代码生成        code-generator：仅在确有生成器时；否则写明不适用
业务开发        dev：纵向实现与自验（生产写入从这里才解锁）
代码审查        一次完整 Review
测试阶段        test-development：仅在本轮授权或仓库强制要求时
用户验收        real-browser-automation：适用时的真实验收
Git 交付        git-commit：授权后的交付
完成
```

推进、等待确认、阻塞和恢复都是原子操作，不靠手工编辑那一行状态。重点不在命令长什么样，而在每次推进都要留下四样东西：这一段的产物路径、过关证据、下一段是谁，以及阻塞时的恢复条件。"阶段结果"那一行放的是证据而不是结论：写"产品定义已确认：3 个角色、5 个能力、用户点头通过"，和写"已完成"，三天后的价值差得远。

三件事没有商量余地：

- **两个确认段必须来自真实确认。** 自己替用户点头往下推，等于把没批过的方案变成下游的既定事实。
- **用不上的段要写清为什么用不上。** 代码生成、测试生成、用户验收经常不适用；写"不适用：项目手写代码，无生成器"和留一片空白，半年后是两回事。
- **推到业务开发、且当前实例真的领到一项之前，生产文件写不进去。** 这期间读仓库、推进状态、写规划文档都不受限；被拦下来时看一眼拒绝消息里的段名，把缺的几步走完即可。换成 shell 重定向或 `sed -i` 这类等价写入同样会被识别。

### 来源锚点：跨会话恢复靠的是它

队列里每个能开工的条目都带一段短锚点：来源文档与章节、用户结果与菜单入口、必须实现与明确不做的范围、数据与权限边界、稳定的验收编号、设计约束、选定的技术结论。它只放摘要——把上游正文抄一份进来，等于在 TODO 里维护第二份需求文档，两份很快就会不一致。

它在四个时刻被回读：第一次领这一项、继续一个还在做的 `[~]`、换 runtime 或换设备恢复之后、上下文被压缩之后。回读的结果要落成一行：

```text
来源复核：docs/product-spec.md#批量导出 -> 锚点一致
来源复核：docs/ui-design.md#导出弹窗   -> 已发现变化（新增了脱敏字段）
```

<Aside type="caution">
原文、锚点、TODO 和代码之间只要有一处对不上，正确动作是先停手：交 [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/) 把受影响的范围和验收算清、原位更新 TODO，再继续写。带着一个已知的不一致往下写，后面要返工两次——一次改代码，一次改文档。
</Aside>

### 状态与项目记忆的分工

TODO 只记"现在做到哪、卡在什么条件上"。项目上长期成立的那些约定——分页从 0 开始、异步只有一个入口、导出不落本地盘——归 `PROJECT-MEMORY.md`，由 [project-details](/skills/skills-reference/high/project-details/) 原位维护。启动、第一次领项、续作或恢复时，先读记忆里的 `Quick facts`、`Reuse map`、`Boundaries` 拿到全局约束，再按当前这一项定向翻相关章节，而不是把整份记忆贴进提示词。

仓库里不会长出第三种上下文文件：没有越写越大的 `context.json`，没有按次追加的执行日志或证据文件。代价是每次恢复要重新读一点东西，收益是不会出现一个谁都不敢删、又谁都不完全相信的巨型状态文件。

## 与其他 Skill 的关系

上游是结论的产出方：[product-manager](/skills/skills-reference/critical/product-manager/) 给需求与验收，[architecture-design](/skills/skills-reference/high/architecture-design/)、[frontend-design](/skills/skills-reference/high/frontend-design/) 和 [tech-decision](/skills/skills-reference/high/tech-decision/) 给设计与技术结论。下游是 [project-manager](/skills/skills-reference/high/project-manager/) 把这些结论写成条目，再由 [dev](/skills/skills-reference/high/dev/) 逐项实施。日常协作固定是三个：[add-todo](/skills/skills-reference/medium/add-todo/)、[update-status](/skills/skills-reference/medium/update-status/)、[progress](/skills/skills-reference/medium/progress/)。

```text
product-manager · architecture-design / frontend-design / tech-decision
        ↓
task-todo-workflow（阶段记录 + 唯一 TODO）
        ↓
project-manager（写入条目）→ dev（实施）→ code-review → git-commit
        ↕
add-todo（追加）· update-status（回写状态）· progress（只读统计）· next（挑一项）
        ↕
project-details（长期约定）· change-impact-analysis（已批准范围真的变了）
```

四个都会碰这份文件的 Skill 最容易叫错。区别在于你手上有什么、想让文件发生什么变化：

| 你的处境 | 该叫谁 | 对文件做什么 |
| --- | --- | --- |
| 什么都还没有，只有一句话的想法 | `task-todo-workflow` | 从零建文件和阶段记录，定 Owner 与路径 |
| 产品、设计、架构、技术结论都齐了 | [project-manager](/skills/skills-reference/high/project-manager/) | 一次性写入覆盖全部交付面的功能+菜单条目 |
| 已经在做了，临时加一个功能或一步 | [add-todo](/skills/skills-reference/medium/add-todo/) | 追加，并先查一遍重复 |
| 某一项做完了、状态变了 | [update-status](/skills/skills-reference/medium/update-status/) | 按代码与 Review 事实回写状态，不新增条目 |

最常见的错法是拿 `add-todo` 去开新项目：它会老实地往一份还没有阶段记录的文件里追加，结果 Owner、路径、阶段全是空的。反方向也常见——整个项目的功能一条条用 `add-todo` 加进去，比一次规划慢得多，还容易漏掉菜单和权限这类交付面。

## 产出与验收

它只产出一份文件，但这份文件要能被别人核对：

- **文件本身**：`docs/<developer-id>/tasks/todo/<原文件名>.md`，顶部写 `Owner`。
- **阶段记录**：当前段、状态、Owner、门禁、产物、已完成的段、结果、下一段、阻塞与恢复条件。已完成的段必须是当前段之前的完整前缀，缺一段就说明有人跳过了。
- **功能队列**：`[x]` 已完成、`[~]` 正在做、`[ ]` 未开始、阻塞项在同一行写原因和恢复条件。`执行实例` 只属于 `[~]`；阻塞时改写成 `最后执行实例`，供确认之后释放。
- **每次续作的那一行来源复核**，以及完成时那条带 `AC -> 证据` 的合并结果。

一项要被标成完成，得同时成立：用户能看见的功能和全部适用交付面真的接上了——菜单或按钮入口背后的那一串东西要全在，权限点、默认角色授权、后端鉴权、页面，以及页面上真实来自接口的数据，缺一样都不算；每条验收都有新鲜证据，没有一条停在未验证；开发者自验通过；一次完整 Review 没有未关闭的严重或重要 finding；已授权的提交推送完成并能从目标 ref 回读，或者文件里明确记着未授权/外部阻塞。

<Aside type="note">
勾选发生在提交之前，和业务改动进同一次 commit&push，推送后核验 local / upstream / remote 三方一致。只有远端那份文件里的 `[x]` 成立，依赖它的条目才解锁——本地勾上但没推，下一项仍然要等。
</Aside>
