## 概述

一份需求最贵的失败不是写错代码，是"看起来定义完了，其实没有"。正常流程写了，第 37 行校验失败怎么办没写；页面画了，谁能看到哪些数据没写。这些空白不会自己消失，只会被推到实现阶段，由写代码的人替你决定——而且前端答一次、后端答一次，答得还不一样。

`product-manager` 的做法是在动手之前把这些空白逼出来。它先过一道清晰度门禁：只要还有会改变产品定义的决定悬着，就只允许继续查事实，不允许输出定义。门禁过了才研究仓库已有能力、真实用户与现有替代方式、会改变方向的外部约束，做一次方案发散收敛，然后输出覆盖能力、旅程、入口、规则、权限、数据、异常与恢复、验收的定义，交给架构、技术选型和 TODO 三个下游。

它定义产品，不选技术、不写代码、不管 Git。流程上允许精简的只有重复的上下文回读、状态对象和摘要计算——研究、设计输入、功能范围和验收条件不在可砍范围内。

## 什么时候用

| 你会这样说 | 场景 |
| --- | --- |
| "我想做个内部工单系统，从零开始" | 全新项目，要从研究一路走到验收 |
| "再加一个批量导入" | 还没进过 TODO 的能力，要连异常和权限一起定 |
| "这需求我自己也没想清楚" | 先把决定问定，再动笔 |
| "有两三种做法，帮我定一个" | 一次发散收敛，落到带取舍理由的方向 |
| "验收条件怎么写才算数" | 可观察的用户结果，不是"接口已开发完成" |
| "这个功能菜单挂哪儿" | 入口，以及入口和能力、Feature、验收的映射 |

触发面覆盖全新项目启动、尚未规划过的能力定义、需求澄清与验收标准这一类说法，具体触发词由 Skill 自己的 frontmatter 维护。

## 什么时候不要用

- **已批准 TODO 的续作、Bug、编译错误、不改变行为的维护** → [dev](/skills/skills-reference/high/dev/) 或 [bug-detective](/skills/skills-reference/high/bug-detective/)。重跑一遍产品流程不会产生新结论，只让实现停下来等文档。
- **已批准范围真的变了** → [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。分界只有一个问题：这件事进过 TODO 吗。当成新需求重新定义一遍，TODO 里会出现两个描述不同的相似 Feature，执行者按哪个做都不对。
- **方向早就定了，只缺一份 PRD、OKR 或路线图** → [product-execution](/skills/skills-reference/high/product-execution/)。
- **机会本身还没验证** → [product-discovery](/skills/skills-reference/high/product-discovery/)；**要定市场、竞争与商业模式** → [product-strategy](/skills/skills-reference/high/product-strategy/)。这两个各自交付证据和产物，不负责编排整遍流程，也不承担批准。
- **要定指标口径、做漏斗与留存分析** → [product-analytics](/skills/skills-reference/medium/product-analytics/)。
- **要划模块与数据边界** → [architecture-design](/skills/skills-reference/high/architecture-design/)；**要选技术** → [tech-decision](/skills/skills-reference/high/tech-decision/)。
- **要把结论写成 TODO** → [project-manager](/skills/skills-reference/high/project-manager/)。
- **没有产品面的纯技术维护** → [universal-development](/skills/skills-reference/low/universal-development/)。

## 前置条件

1. **这一轮针对的是全新项目，或还没规划过的能力。** 已批准 TODO 的续作走这里，等于重新定义正在被实现的东西。
2. **需求确实需要被完整定义**：用户与调用方、能力、入口、规则、权限、数据边界、验收都要有答案。只改一句文案不值得走这一遍。
3. **当前开发者那份唯一 TODO 已经存在，流程状态机也已经起过**（由 [task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 建立 `intake` 阶段）。没有落点的定义谁接都不知道；也正因为有状态机，产品阶段收尾时才能带着产物和门禁证据原子推进到 `technical-plan`，而不是在回复里说一句"交给下游"。

清晰度门禁算单独一条硬要求：用户与结果、范围与非目标、核心规则、权限与数据边界、可观察验收里只要还有会改变定义的用户决定没定，就只做事实调查，并把真正的决定交给 [grilling](/skills/skills-reference/medium/grilling/) 一次一个问题问定。大约 95% 清晰之前，不输出定义，也不把假设写进 TODO。

<Aside type="caution">
不替你编数据。用户量、市场数字、负责人、日期、谁批准了、上线后能提升多少、某件事是不是已经做完——没有来源就写未知，或者回问你。这类内容一旦进了文档，下游会当成事实照着排期。
</Aside>

## 怎么用

说清你要什么就行（在 Claude Code 里也可以用 `/product-manager` 按名字直接调用；Codex 走自己的原生发现，不需要这个写法）。它会按下面的顺序推进。

**1. 过门禁，再动笔。** 先从你的输入、项目文档和源码查明能查的，剩下的真决策一次一个问。同时把 Runtime 已经读到的 `PROJECT-MEMORY.md` 相关事实逐项判成 `reuse` / `extend` / `not-applicable`，本轮确认的稳定边界、入口和规则交给 [project-details](/skills/skills-reference/high/project-details/) 原位归并。记忆是要被后面的规划真的引用的，不是拿来展示的。

**2. 声明规划档位和自主模式。** 两个维度不能互相替代：

```text
档位（这一遍走多深）
  Lite       已批准范围内的低风险续作、纯文案/配置/重命名
             → 只留目标、入口、最小验收、具名技术核对、交付面、一次验证和 Review
             → 真正的新业务能力默认不能用 Lite
  Standard   新增用户行为、页面或入口、接口、数据，或者跨层联动
             → 完整定义，并按实际变化调用设计、架构和技术 Owner
  High-risk  权限或租户、迁移或删除、公开契约、并发幂等、资金、
             跨仓与外部集成、难回滚、核心架构变化
             → Standard 之上再加风险与回滚矩阵、人工决策边界、独立方案复核

模式（能不能连续往下走）
  Goal   目标、白名单和可回滚预算都明确 → 在这个范围内连续推进
  Plan   关键需求或方案还没定，或有不可逆动作 → 只产出待批准结论，不进可领取 TODO
  Build  方案和 TODO 都批过了 → 直接续作，不重复要多方案、不重复确认文件写入
```

任何模式下遇到写集越界、外部写入、删除、Git 与发布，或者风险升档，都停在新增授权边界上。往下游只传一行结论：档位与模式、为什么这么定、保留了什么、这轮不做什么、什么条件下要升档。

**3. 研究到能改变结论为止。** 深度和风险匹配，但至少覆盖仓库已有能力与可复用模式、目标用户的任务与现有替代方式、会改变方向的市场或组织约束、权限隐私法规数据成本设备与外部系统限制，以及事实、假设、未知项和各自最便宜的验证方式。只记录会改变结论的来源，不为了形式完整堆资料。

**4. 发散一次再收敛。** 简单项可以直接确认复用现有做法；复杂项比价值、可用性、可行性、成本、风险和可逆性，这一遍交给 [brainstorm](/skills/skills-reference/medium/brainstorm/)。选中方向、关键取舍和非目标直接进定义，不额外产出一层批准对象。

**5. 把定义写全。** 十二个面里最容易漏的是异常与恢复——它要求每条功能把分支答完：

```text
功能：批量导入用户
正常      上传文件，逐行校验，给出成功条数
空        文件没有数据行 → 明确提示，不创建任何记录
错误      第 37 行邮箱格式错 → 整批回滚，还是跳过继续（这里必须选一个）
重复      同一个文件被点了两次 → 幂等键是什么
并发      两个人同时导入含相同账号的文件 → 谁赢，另一个看到什么
超时      一万行超过 60 秒 → 前端怎么表现，后台是否继续
权限不足  没有导入权限的人调接口 → 拒绝，且不泄露表结构
数据过期  导入过程中部门被删了 → 报错，还是落到未分配
取消      导入到一半能不能停，停了已导入的怎么办
```

另一个常漏的是数据与权限：数据归属、可见范围、租户或组织边界、敏感字段、审批、审计与保留规则。这一面缺了的典型后果是功能全都能用，然后发现 A 部门的人能看到 B 部门的数据。填不出来的进开放问题，不用听起来合理的内容补上。

**6. 让每个功能点回指真实用户结果。** 映射链是 `requirement -> capability -> journey -> menu/entry -> feature -> acceptance`，顺着数一遍能同时防漏和防多：

```text
✗ 按技术阶段拆（四格全勾上，用户还是不能注册）
   建表 / 写接口 / 做页面 / 联调

✓ 按用户能得到的结果拆（每格完成，用户就真的多能做一件事）
   USER-REG   用户可以用邮箱注册并激活
              交付面：数据 / 接口 / 后端 / Web / 权限
```

菜单只是入口，不是拆分依据；同一件事的数据、接口、后端、各端页面、权限和外部集成始终是一个纵向交付单元。有 Web、App 或桌面端的部分，页面结构、真实内容、状态、响应式、无障碍和权限反馈交 [frontend-design](/skills/skills-reference/high/frontend-design/) 定基线——设计结论是实现输入，不代表页面已经做完。

**7. 收尾。** 定义、门禁证据和下一步写回唯一 TODO，再推进到技术方案阶段。用户或授权 Owner 还没确认时，停在需求确认阶段等确认，不自己往前走。

## 与其他 Skill 的关系

上游只有一个：[task-todo-workflow](/skills/skills-reference/high/task-todo-workflow/) 先把流程状态机建起来，这一遍才有落点。下游有三个，顺序固定：[architecture-design](/skills/skills-reference/high/architecture-design/) 冻结系统与数据边界，[tech-decision](/skills/skills-reference/high/tech-decision/) 逐 Feature 选型，[project-manager](/skills/skills-reference/high/project-manager/) 把全部结论压进唯一 TODO。过程中按需借用 [grilling](/skills/skills-reference/medium/grilling/)、[brainstorm](/skills/skills-reference/medium/brainstorm/) 和 [frontend-design](/skills/skills-reference/high/frontend-design/)。

```text
task-todo-workflow（建状态机，推进到需求阶段）
      ↓
product-manager（门禁 → 研究 → 收敛 → 定义 → 验收）
      ↕ grilling · brainstorm · frontend-design · project-details
      ↓
architecture-design（边界）→ tech-decision（逐 Feature 选型）
      ↓
project-manager（唯一 TODO）→ dev → code-review → git-commit
```

产品侧还有一条三段式路线：[product-discovery](/skills/skills-reference/high/product-discovery/) 验证机会 → [product-strategy](/skills/skills-reference/high/product-strategy/) 定市场与商业模式 → [product-execution](/skills/skills-reference/high/product-execution/) 写成 PRD 与路线图。它的好处是每段都留下能被单独追问的产物，适合需要对外解释"为什么做这个"的场景；一次编排的好处是快，适合内部项目直接开工。最贵的是走一半——拿一份没有证据支撑的定义去排 TODO，返工会同时发生在文档、代码和测试三处。

## 产出与验收

产出直接落在项目既有文档和那份唯一 TODO 里，不再复制成逐阶段对象：完整的产品定义、能力与入口到 Feature 的映射、每个功能的规则权限数据与验收、风险与非目标，以及给下游的那一行档位结论。

判断真的完成了，逐条问：项目介绍里承诺过的能力，是不是每个都有对应功能和入口；每个功能的正常、异常、恢复路径和验收是不是都写了；有页面入口的后端能力，页面和真实接口是不是在同一个功能里；纯后端能力有没有写清真实调用方（定时任务？开放接口？内部服务？）；指标、风险、非目标和未知项是真的还是凑的；验收写的是用户能观察到的结果，还是"代码已写完"。答不上来的不要硬答，写进开放问题回问——开放问题留在文档里，比猜一个答案便宜得多。

<Aside type="note">
这一遍结束后，实现类 Skill 只消费 TODO 里的当前项。只有产品面真的发生变化才定向回到这里，其余情况走 [change-impact-analysis](/skills/skills-reference/critical/change-impact-analysis/)。
</Aside>
