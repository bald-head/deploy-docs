## 如何查阅

知道名称时，使用站点搜索或展开左侧参考手册；只知道要做什么时，先看下面的领域索引或 [Skill 目录](/skills/catalog/)。每个链接都指向独立参考页，不需要从头读完。

使用自然语言描述任务即可。显式调用时，Claude Code 使用 `/skill-name`，Codex 使用 `$skill-name`；Codex 的 `/skills` 用于浏览。示例：`/api-development 设计登录 API` 或 `$api-development 设计登录 API`，分别输入对应客户端。

| Low | 38 | 文件、设计、工具、第三方集成与兜底 |

合计 97 个框架 Skill，不包含客户端系统 Skill。优先级是源文件的职责声明和文档分组，不代表能力强弱，也不保证客户端固定评分或路由抢占。

## 先看完整任务流程

参考页解释单项能力；完整任务的前后步骤见[使用指南](/skills/usage/)。已有 TODO 直接复用确认结论，只有范围真实变化才定向重规划。

实现按实际交付面调用专业 Skill，统一自验与一次 Review。已有 Git 授权时，先把验收结果写回 TODO 并由状态机准备完成状态，再把业务改动、必要文档和该 TODO hunk 同次提交、推送。远端核验后才解锁依赖并续领下一项，具体步骤见 [Git 操作指南](/skills/usage/git-workflow/)。

## Skill 路由机制

Skills Framework 通过三层机制实现精确路由：

### 1. Frontmatter 元数据

每个 Skill 的 `SKILL.md` 包含结构化元数据：

```yaml
triggers:
  zh: [中文触发词]
  en: [English triggers]

gates:
  - "前置条件1"
  - "前置条件2"

conflicts:
  other-skill: "职责边界说明"

related_skills:
  before: [前置依赖]
  after: [后续推荐]
  complement: [协作 Skill]
```

### 2. 决策树路由

`skill-router.yaml` 只提供辅助场景匹配提示，不是 Harness 的运行时路由表，也不替代各 Skill 的 `SKILL.md`。没有目标 Harness 的真实 observation 时，不能据此宣称路由稳定或有增益。

### 3. Runtime Hook 动态提示

`UserPromptSubmit` 和 `SubagentStart` Hook 根据当前 TODO 状态和项目记忆提示适用 Skill。

详细路由机制见 [核心概念 - 路由机制](/skills/core-concepts/routing/)。

## 使用建议

### 明确调用 vs 自动路由

```bash
# Claude Code 明确调用
/code-review

# Codex 明确调用
$code-review

# 自然语言触发自动路由
"帮我设计用户登录的 API"  # → api-development
"需求改了，要加个字段"    # → change-impact-analysis
"Review 这段代码"         # → code-review
```

### 前置条件检查

部分 Skill 有明确的 gates（前置条件）：

- `change-impact-analysis`: 需要已有批准范围
- `frontend-design`: 需要已有产品定义
- `code-review`: 需要有 git diff
- `update-status`: 需要有代码变更或 Review 结果

### 冲突解决

当多个 Skill 触发词重叠时，conflicts 规则自动选择：

- **"优化页面"**: 
  - 新页面 → `frontend-design`
  - 已有页面 → `frontend-polish`
  
- **"需求改了"**: 
  - 新需求 → `product-manager`
  - 已有范围变更 → `change-impact-analysis`

### 链式调用

复杂任务通常需要多个 Skill 协作：

```
1. product-manager        # 产品定义
2. frontend-design        # UI/UX 设计
3. architecture-design    # 系统架构
4. tech-decision          # 技术选型
5. project-manager        # 生成 TODO
6. api-development        # 实现 API
7. ui-pc                  # 实现页面
8. code-review            # 代码审查
9. update-status          # 写完成摘要并准备状态
10. git-commit             # 与 TODO hunk 一次提交
```
