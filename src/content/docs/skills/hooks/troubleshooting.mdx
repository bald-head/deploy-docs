## 1. Hook 没生效

先只读检查托管配置：

```bash
node "<skills-root>/runtime-hooks/scripts/install.mjs" --check --json
```

通过条件是 `installed: true` 且 `needsInstall: false`；`files[].changed` 和 `changed` 指出差异。需要更新时运行安装器，再让客户端重新加载，详见 [安装指南](/skills/hooks/installation/)。

`sourceVersion` 和 `versions[].installedVersion` 是 Runtime Hooks 自身的版本，来自 `runtime-hooks/VERSION` 与各客户端的 `.runtime-hook-version`，不是 Codex 或 Claude Code 的客户端版本。旧记录 `0.0.0`、损坏或缺失记录显示为未知，重新运行安装器会修复；源 `VERSION` 缺失或无效时先补齐 Skills 源码，不手填客户端版本，也不需要删除 `hooks.json`。

| 客户端 | 配置文件 | 配置目录变量 |
|---|---|---|
| Claude Code | `~/.claude/settings.json` | `CLAUDE_CONFIG_DIR` |
| Codex | `~/.codex/hooks.json` 与 `~/.codex/config.toml` 的顶层 `notify` | `CODEX_HOME` |

两端都注册 SessionStart、UserPromptSubmit、SubagentStart、PreToolUse、Stop 和 SubagentStop。PermissionRequest 只在 Claude Code 注册；Codex 通知走 `notify`。

Claude Code 安装后重启会话；Codex 通过 `/hooks` 审查并信任新增或发生定义变化的 Hook。安装器使用固定 Node 路径，切换 Node 版本后需要刷新配置。

<Aside type="note">
`AGENT_RUNTIME_HOOKS_DISABLED=1` 停用 SessionStart、PreToolUse 与提示音，不会关闭上下文或 TODO 脚本。安装检查通过也不等于远端 MCP 连通。
</Aside>

## 2. Hook 卡死或响应变慢

先确认耗时发生在哪个事件。上下文注入有字节预算，超限时折叠或截断并提示读取源文件；Stop 还可能等待远端 Git 核验。

常见边界：

- 原生 Skill 发现正常时，无需开启 `AGENT_SKILL_DISCOVERY_FALLBACK=1`；兜底发现会增加目录读取。
- `skill-catalog-context.cjs --check` 可能创建项目记忆，不是对任意当前目录都只读；测量方法见 [评估与验证边界](/skills/advanced/performance-metrics/)。
- PreToolUse 会读取活动工作流状态；Git 查询较慢时，需要核对实际仓库与调用耗时。
- Stop 的长超时用于状态和远端查询，不表示 Hook 正在自动 commit 或 push。

`health-check.sh` 是旧版辅助汇总，部分固定路径和 MCP 判据可能过时，不能替代安装器与真实事件结果。

### 行为内核校验失败

如果看到 `behavior-kernel.md 必须只包含 4–8 条简短原则`，先检查共享 Skills 仓库中的唯一内核：

```bash
node "<skills-root>/runtime-hooks/scripts/skill-catalog-context.cjs" --check
```

`behavior-kernel.md` 只能包含 4–8 条非空、以 `- ` 开头的原则。原则过多时合并已有原则或移到对应 Skill 文档；不要在业务仓库新建副本，也不要删除校验来绕过。请求期间若文件缺失或损坏，Hook 会注入 `status="unavailable"` 的降级提示并成功退出，不会把每次输入拦住，也不会自动写入原则或修改源文件。修复 Skills 仓库中的唯一文件后重新运行 `--check` 和安装器，再重启客户端：

```bash
node "<skills-root>/runtime-hooks/scripts/skill-catalog-context.cjs" --check
node "<skills-root>/runtime-hooks/scripts/install.mjs"
```

`--check` 仍会严格报告格式错误；降级只用于保证请求可继续，不代表行为内核已经恢复。

## 3. 提交或命令被拦住

保留完整前缀和原因，先区分三类：

| 前缀 | 检查方向 |
|---|---|
| `危险操作已阻止：` | 命令目标和参数是否命中当前危险规则 |
| `提交信息违反安全约束：` | 提交信息是否包含被禁止的 AI 署名元数据 |
| `研发流程门禁已阻止写入：` | 活动流程阶段、状态、TODO 写入和 runtime instance |

防护检查高置信度命令模式，不是完整 Shell 或 SQL 解析器。误报也应保留真实输入和对应规则证据，定向修正，不通过换邮箱、改变命令外形或关闭 Hook 掩盖问题。

### 流程门禁

| 原因 | 处理 |
|---|---|
| 仍处于业务开发之前 | 核对已确认产物，通过状态机推进阶段 |
| `awaiting-user` 或 `blocked` | 按真实缺口完成确认或恢复 |
| 已到 `git-delivery` | 只核验状态和执行已授权 Git 交付，不继续生产编辑 |
| 当前实例未领取 Feature | 先确认 Owner、依赖与写集，再原子领取 |
| 直接写入唯一 TODO | 通过既有状态机更新，不手改 checkbox |

当前 PreToolUse 不逐文件比对并行写集。写集冲突在 TODO 状态机的解析、领取与完成检查中处理，实际 diff 仍由 Agent 收口核对。

验证防护无需执行被检查的命令。脚本导出的判定函数可只检查字符串，见 [PreToolUse Hook](/skills/hooks/pre-tool-use/#不执行目标命令的检查)。

### 凭据与测试

默认安装器跳过凭据提示；开启后也只是非阻断提醒，不改变当前配置授权。测试源码则必须由用户本轮明确要求新增或修改，高风险、覆盖率和 Review finding 不会自动授权。

## 4. 项目记忆没加载

查找顺序为根目录 `PROJECT-MEMORY.md`、`docs/PROJECT-MEMORY.md`、`docs/project-memory.md`。先确认请求工作目录在目标 Git 仓库中，并检查 `Quick facts`、`Reuse map`、`Boundaries` 是否包含真实事实。

空模板需要先由 [init-docs](/skills/skills-reference/medium/init-docs/) 采集核对，再由 [project-details](/skills/skills-reference/high/project-details/) 原位归并。不能把占位行删除后就宣称初始化完成。

摘要解析以 `##` 二级标题分节，从每个目标章节中选取相关行，必要时再补一节 Contracts、Commands 或 Open decisions。没有出现在摘要中的事实仍需直接回读源章节；示例技术栈不能当作当前项目事实。

## 5. TODO 提醒不对

TODO 规范路径是 `docs/<developer-id>/tasks/todo/<原文件名>.md`。身份优先级为 Git `user.name`、系统登录用户名、最后才是 `AGENT_DEVELOPER_NAME`；名称会规范化，优先核对注入的 `<developer_scope>`。

```bash
git rev-parse --show-toplevel
git config --get user.name
whoami
```

当前实例没有领取 Feature 时，可能没有当前项上下文，这不代表 TODO 丢失。缺少稳定 runtime instance ID 时也不能安全判断归属；优先使用 Harness 提供的实例标识。

一个实例不能同时拥有多个 `[~]`；不同实例可在依赖已经远端核验、写集和共享资源互斥时并行处理不同 Feature。多个活动 TODO 应先核对 Owner 和实例，再通过 `task-todo-workflow` 处理，不手写选择文件掩盖冲突。

Stop 没续作时，还要核对：

- 客户端是否实际发出 Stop 或 SubagentStop。
- 最后回复是否包含确认标记，表示正在等待人工接续。
- 是否处于 linked worktree，状态是否需要交回主 checkout 收口。
- 是否为 `delivery-pending`，即本地 `[x]` 与业务改动尚未同次进入 HEAD、upstream 和 remote。

本地完成 hunk 不能提前解锁下游，详见 [Stop Hook](/skills/hooks/stop/)。

## 6. 通知音频不响或响错

通知脚本提供诊断模式，只输出判定，不播放或转发：

```bash
node "<skills-root>/runtime-hooks/scripts/notify-complete.cjs" --diagnose '{"type":"agent-turn-complete","message":"done"}'
```

| 字段 | 需要核对的内容 |
|---|---|
| `enabled` | 是否被提示音或部分 Hook 开关关闭 |
| `eligible` | 事件是否属于通知类别 |
| `audioExists` | 默认或自定义音频路径是否有效 |
| `player` | 当前平台是否有可用播放器 |
| `notificationKind` | confirmation、task、reply 或 none |
| `wouldPlay` | 上述条件是否同时满足 |

macOS 使用 `afplay`，Windows 使用 PowerShell，Linux 按可用性尝试 paplay、aplay、ffplay、mpv。还要核对系统音量和输出设备。

确认事件或确认标记归为 `confirmation`；任务完成事件或完成标记归为 `task`；普通回合完成归为 `reply`。标记只影响通知分类，不能替代实际交付证据。

当前安装器在 Claude Code 只为 PermissionRequest 注册音频，Stop 归 TODO 脚本；Codex 的完成通知由 `notify` 驱动。详见 [中文语音通知](/skills/hooks/notification/)。

## 7. MCP 连不上

502、超时或握手失败是连接故障，不等于未注册。分别确认本地注册、实际连接和工具能力：

| 结论 | 判据 |
|---|---|
| 已注册 | 客户端能读取本地服务器条目 |
| 能连上 | 当前会话建立连接成功 |
| 能力可用 | 连接成功且工具列表可读 |

SessionStart 只读取 Penpot 本地注册状态，不注册、不探测、不连接远端。可用下面的只读检查核对本地状态：

```bash
node "<skills-root>/project-manager/scripts/penpot-mcp-setup.mjs" --check --json
```

查看 `configured`、`needsRegistration`、`state` 和 `urlSource`。注册存在而连接失败时，核对真实端点、网关、隧道、证书或客户端重连；不要因为一次 502 就重写注册配置。

`health-check.sh` 的旧 MCP 检查不一定读取真实用户级注册文件，以安装脚本的检查和客户端本次连接结果为准。相关操作见 [penpot](/skills/skills-reference/low/penpot/)。

## 8. nul 文件从哪来的

Windows `cmd.exe` 的空设备重定向写法在 POSIX Shell 中可能创建名为 `nul` 的普通文件。Runtime Hook 拒绝源码识别出的这类重定向，不会扫描或自动删除既有文件。

只读确认实际文件：

```bash
rg --files --hidden -g nul -g '!**/.git/**'
git status --short
```

确认是误建文件后，按精确路径处理；不要递归清理整个目录。POSIX Shell 应使用 `/dev/null`，Windows 命令则按实际 Shell 语法处理。
