## 概述

Skills Framework 使用**流程状态机**控制开发阶段，通过**档位**和**自主模式**平衡质量与效率。

<Aside type="tip">
三个正交维度：
- **流程状态机**：当前在哪个阶段（系统自动管理）
- **档位**：质量要求（Lite/Standard/High-risk）
- **自主模式**：授权范围（Goal/Plan/Build）
</Aside>

## 流程状态机

### 完整流程

新功能开发会自动经过以下阶段：

```
需求录入 → 需求分析 → 需求确认 ⚠️
  ↓
技术方案 → 方案确认 ⚠️
  ↓
任务拆分 → 代码生成
  ↓
业务开发 ✅ → 代码审查
  ↓
测试生成 → 测试运行
  ↓
用户验收 → Git 交付 → 完成
```

<Aside type="caution">
**⚠️ 关键门槛**：
- 进入"业务开发"阶段前，不允许修改生产代码
- 只能进行只读调查和规划文档编写
- 这是 PreToolUse Hook 强制执行的防护
</Aside>

### 阶段说明

#### 1. 需求录入

**目标**：采集用户需求

**Skill**：task-todo-workflow

**产物**：初始需求描述

**门槛**：无

#### 2. 需求分析

**目标**：深入理解和细化需求

**Skill**：product-manager, grilling

**产物**：PRD、用户故事、验收条件

**门槛**：需求明确性检查

#### 3. 需求确认 ⚠️

**目标**：用户或 PM 确认需求

**人工检查点**：是

**产物**：批准的需求

**门槛**：用户确认

#### 4. 技术方案

**目标**：设计架构和技术选型

**Skill**：architecture-design, tech-decision

**产物**：技术方案文档

**门槛**：需求已批准

#### 5. 方案确认 ⚠️

**目标**：架构师或 Tech Lead 确认方案

**人工检查点**：是（High-risk 档位必需）

**产物**：批准的技术方案

**门槛**：方案可行性验证

#### 6. 任务拆分

**目标**：生成完整 TODO

**Skill**：project-manager

**产物**：功能点、写集、依赖、验收

**门槛**：方案已批准

#### 7. 代码生成

**目标**：生成脚手架代码（可选）

**Skill**：code-generator, crud

**产物**：基础代码框架

**门槛**：TODO 已生成

#### 8. 业务开发 ✅

**目标**：实现业务逻辑

**Skill**：universal-development, crud-development, api-development, ui-pc 等

**产物**：功能实现代码

**门槛**：进入此阶段后才允许修改生产代码

<Aside type="tip">
**写集保护**：只能修改 TODO 中声明的写集文件，越界会被 PreToolUse Hook 拦截。
</Aside>

#### 9. 代码审查

**目标**：发现缺陷和风险

**Skill**：code-review

**产物**：Review 报告、findings

**门槛**：功能实现完成

**原则**：
- 每个功能只做一次完整 Review
- 发现问题自动修复后重新 Review
- Review 通过后不再重复审查同一 diff

#### 10. 测试生成

**目标**：编写测试代码（按需）

**Skill**：test-development, test-strategy

**产物**：单元测试、集成测试

**门槛**：
- 用户本轮明确要求，或
- 高风险功能，或
- 项目测试覆盖率要求

<Aside type="note">
**测试策略**：默认只做真实主路径验证，不自动编写测试代码。
</Aside>

#### 11. 测试运行

**目标**：执行测试验证

**Skill**：test-development

**产物**：测试报告

**门槛**：测试代码已生成

#### 12. 用户验收

**目标**：验证验收条件

**Skill**：update-status

**产物**：验收确认

**门槛**：所有 AC 通过

#### 13. Git 交付

**目标**：提交和推送代码

**Skill**：git-commit

**产物**：Git commit

**门槛**：
- Review 通过
- 验收确认
- 写集内所有文件已修改

#### 14. 完成

**目标**：标记任务完成

**Skill**：update-status

**产物**：TODO 状态更新为 `[x]`

**门槛**：Git 已推送

## 开发档位

档位决定质量要求和验证深度。

### Lite（轻量模式）

**特点**：
- 只裁剪重复文书
- 不裁剪交付面
- 快速迭代

**适用场景**：
- 简单的 CRUD 功能
- Bug 修复
- 小型优化
- 原型验证

**流程调整**：
- ✅ 保留：需求分析、技术方案、代码实现、Review
- ⚠️ 简化：PRD 可以是简单描述
- ✅ 跳过：详细的风险分析

**在 TODO 中标注**：
```markdown
## Feature: USER-LOGIN
档位: Lite
```

### Standard（标准模式）

**特点**：
- 完整规划和证据
- 标准验收流程
- 平衡质量和效率

**适用场景**：
- 常规业务功能
- API 开发
- 页面开发
- 大多数功能（默认）

**流程**：
- ✅ 完整流程状态机
- ✅ 一次完整 Review
- ✅ 真实主路径验证

**在 TODO 中标注**：
```markdown
## Feature: USER-MGMT
档位: Standard
```

<Aside type="tip">
Standard 是默认档位，不标注时使用此档位。
</Aside>

### High-risk（高风险模式）

**特点**：
- 额外的风险边界分析
- 回滚方案
- 方案复核（人工检查点）
- 发布检查

**适用场景**：
- 数据库迁移
- 认证系统变更
- 生产环境部署
- 支付、订单等关键功能
- 涉及用户数据的变更

**流程增强**：
- ✅ 强制方案确认人工检查点
- ✅ 风险边界分析
- ✅ 回滚方案（必需）
- ✅ 发布检查清单
- ✅ 更严格的 Review

**在 TODO 中标注**：
```markdown
## Feature: AUTH-MIGRATION
档位: High-risk

### 风险边界
- 影响所有用户登录
- 数据库不可逆变更
- 需要停机维护

### 回滚方案
1. 保留旧认证系统 24 小时
2. 数据库备份已确认可恢复
3. 准备降级开关

### 发布检查
- [ ] 数据库备份已验证
- [ ] 回滚脚本已测试
- [ ] 监控告警已配置
- [ ] 团队已通知维护窗口
```

<Aside type="danger">
**High-risk 强制要求**：
- 必须有回滚方案
- 必须有风险边界分析
- 必须通过方案确认检查点
- 完成摘要必须包含发布检查
</Aside>

## 自主模式

自主模式决定当前授权内可连续执行到哪里。

### Goal（目标模式）

**特点**：
- 只规划，不实施
- 输出完整 TODO
- 停在"任务拆分"阶段

**适用场景**：
- 需要人工审批预算
- 需要外部资源协调
- 技术方案不确定
- 仅做可行性研究

**流程**：
```
需求录入 → ... → 任务拆分 → [停止]
```

**在 TODO 中标注**：
```markdown
自主模式: Goal
```

**示例**：
```
我要做一个推荐系统，先规划一下需要哪些工作
```

系统会生成完整 TODO 但不开始实施。

### Plan（计划模式）

**特点**：
- 规划 + 部分实施
- 关键步骤需人工确认
- 停在每个阶段门槛

**适用场景**：
- 需要阶段性确认
- 涉及多个系统协调
- 需要外部依赖
- 学习新技术

**流程**：
```
需求录入 → 需求确认 ⚠️ [停止，等待确认]
  ↓ [确认后继续]
技术方案 → 方案确认 ⚠️ [停止，等待确认]
  ↓ [确认后继续]
任务拆分 → 业务开发 → ...
```

**在 TODO 中标注**：
```markdown
自主模式: Plan
```

### Build（构建模式）

**特点**：
- 完整实施
- 自动推进流程
- 遇到阻塞才停止

**适用场景**：
- 需求明确
- 技术方案确定
- 可独立完成
- 大多数常规功能（默认）

**流程**：
```
需求录入 → ... → Git 交付 → 完成
[全自动推进]
```

**在 TODO 中标注**：
```markdown
自主模式: Build
```

<Aside type="tip">
Build 是默认自主模式，不标注时使用此模式。
</Aside>

## 组合推荐

| 场景 | 档位 | 自主模式 | 说明 |
|------|------|---------|------|
| 快速验证原型 | Lite | Build | 最快速度看到效果 |
| 日常功能开发 | Standard | Build | 常规开发（默认） |
| 复杂新功能 | Standard | Plan | 分阶段确认降低风险 |
| 技术调研 | Lite | Goal | 只要规划不要实施 |
| 数据库迁移 | High-risk | Plan | 最高质量要求 + 人工确认 |
| Bug 修复 | Lite | Build | 快速修复 |
| 支付功能 | High-risk | Plan | 关键功能严格把控 |

## 状态转换

### 任务生命周期

```
[ ] Ready（可领取）
  ↓ 原子领取
[~] In Progress（进行中）
  ↓ 完成并验证
[x] Done（已完成）
  ↓ 自动检查依赖
[ ] Ready（后续任务变为可领取）
```

### 领取条件

任务可以被领取的条件：

1. ✅ 状态为 `[ ]` Ready
2. ✅ 所有依赖任务已完成 `[x]`
3. ✅ 写集与其他进行中任务不冲突
4. ✅ 当前开发者没有其他进行中任务（单任务模式）

### 完成条件

任务可以标记为完成的条件：

1. ✅ 所有验收条件（AC）通过
2. ✅ 所有交付面完成
3. ✅ Review 通过
4. ✅ Git 已提交推送
5. ✅ 写集内所有文件已修改

## 常见场景

### 场景 1：紧急 Bug 修复

```
档位: Lite
自主模式: Build
流程: 跳过需求分析，直接定位 → 修复 → Review → 提交
```

输入：
```
用户登录失败，报错 401
```

系统自动：
```
bug-detective（定位） → universal-development（修复） 
→ code-review → git-commit
```

### 场景 2：新功能预研

```
档位: Lite
自主模式: Goal
流程: 停在任务拆分，不实施
```

输入：
```
调研一下接入微信支付需要做哪些工作
```

系统输出：
```
完整 TODO（任务列表、依赖、工作量估算）
不开始实施
```

### 场景 3：支付功能开发

```
档位: High-risk
自主模式: Plan
流程: 每个阶段人工确认
```

输入：
```
实现微信支付功能
档位: High-risk
自主模式: Plan
```

系统行为：
```
需求分析 → [停止，请确认需求]
  ↓ 用户确认
技术方案 → [停止，请确认方案和回滚计划]
  ↓ 用户确认
实施 → Review → [停止，请确认发布检查清单]
  ↓ 用户确认
Git 交付 → 完成
```

## 调试和监控

### 查看当前阶段

```bash
cat docs/<你的名字>/tasks/todo/<project>.md
```

查找：
```markdown
## Feature: USER-LOGIN
Status: [~] In Progress
当前阶段: 业务开发 ✅
```

### 查看流程历史

```bash
git log --oneline docs/<你的名字>/tasks/todo/<project>.md
```

### 强制跳过阶段（不推荐）

```
跳过需求确认，直接开始实施
```

<Aside type="caution">
强制跳过会绕过防护门槛，可能导致返工，不推荐使用。
</Aside>

## 最佳实践

### 1. 选择合适的档位

- 默认用 Standard
- 只在明确需要时降级到 Lite
- 关键功能主动升级到 High-risk

### 2. 合理使用自主模式

- 需求不明确时用 Goal 先规划
- 复杂功能用 Plan 分阶段确认
- 日常开发用 Build 自动推进

### 3. 遵守流程门槛

- 不要强制跳过人工检查点
- 进入业务开发前确保方案已批准
- Review 通过后再提交

### 4. 写集管理

- TODO 生成时写集已确定
- 不要越界修改写集外的文件
- 并行任务确保写集互斥
