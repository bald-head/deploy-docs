## Skill 是什么？

Skill 是一个**自包含的能力单元**，封装了完成特定软件工程任务所需的全部知识和规则。每个 Skill 都是独立的，不依赖其他 Skill 的内部实现，只通过名称进行协作。

## Skill 目录结构

```
<skill-name>/
├── SKILL.md              # 完整的规则和逻辑（必需）
└── references/           # 可选的参考文档
    ├── example.md
    ├── patterns.md
    └── checklist.md
```

<Aside type="tip">
每个 Skill 必须在自身目录内自包含必要资源和事实发现门槛。兄弟 Skill 只能按名称协作，不能作为相对路径依赖。
</Aside>

## SKILL.md 结构

每个 `SKILL.md` 由两部分组成：

### 1. Frontmatter 元数据

```yaml
---
name: product-manager
description: "对新项目或新功能完成研究、brainstorm、产品定义与验收"
category: product
tags: [definition, requirements, planning]
priority: critical

triggers:
  zh:
    - 产品定义
    - 完整需求
    - 产品规划
    - 新项目
    - 新功能
    - 需求分析
    - PRD
  en:
    - product definition
    - requirements
    - PRD
    - product planning

gates:
  - "新项目或尚未规划的新功能（非已批准 TODO 的续作）"
  - "需求需要完整定义（用户、能力、菜单、规则、权限、验收）"
  - "存在唯一 TODO 文件且已执行 --plan-start"

conflicts:
  universal-development: "universal-development 负责已有产品定义的实现；product-manager 负责新项目/新功能的产品定义"
  change-impact-analysis: "change-impact-analysis 负责已有范围的变更分析；product-manager 负责新项目/新功能的完整定义"

related_skills:
  before: [task-todo-workflow]
  after: [architecture-design, tech-decision, project-manager]
  complement: [product-discovery, product-execution, brainstorm, grilling]

not_for: [已有完整PRD的实现, 纯技术维护, Bug修复, 架构设计, 技术选型]
---
```

### 2. Markdown 正文

包含详细的规则、流程、注意事项和示例。

## Frontmatter 字段详解

### name（必需）

Skill 的唯一标识符，使用小写字母和连字符。

```yaml
name: product-manager
```

### description（必需）

一句话描述 Skill 的核心用途和关键边界，用于 Skill 发现和选择。

```yaml
description: "对新项目或新功能完成研究、brainstorm、产品定义与验收"
```

### category（可选）

Skill 的分类：

- `product` - 产品相关
- `architecture` - 架构设计
- `development` - 开发实施
- `quality` - 质量保障
- `git` - Git 操作
- `special` - 特殊场景

### priority（必需）

Skill 的优先级，影响路由时的选择顺序：

- `critical` - 关键（1 个）：task-todo-workflow
- `high` - 高优先级（19 个）：核心开发流程
- `medium` - 中优先级（30 个）：专业领域
- `low` - 低优先级（35 个）：扩展功能
- `fallback` - 兜底（10 个）：通用能力

### triggers（必需）

触发词列表，支持中英文：

```yaml
triggers:
  zh:
    - 产品定义      # 精确匹配
    - 新项目        # 关键词
    - 需求改了      # 口语化表达
  en:
    - product definition
    - new project
    - requirements changed
```

<Aside type="tip">
**设计原则**：
- 至少 5-7 个中文触发词
- 包含口语化表达（如"需求改了"）
- 避免歧义（如"优化"太宽泛）
</Aside>

### gates（必需）

前置条件，用于避免过早触发或职责越界：

```yaml
gates:
  - "新项目或尚未规划的新功能"
  - "需求需要完整定义"
  - "存在唯一 TODO 文件且已执行 --plan-start"
```

**作用**：

- ✅ 避免过早触发：tech-decision 要求"尚未开始生产代码编辑"
- ✅ 确保输入完整：api-development 要求"已有相邻生产接口参考"
- ✅ 防止职责越界：bug-detective 要求"已确认是故障而非需求变更"

### conflicts（必需）

冲突解决规则，定义与其他 Skill 的职责边界：

```yaml
conflicts:
  frontend-polish: "frontend-design 负责从零设计新页面；frontend-polish 负责已有页面的优化"
  change-impact-analysis: "product-manager 负责新项目产品定义；change-impact-analysis 负责已有范围的变更分析"
```

**冲突解决示例**：

用户说"优化这个页面"：

1. 触发词匹配：`frontend-design` 和 `frontend-polish` 都匹配
2. 检查 gates：
   - `frontend-design` 要求"尚未有实现"
   - `frontend-polish` 要求"已有页面实现"
3. 检查当前状态：页面已存在
4. 应用 conflicts 规则 → 选择 `frontend-polish`

### related_skills（必需）

依赖关系，指导 Skill 的协作和路由：

```yaml
related_skills:
  before: [task-todo-workflow]                    # 通常在这些 Skill 之后执行
  after: [architecture-design, project-manager]   # 完成后应该进入这些 Skill
  complement: [brainstorm, grilling]              # 可以配合调用的 Skill
```

**依赖类型**：

- **before**：前置依赖，通常应该先执行的 Skill
- **after**：后续 Skill，完成后自动路由到这些 Skill
- **complement**：协作 Skill，可以在执行过程中调用

### not_for（可选）

明确不适用的场景，避免误用：

```yaml
not_for: [已有完整PRD的实现, 纯技术维护, Bug修复, 架构设计, 技术选型]
```

## Skill 发现机制

### 两阶段加载

Skills Framework 使用两阶段加载机制，降低上下文负担：

#### 阶段 1：发现（Discovery）

客户端原生扫描所有 Skill 的 frontmatter，提取：

- `name` - Skill 名称
- `description` - 一句话描述
- `path` - 文件路径

这些元数据用于初步匹配和选择。

#### 阶段 2：加载（Loading）

命中后才读取完整的 `SKILL.md` 正文和 `references/`。

```
用户输入 "需求改了"
↓
扫描所有 Skill frontmatter
↓
匹配 triggers.zh: "需求改了"
↓
检查 gates 和 conflicts
↓
选中 change-impact-analysis
↓
读取完整 change-impact-analysis/SKILL.md
↓
执行 Skill 逻辑
```

<Aside type="caution">
Runtime Hook 不重复注入完整 Skill 清单或正文，只提供行为内核和当前问题相关的提示。
</Aside>

### 发现路径优先级

多个路径存在同名 Skill 时，按以下优先级选择：

1. **项目局部目录**：`<项目根>/.agent-workflow/skills/`
2. **共享本地目录**：`~/.agent-workflow/skills/`
3. **system 目录**：客户端内置 Skill
4. **用户镜像目录**：`~/.claude/skills/` 或 `~/.agents/skills/`

```bash
# 查看同名覆盖情况
node runtime-hooks/scripts/skill-catalog-context.cjs --check

# 输出示例：
# Skills discovered: 95 skills
# Overrides detected:
#   - product-manager: project-local overrides shared
```

## Skill 协作方式

### 1. 顺序协作

通过 `related_skills.after` 自动路由：

```yaml
# product-manager/SKILL.md
related_skills:
  after: [architecture-design, tech-decision, project-manager]
```

执行流程：

```
product-manager（产品定义）
↓
architecture-design（架构设计）
↓
tech-decision（技术选型）
↓
project-manager（生成 TODO）
```

### 2. 并行协作

通过 `related_skills.complement` 在需要时调用：

```yaml
# product-manager/SKILL.md
related_skills:
  complement: [brainstorm, grilling]
```

执行逻辑：

```
product-manager 执行中
↓
遇到关键决策点
↓
调用 grilling（澄清问题）
↓
继续 product-manager
```

### 3. 互斥协作

通过 `conflicts` 避免职责重叠：

```yaml
# frontend-design/SKILL.md
conflicts:
  frontend-polish: "frontend-design 负责从零设计新页面；frontend-polish 负责已有页面的优化"
```

路由决策：

```
用户输入包含 "页面"
↓
匹配 frontend-design 和 frontend-polish
↓
检查当前状态：页面已存在
↓
应用 conflicts 规则
↓
选择 frontend-polish
```

## Skill 优先级规则

当多个 Skill 都匹配时，按以下顺序选择：

1. **priority 高的优先**：critical > high > medium > low > fallback
2. **gates 满足度高的优先**：所有 gates 都满足 > 部分满足
3. **触发词匹配度高的优先**：精确匹配 > 部分匹配
4. **conflicts 规则优先**：有明确职责边界的优先

示例：

```
用户输入："开发用户注册功能"

匹配结果：
1. universal-development（priority: low）
   - 触发词: "开发"
   - gates: ✓ 已有批准需求

2. crud-development（priority: high）
   - 触发词: "开发功能"
   - gates: ✓ 已有批准需求
   - conflicts: "明确 CRUD 时优先使用 crud-development"

最终选择：crud-development（priority 高 + 有明确职责边界）
```

## References 参考文档

`references/` 目录存放可选的参考文档，按需加载：

```
frontend-design/
├── SKILL.md
└── references/
    ├── visual-quality-rubric.md    # 视觉质量量规
    ├── design-patterns.md          # 设计模式
    └── accessibility-checklist.md  # 无障碍检查清单
```

**使用方式**：

```markdown
<!-- 在 SKILL.md 中引用 -->
需要具体评分时按需读取 [视觉质量量规](references/visual-quality-rubric.md)
```

<Aside type="tip">
References 不会在 Skill 发现阶段加载，只在 Skill 执行过程中按需读取，进一步降低上下文负担。
</Aside>

## Skill 自包含原则

每个 Skill 必须遵循自包含原则：

### ✅ 正确做法

```
api-development/
├── SKILL.md                        # 包含完整的 API 开发规则
└── references/
    ├── rest-conventions.md         # REST 规范
    └── error-codes.md              # 错误码设计
```

### ❌ 错误做法

```markdown
<!-- api-development/SKILL.md -->
参考 ../database-design/references/schema-patterns.md
```

**为什么？**

- ❌ 破坏了 Skill 的独立性
- ❌ 无法单独分发 api-development
- ❌ 依赖路径在不同环境可能不同

**正确做法**：

```markdown
<!-- api-development/SKILL.md -->
需要数据库设计时，协作调用 `database-design` Skill。
```

## 95 个 Skill 分类

### Critical（1 个）

- `task-todo-workflow` - 任务管理核心

产品和架构：
- `product-manager` - 产品定义

- `architecture-design` - 架构设计

- `database-design` - 数据库设计
- `frontend-design` - 前端设计
- `ui-pc` - PC 界面
- `ui-app` - 移动界面

质量保障：
- `code-review` - 代码审查
- `bug-detective` - 故障排查

Git 操作：
- `git-commit` - 提交推送
- `git-workflow` - 分支管理

- `change-impact-analysis` - 影响分析

### Low & Fallback（45 个）

文档生成、特殊工具集成、平台特定能力等。
