## Skill 是什么？

Skill 是一个**自包含的能力单元**，封装了完成特定软件工程任务所需的全部知识和规则。每个 Skill 都是独立的，不依赖其他 Skill 的内部实现，只通过名称进行协作。

## Skill 目录结构

```
<skill-name>/
├── SKILL.md              # 完整的规则和逻辑（必需）
└── references/           # 可选的参考文档
    ├── example.md
    ├── patterns.md
    └── checklist.md
```

<Aside type="tip">
每个 Skill 必须在自身目录内自包含必要资源和事实发现门槛。兄弟 Skill 只能按名称协作，不能作为相对路径依赖。
</Aside>

## SKILL.md 结构

每个 `SKILL.md` 由两部分组成：

### 1. Frontmatter 元数据

下面用一个虚构的 `invoice-export` 当例子——它不是仓库里真实存在的 Skill，只用来把字段结构讲清楚。真实 Skill 的取值请直接看它自己的 `SKILL.md`。

```yaml
---
name: invoice-export
description: "把对账明细导出成财务可直接入账的文件"
category: development
tags: [export, finance, report]
priority: medium

triggers:
  zh:
    - 导出对账单
    - 财务导出
    - 生成对账明细
  en:
    - export invoice
    - reconciliation export

gates:
  - "已确认导出字段与口径（不是还在讨论要导什么）"
  - "已有可查询的账务数据源"

conflicts:
  some-report-skill: "报表 Skill 负责屏幕上的可视化；本 Skill 负责可入账的文件产物"

related_skills:
  before: [database-design]
  after: [code-review]
  complement: [xlsx]

not_for: [口径还没定, 只是想看图表, 一次性手工取数]
---
```

### 2. Markdown 正文

包含详细的规则、流程、注意事项和示例。

## Frontmatter 字段详解

### name（必需）

Skill 的唯一标识符，使用小写字母和连字符。

```yaml
name: product-manager
```

### description（必需）

一句话描述 Skill 的核心用途和关键边界，用于 Skill 发现和选择。

```yaml
description: "把对账明细导出成财务可直接入账的文件"
```

### category（可选）

Skill 的分类：

- `product` - 产品相关
- `architecture` - 架构设计
- `development` - 开发实施
- `quality` - 质量保障
- `git` - Git 操作
- `special` - 特殊场景

### priority（必需）

Skill 的优先级，影响路由时的选择顺序：

| 取值 | 含义 | 当前数量 |
|---|---|---|
| `critical` | 范围变化与产品定义，先于一切实现 | 2 |
| `high` | 核心开发流程 | 25 |
| `medium` | 专业领域能力 | 30 |
| `low` | 扩展能力 | 38 |
| `fallback` | 兜底（当前未使用，保留取值） | 0 |

数量会随 Skill 增删变化，按桶位的完整名单以 [Skill 目录](/skills/catalog/) 为准；单个 Skill 的真实取值只看它自己 `SKILL.md` 的 `priority`。

### triggers（必需）

触发词列表，支持中英文：

```yaml
triggers:
  zh:
    - 导出对账单    # 精确匹配
    - 财务导出      # 关键词
    - 这个月的账导一下  # 口语化表达
  en:
    - export invoice
    - reconciliation export
```

<Aside type="tip">
**设计原则**：
- 至少 5-7 个中文触发词
- 带上口语化说法，用户不会照着文档背词
- 避免歧义，像"优化"这种没有领域限定的词会到处乱撞
</Aside>

### gates（必需）

前置条件，用于避免过早触发或职责越界：

```yaml
gates:
  - "已确认导出字段与口径"
  - "已有可查询的账务数据源"
```

**作用**：

- ✅ 避免过早触发：技术选型类 Skill 会要求"尚未开始生产代码编辑"
- ✅ 确保输入完整：接口类 Skill 会要求"已有相邻生产接口可参考"
- ✅ 防止职责越界：排障类 Skill 会要求"已确认是故障而不是需求变更"

具体门槛逐个 Skill 不同，以各自 `SKILL.md` 的 `gates` 为准。

### conflicts（必需）

冲突解决规则，定义与其他 Skill 的职责边界：

```yaml
conflicts:
  some-report-skill: "报表 Skill 负责屏幕上的可视化；本 Skill 负责可入账的文件产物"
  some-etl-skill: "ETL 负责把数据搬进仓；本 Skill 只负责出账务口径的文件"
```

**冲突解决示例**：

用户说"优化这个页面"：

1. 触发词匹配：`frontend-design` 和 `frontend-polish` 都匹配
2. 检查 gates：
   - `frontend-design` 要求"尚未有实现"
   - `frontend-polish` 要求"已有页面实现"
3. 检查当前状态：页面已存在
4. 应用 conflicts 规则 → 选择 `frontend-polish`

### related_skills（必需）

依赖关系，指导 Skill 的协作和路由：

```yaml
related_skills:
  before: [database-design]   # 通常在这些 Skill 之后执行
  after: [code-review]        # 完成后应该进入这些 Skill
  complement: [xlsx]          # 可以配合调用的 Skill
```

**依赖类型**：

- **before**：前置依赖，通常应该先执行的 Skill
- **after**：后续 Skill，完成后自动路由到这些 Skill
- **complement**：协作 Skill，可以在执行过程中调用

### not_for（可选）

明确不适用的场景，避免误用：

```yaml
not_for: [口径还没定, 只是想看图表, 一次性手工取数]
```

## Skill 发现机制

### 两阶段加载

Skills Framework 使用两阶段加载机制，降低上下文负担：

#### 阶段 1：发现（Discovery）

客户端原生扫描所有 Skill 的 frontmatter，提取：

- `name` - Skill 名称
- `description` - 一句话描述
- `path` - 文件路径

这些元数据用于初步匹配和选择。

#### 阶段 2：加载（Loading）

命中后才读取完整的 `SKILL.md` 正文和 `references/`。

```
用户输入 "需求改了"
↓
扫描所有 Skill frontmatter
↓
匹配 triggers.zh: "需求改了"
↓
检查 gates 和 conflicts
↓
选中 change-impact-analysis
↓
读取完整 change-impact-analysis/SKILL.md
↓
执行 Skill 逻辑
```

<Aside type="caution">
Runtime Hook 不重复注入完整 Skill 清单或正文，只提供行为内核和当前问题相关的提示。
</Aside>

### 发现路径优先级

多个路径存在同名 Skill 时，按以下优先级选择：

1. **项目局部目录**：`<项目根>/.agent-workflow/skills/`
2. **共享本地目录**：`~/.agent-workflow/skills/`
3. **system 目录**：客户端内置 Skill
4. **用户镜像目录**：`~/.claude/skills/` 或 `~/.agents/skills/`

```bash
# 查看同名覆盖情况
node runtime-hooks/scripts/skill-catalog-context.cjs --check

# 输出示例：
# Skills discovered: 95 skills
# Overrides detected:
#   - product-manager: project-local overrides shared
```

## Skill 协作方式

### 1. 顺序协作

通过 `related_skills.after` 自动路由：

```yaml
# product-manager/SKILL.md
related_skills:
  after: [architecture-design, tech-decision, project-manager]
```

执行流程：

```
product-manager（产品定义）
↓
architecture-design（架构设计）
↓
tech-decision（技术选型）
↓
project-manager（生成 TODO）
```

### 2. 并行协作

通过 `related_skills.complement` 在需要时调用：

```yaml
# product-manager/SKILL.md
related_skills:
  complement: [brainstorm, grilling]
```

执行逻辑：

```
product-manager 执行中
↓
遇到关键决策点
↓
调用 grilling（澄清问题）
↓
继续 product-manager
```

### 3. 互斥协作

通过 `conflicts` 避免职责重叠：

```yaml
# frontend-design/SKILL.md
conflicts:
  frontend-polish: "frontend-design 负责从零设计新页面；frontend-polish 负责已有页面的优化"
```

路由决策：

```
用户输入包含 "页面"
↓
匹配 frontend-design 和 frontend-polish
↓
检查当前状态：页面已存在
↓
应用 conflicts 规则
↓
选择 frontend-polish
```

## Skill 优先级规则

当多个 Skill 都匹配时，按以下顺序选择：

1. **priority 高的优先**：critical > high > medium > low > fallback
2. **gates 满足度高的优先**：所有 gates 都满足 > 部分满足
3. **触发词匹配度高的优先**：精确匹配 > 部分匹配
4. **conflicts 规则优先**：有明确职责边界的优先

示例：

```
用户输入："开发用户注册功能"

匹配结果：
1. universal-development（priority: low）
   - 触发词: "开发"
   - gates: ✓ 已有批准需求

2. crud-development（priority: high）
   - 触发词: "开发功能"
   - gates: ✓ 已有批准需求
   - conflicts: "明确 CRUD 时优先使用 crud-development"

最终选择：crud-development（priority 高 + 有明确职责边界）
```

## References 参考文档

`references/` 目录存放可选的参考文档，按需加载：

```
frontend-design/
├── SKILL.md
└── references/
    ├── visual-quality-rubric.md    # 视觉质量量规
    ├── design-patterns.md          # 设计模式
    └── accessibility-checklist.md  # 无障碍检查清单
```

**使用方式**：

```markdown
<!-- 在 SKILL.md 中引用 -->
需要具体评分时按需读取 [视觉质量量规](references/visual-quality-rubric.md)
```

<Aside type="tip">
References 不会在 Skill 发现阶段加载，只在 Skill 执行过程中按需读取，进一步降低上下文负担。
</Aside>

## Skill 自包含原则

每个 Skill 必须遵循自包含原则：

### ✅ 正确做法

```
api-development/
├── SKILL.md                        # 包含完整的 API 开发规则
└── references/
    ├── rest-conventions.md         # REST 规范
    └── error-codes.md              # 错误码设计
```

### ❌ 错误做法

```markdown
<!-- api-development/SKILL.md -->
参考 ../database-design/references/schema-patterns.md
```

**为什么？**

- ❌ 破坏了 Skill 的独立性
- ❌ 无法单独分发 api-development
- ❌ 依赖路径在不同环境可能不同

**正确做法**：

```markdown
<!-- api-development/SKILL.md -->
需要数据库设计时，协作调用 `database-design` Skill。
```

## 95 个 Skill 怎么分布

按 `priority` 分成四个在用的桶位：

| 桶位 | 数量 | 里面装的是什么 | 完整名单 |
|---|---|---|---|
| Critical | 2 | 范围变化与产品定义。这两件事没结论，后面的实现都可能白做 | [Critical & High](/skills/catalog/critical-high/) |
| High | 25 | 从项目规划、架构、逐 Feature 技术选型，一路到实现、Review、提交的主干 | [Critical & High](/skills/catalog/critical-high/) |
| Medium | 30 | 专业领域：数据库与缓存、鉴权、实时通信、定时任务、前端状态、Skill 治理 | [Medium](/skills/catalog/medium/) |
| Low | 38 | 扩展能力：文档与办公文件生成、平台集成、设计工具、增长与内容 | [Low & Fallback](/skills/catalog/low-fallback/) |

`fallback` 是保留取值，当前没有 Skill 使用。

<Aside type="caution">
桶位会随 Skill 增删和职责调整变化，这里只给形态、不逐个点名——名单写进正文就一定会过期。要查某个 Skill 归哪一桶，看它自己 `SKILL.md` 里的 `priority`；要看整桶，走上面三个目录页。
</Aside>
