## 概述

当已批准的需求发生变化时，使用 `change-impact-analysis` Skill 分析影响范围并更新 TODO。

<Aside type="caution">
**适用场景**：已有批准的范围、契约或交付面发生**真实变化**。  
**不适用**：全新需求（使用 `product-manager`）
</Aside>

## 典型场景

### 场景 1：添加字段

```
需求改了，用户表要加手机号字段
```

**自动触发**：change-impact-analysis

**分析内容**：
- 受影响的 API：注册、登录、个人资料
- 受影响的数据库：users 表结构
- 受影响的前端：注册表单、个人资料页

### 场景 2：修改业务规则

```
需求变了，注册不再需要邮箱验证，改成手机验证码
```

**分析内容**：
- 验证逻辑变更
- API 契约变化
- 第三方服务接入（短信服务）

### 场景 3：删除功能

```
产品说不要评论功能了，去掉
```

**分析内容**：
- 要删除的代码
- 依赖此功能的其他模块
- 数据库清理

## 完整流程

### 第 1 步：描述变更

明确说明什么变了：

```
需求改了，用户注册流程：
- 原来：邮箱 + 密码注册
- 现在：手机号 + 验证码注册
```

### 第 2 步：自动影响分析

系统会分析：

```markdown
## 影响分析报告

### 受影响的功能
- [x] USER-REG（用户注册）- 直接影响
- [x] USER-LOGIN（用户登录）- 登录方式变化
- [ ] USER-PROFILE（个人资料）- 无影响

### 受影响的 API
- POST /api/auth/register
  - 参数变化：email → phone
  - 新增：验证码校验
- POST /api/auth/login
  - 支持手机号登录

### 受影响的数据库
- users 表
  - 删除字段：email (需迁移)
  - 新增字段：phone, phone_verified
  - 索引调整：UNIQUE(email) → UNIQUE(phone)

### 受影响的前端
- src/pages/register.vue
  - 表单字段：邮箱输入 → 手机号输入
  - 新增：验证码输入和倒计时
- src/pages/login.vue
  - 支持手机号登录

### 第三方依赖
- 新增：短信服务（阿里云/腾讯云）

### 风险评估
- ⚠️ 高风险：数据库字段删除不可逆
- ⚠️ 中风险：已注册用户需迁移方案
- ✓ 可回滚：保留 email 字段 7 天
```

### 第 3 步：确认变更范围

系统会询问：

```
影响分析完成，建议的变更范围：
1. 修改 USER-REG 的实现
2. 修改 USER-LOGIN 的实现
3. 数据库迁移（保留 email 字段 7 天）
4. 接入短信服务

是否确认此变更范围？
```

### 第 4 步：更新 TODO

确认后，系统自动更新 TODO：

```markdown
## Feature: USER-REG - 用户注册

Status: [~] In Progress（需求变更中）

### 变更记录
- 2026-09-04: 邮箱注册 → 手机号注册

### 用户结果（已更新）
AC-001: 用户输入手机号和验证码，注册成功后跳转到首页
AC-002: 验证码错误时，显示"验证码错误"提示

### 写集（已更新）
- src/api/auth/register.ts
- src/api/auth/send-sms.ts（新增）
- src/models/user.ts
- src/pages/register.vue
- src/utils/sms-client.ts（新增）
- migrations/002_add_phone_to_users.sql（新增）
- migrations/003_drop_email_from_users.sql（7天后执行）

### 依赖（已更新）
- 新增依赖：短信服务配置
```

### 第 5 步：实施变更

按照更新后的 TODO 实施：

```
开始实施用户注册变更
```

系统会按新的写集和验收条件推进。

## 与新需求的区别

| 维度 | 需求变更 | 新需求 |
|------|---------|--------|
| **Skill** | change-impact-analysis | product-manager |
| **前提** | 已有批准的范围 | 无现有范围 |
| **输出** | 影响分析 + 更新 TODO | 新 TODO |
| **关注点** | 受影响的已有代码 | 从零设计 |

## 常见问题

### Q1: 如何判断是变更还是新需求？

```
变更：修改已有功能的行为或数据
新需求：添加全新的功能模块
```

**示例**：
- 变更："注册不要邮箱了，改成手机号"
- 新需求："增加微信登录"

### Q2: 变更太大怎么办？

如果影响范围超过 50% 的代码，建议：
1. 评估是否应该重新规划
2. 考虑分阶段实施
3. 使用 High-risk 档位

### Q3: 如何回滚变更？

```
回滚用户注册变更
```

系统会：
1. 恢复旧的 TODO 版本
2. 提示哪些代码需要回退
3. 建议 Git 回滚策略

## 最佳实践

### 1. 明确变更边界

❌ 模糊：
```
需求改了，注册有点变化
```

✅ 明确：
```
需求改了，用户注册从邮箱改成手机号，
需要接入短信验证码服务
```

### 2. 评估风险

对于不可逆变更（如删除字段），主动要求：
- 数据备份
- 回滚方案
- 灰度发布

### 3. 沟通团队

变更影响其他人时：
```
"这个变更会影响 Alice 正在做的登录功能，
需要协调一下写集"
```

### 4. 记录变更历史

每次变更都会记录在 TODO 中：
```markdown
### 变更记录
- 2026-09-01: 初始需求
- 2026-09-04: 邮箱 → 手机号
- 2026-09-06: 增加实名认证
```
