## 概述

Git 操作分给两个 Skill：

- `git-commit` 管"把这次改动准确地放进一个提交，并在授权后推上去"。
- `git-workflow` 管"分支、历史和冲突长什么样"。

边界是硬的：`git-workflow` 不写提交信息、不执行普通 commit 和功能分支 push；`git-commit` 不动分支、历史和远端 ref。

**前置条件**：
- ✅ 代码已通过一次 [代码审查](/skills/usage/code-review/)，没有未关闭的严重/重要 finding
- ✅ 你已明确授权提交（推送需要单独授权）
- ✅ 提交范围明确，知道哪些文件属于这次任务

## 分工对照

| 你要做的事 | Skill |
|---|---|
| 精确暂存、写提交信息、commit | `git-commit` |
| 功能分支 push、推送后核验 | `git-commit` |
| 建分支、切分支、删分支、打 Tag | `git-workflow` |
| merge、rebase、cherry-pick、revert | `git-workflow` |
| stash、查历史、解冲突 | `git-workflow` |
| force push、删远端 ref、改已推送历史 | `git-workflow`（且需一次性精确授权） |

"合并完顺手提交一下"这类请求会拆成两段：先由 `git-workflow` 收敛合并结果和冲突，再交给 `git-commit` 复核并提交。

## 变更日志

每个真实变更包都要同步更新仓库现有的 `CHANGELOG.md` 或等价日志路径，并与改动放在同一提交中。记录实际用户影响、兼容注意和必要恢复信息，不写未发生的发布、伪造 commit OID 或只有日志的空提交。完整格式见[变更日志指南](/skills/usage/changelog/)。

合并时先判断 Git 是否真的产生了 merge commit：

- fast-forward 只继承来源提交已有日志，不重复抄写历史，也不制造日志提交；
- 产生 merge commit 时，只补充本次合并新增的冲突解决、兼容处理或用户可见影响；
- 并行分支共享日志时，由主 Agent 在最终收口前合并并去重。

## 提交流程

### 第 1 步：确认提交范围

```bash
git status --short --branch
git diff
```

暂存必须精确到路径，甚至精确到 hunk：

```bash
# 正确: 只暂存这次任务的文件
git add src/main/java/service/OrderExportService.java
git add src/pages/order/export.vue

# 错误: 会把不属于这次任务的改动一起带走
git add .
git add -A
```

遇到下面几种情况，正确做法是**停下来报告**，而不是替你清理工作区：

- 同一个文件里既有你早先的改动又有这次任务的改动，且无法可靠拆分 hunk。
- index 里已经有不属于这次功能的 staged 路径。
- 未跟踪文件、删除、重命名、锁文件、迁移脚本的归属说不清。

不会靠 `reset`、`restore --staged`、`stash` 或者把整个文件重新暂存来"凑"出一个干净提交，那些做法都会盖掉你自己的改动。

✅ **检查点**：`git diff --cached --name-status` 列出的每个路径你都认得，都属于这次任务。

### 第 2 步：写提交信息

标题、正文段落和正文 bullet 用中文表达真实变更。Conventional Commit 的类型和 scope、`BREAKING CHANGE`、`Refs`、`Closes` 这类脚注关键字，以及路径、命令、API、类名、字段名、Issue 编号保持原样。

```bash
# 单文件、单一小修复、纯文档：只用标题
fix: 修复导出接口未按租户过滤的问题

# 多文件、接口行为、数据结构、迁移：标题加正文 bullet
feat: 新增订单导出功能

- 导出查询复用订单列表的租户与状态条件
- 区分权限不足与数据超限两类失败的错误码
- 导出页新增进度反馈与失败重试入口
```

每条 bullet 写真实行为、兼容影响或关键实现，不写"优化代码""调整逻辑"这种空话。仓库已有提交规范时以仓库为准。

### 第 3 步：提交信息里不允许出现 AI 署名

这是硬门禁，不是风格建议。提交信息里不能出现 AI 协作者、生成器或任何自动署名的元数据：

```bash
# ❌ 禁止
Co-Authored-By: Claude <noreply@anthropic.com>
Co-Authored-By: OpenAI Codex
Generated by Claude
Generated by AI
<noreply@anthropic.com>

# ✅ 只写真实变更
feat: 新增订单导出功能

- 导出查询复用订单列表的租户与状态条件
```

真实业务名称、技术名词或文件内容里合法出现的 "AI" 不受影响；`Refs`、`Closes`、`BREAKING CHANGE` 这类业务脚注照常可用。`Reviewed-by`、`Signed-off-by` 只在仓库明确要求且身份事实可证明时才写，不能照着示例编。

**Runtime Hook 会在 `PreToolUse` 阶段拦这件事**：它扫 `git commit` 命令里 `-m` / `--message` 的消息内容，命中就直接拒绝这次工具调用。实测会命中的四类模式：

| 模式 | 命中示例 |
|---|---|
| `Co-Authored-By: Claude` | `Co-Authored-By: Claude` |
| `Co-Authored-By:` 后含 Anthropic / OpenAI / `ai` 子串 | `Co-Authored-By: Anthropic`、`Co-Authored-By: 某某 AI` |
| `Generated by` + Claude / Codex / AI | `Generated by Codex` |
| Anthropic 邮箱署名 | `<noreply@anthropic.com>` |

<Aside type="caution">
Hook 是机械兜底，只看它能解析到的那段消息文本。**换一种写法没被拦下，不等于允许**：规则在 Skill 层，提交后还会重新读取最终提交正文复核一次。已经推送的提交带了署名属于历史改写，不会自动 amend 或 force push，只能保留历史或按授权追加修正。
</Aside>

<Aside type="tip">
两个实际会撞到的坑：

1. Hook 扫的是**命令原文**。用 shell（比如 heredoc）往文件里写包含这类示例提交信息的文档或脚本时，命令文本本身就命中了模式，会被拒绝。改用文件写入工具，不要走 shell。
2. `Co-Authored-By:` 后面只要出现 `ai`（不分大小写）就命中，名字里带 "ai" 的真实协作者脚注也会被拦。最稳的做法是完全不写协作者脚注。
</Aside>

### 第 4 步：推送需要明确授权

提交授权不自动包含推送。推送授权也有包络：只覆盖已确认的仓库、分支、remote 和目标 ref，不延伸到新仓库、新 ref、force、远端删除或历史改写。

```bash
# 正确: 在功能分支上用显式 refspec 推送
git push origin HEAD:refs/heads/feature/order-export

# 错误: 目标不明确，可能推到意料之外的 ref
git push
git push --all
git push --tags
```

规则：

- **不直接推 main / master**，在功能分支上开发和推送。
- 不假设 remote 叫 `origin`；多个 remote、目标不明确或处于 detached HEAD 时停下来确认。
- 已配置 upstream 时用它真实的 remote 和 remote branch；没有 upstream 时先确认目标，不靠分支同名去猜。

### 第 5 步：推送后做三方核验

"终端打印了成功"不算推上去。三个 OID 一致才算：

```bash
git rev-parse HEAD
git rev-parse @{upstream}
git ls-remote origin refs/heads/feature/order-export
git status --short --branch
```

local HEAD、upstream、目标 remote ref 三者 OID 完全一致，且分支既不 ahead 也不 behind，才记为已推送。任何一项不一致（或 remote 查询失败、没有 upstream）都按未同步处理并报告恢复条件。

跨多个仓库的功能：按真实 Git 根分别提交和推送，先做完全部仓库的范围、Review 和权限预检，再按依赖顺序推。部分成功时保留真实的已推 / 阻塞事实，不用后续"补一个提交"掩盖。

## Runtime Hook 实际拦了哪些 Git 操作

下面这张表来自对 `PreToolUse` Hook 的实测，不是清单推测：

| 命令 | 结果 |
|---|---|
| `git reset --hard <ref>` | 拒绝 |
| `git clean -fd` / `-fdx` / `--force -d` | 拒绝 |
| `git checkout -- .` / `git restore .` | 拒绝 |
| `git push --force` / `-f` | 拒绝 |
| `git push --force-with-lease` / `--force-if-includes` | 拒绝 |
| `git push origin +main:main` | 拒绝 |
| `git push origin --delete <ref>` / `git push origin :<ref>` | 拒绝 |
| `git push --mirror` / `--prune` | 拒绝 |
| `rm -rf .` / `rm -rf ~` / `rm -rf /` | 拒绝 |
| `git commit -m "..."` 消息里带 AI 署名 | 拒绝 |
| `git push origin HEAD:refs/heads/<branch>` | 放行 |
| `git status` / `git log` / `git diff` / `git show` 等只读查询 | 放行 |
| `rm -rf ./build/tmp`（明确子目录） | 放行 |

<Aside type="danger">
"拒绝"的含义是**这次工具调用不执行**，不是弹一个确认框让你点同意。Agent 不能自己绕过去。确实需要执行时有两条路：你在终端里手动执行，或者走 `git-workflow` 的一次性精确授权流程（见下）。注意 `--force-with-lease` 也在拒绝范围内。
</Aside>

### Hook 没拦、但同样需要你确认的

不在 Hook 拦截清单里，不代表可以随手执行。下面这些由 Skill 规则要求先确认：

| 操作 | 为什么仍要确认 |
|---|---|
| `git branch -D` / `-d` | 本地删分支不被 Hook 拦。删除前要确认已合并，或你明确接受丢失风险 |
| `git clean -f`（不带 `-d` / `-x`） | 不被 Hook 拦，但照样删除未跟踪文件 |
| `git rebase` | 命令本身不被拦；已推送的共享分支默认不改写历史，之后的 force push 仍单独走高风险门禁 |
| `git merge` / `git stash` | 命令本身不被拦，但会改动工作区，范围要先说清 |
| `merge --abort` / `rebase --abort` / `cherry-pick --abort` | 会丢弃冲突期间已经解决的结果，执行前要先看清将被丢弃的文件 |

<Aside type="caution">
命令防护可以在会话级关掉（见 [PreToolUse Hook](/skills/hooks/pre-tool-use/)），但那是为了处理误报，不是为了执行被拦下的操作。真要做破坏性远端写入，走授权流程比关掉守卫安全得多。
</Aside>

### 破坏性远端写入的一次性授权

force push、删除远端 ref、移动已存在的远端 Tag 这类操作，即使你之前已经授权过普通 commit & push，也要重新授权，而且授权必须精确到：

```text
仓库根 + remote 名与目标仓库身份
+ 精确 source ref 和 destination ref
+ remote 当前 oldOID
+ 计划写入的 newOID（删除时明确为 delete）
```

"可以强推"、"处理一下远端"这种说法不够。执行前会重新读一次远端 OID：和授权时的 `oldOID` 不一致，授权立即失效并重新确认；一次执行完成或失败后授权即消费，不能复用到下一个 ref 或重试后的新状态。

### 流程门禁也会影响 Git 命令

TODO 里有活动流程状态机时，`PreToolUse` 还会按阶段判断 Shell 命令：

- 只读 git 查询（`status`、`log`、`diff`、`show`、`rev-parse`、`ls-remote`、`ls-files` 等）任何阶段都放行。
- 会改动工作区的 git 子命令要等流程进入允许写入的阶段（`business-development` 之后）。
- `git-delivery` 阶段只放行交付类 git 命令：`add`、`commit`、`push`、`diff`、`diff-tree`、`log`、`ls-remote`、`rev-parse`、`rev-list`、`show`、`status`。

所以"分支或合并命令被拦住了"往往不是因为它被判成危险命令，而是流程阶段还没到。先看当前阶段，再决定是推进阶段还是换个做法。

## 分支与冲突

### 分支操作

- 建分支前确认起点 ref 和仓库命名规则，不凭习惯猜。
- 切分支前检查未提交改动。
- 删本地分支前确认已合并。删远端分支或 Tag 是独立的远端写入授权，本地删除的授权不能替代。
- 推送新 Tag 算一次单 ref 写入：写精确的 `refs/tags/<tag>:refs/tags/<tag>`，推完回读远端 OID 确认。已经存在的远端 Tag 要指向别的 commit，等同非 fast-forward 覆盖，按下面的一次性授权走。
- 切换分支默认用 `git switch`；仓库有惯用工具或 Git 版本较老时，跟着仓库来。

### 合并

```bash
# 1. 先 fetch，看清提交图和差异
git fetch origin
git log --oneline --graph origin/develop...HEAD
git diff origin/develop...HEAD

# 2. 需要产生新提交时先收敛结果，不直接生成合并提交
git merge --no-commit origin/develop
```

不使用裸 `git pull`，它会隐式替你选择是 merge 还是 rebase。合并结果先在工作区收敛好，提交这一步再走 `git-commit`。仓库要求保留 merge commit 时，按仓库自己的策略执行。

### 冲突处理

```bash
# 1. 列出冲突文件
git diff --name-only --diff-filter=U

# 2. 看双方到底改了什么
git log --merge --oneline --left-right
git diff --base -- src/main/java/service/OrderService.java

# 3. 解决后搜残留标记
grep -rn "<<<<<<<\|>>>>>>>" src/
```

步骤上只有一条重点：逐文件读懂**双方真实意图**再解决，不机械选一侧，也不用覆盖工作区的方式绕过冲突。解决完跑与冲突范围匹配的验证，然后交给 `git-commit`。

合并做不下去、又没拿到 abort 授权时，工作区就停在真实的 in-progress 状态并给出恢复命令，不会为了让结果好看而假装工作树是干净的。

### 回滚

| 情况 | 做法 |
|---|---|
| 提交已推送 | 用 `git revert --no-commit` 生成反向改动，确认反向内容和冲突都没问题后，由 `git-commit` 提交 |
| 提交未推送、需要改写 | 先说明影响再动手 |
| 丢弃本地未提交修改 | 破坏性操作，必须先列出具体文件并取得授权 |
| 已推送历史的非 fast-forward 回退 | 等同 force，普通"回滚一下"的授权不覆盖它 |

## 提交前检查清单

```markdown
- [ ] 一次 code-review 已完成，没有未关闭的严重/重要 finding
- [ ] staged 路径逐个确认属于这次任务
- [ ] 提交信息是中文，符合 Conventional Commit
- [ ] 提交信息里没有任何 AI 协作者或生成器署名
- [ ] 当前分支不是 main / master
- [ ] 推送目标 remote 和 ref 明确
- [ ] 推送后完成三方 OID 核验
```

## 常见问题

### Q1: 提交被拒了，说包含禁止的署名，可我没写

检查命令原文。Hook 扫的是整段命令文本，所以用 shell 往文件里写包含示例提交信息的文档、脚本或测试数据时也会命中。这种情况改用文件写入工具。

### Q2: 确实需要 force push 怎么办？

Hook 会拒绝，`--force-with-lease` 也一样。两条路：你在终端里手动执行，或者提供一次性精确授权（仓库根 + remote + destination ref + oldOID + newOID / delete，缺一不可）。授权执行前会重新核对远端 OID，一次用完即失效。

### Q3: push 显示成功，但队友看不到

做三方核验。常见原因是推到了另一个 remote 或另一个 ref、upstream 没配置、或者远端有保护规则实际拒绝了写入。

### Q4: 提交信息写错了能改吗？

未推送、且只改这一次提交的信息、且授权明确覆盖这次修正时可以 amend。已经推送的属于历史改写：不自动 amend，不 force push，只能保留历史或按授权追加一个修正提交。

### Q5: 一个功能改了多个仓库

按真实 Git 根分别提交推送。先做完全部仓库的范围、Review、remote / ref 和权限预检，再按契约兼容顺序推送。submodule 场景从最深层子仓推到父仓，子仓 commit 在远端可达并核验通过后，才更新指向它的父仓 gitlink。

### Q6: 分支操作被流程门禁拦住了

先看当前流程阶段，而不是找绕过方式。改动工作区的 git 命令要等阶段允许，`git-delivery` 阶段只放行交付类命令。详见 [PreToolUse Hook](/skills/hooks/pre-tool-use/)。
