## 什么时候写

每个真实变更包都要更新目标仓库已有的 `CHANGELOG.md` 或团队约定的等价日志文件。没有现成日志时，在第一次真实变更中创建；不要单独提交空日志文件。

日志至少说明：

- 用户可观察的新增、修复或行为变化；
- 兼容影响、迁移要求或回滚注意；
- 并行改动合并时新增的统一结论。

<Aside type="caution">
日志记录事实，不写未发生的发布、伪造 commit OID、命令流水、阶段状态或审计收据。
</Aside>

## 和提交一起收口

日志必须与对应代码、配置、文档和必要的 TODO 收口放在同一提交中。不能先提交业务改动、再补一个只有日志的提交，也不能把日志更新混入无关任务。

```text
真实改动
  + 必要的 CHANGELOG 条目
  + 必要的 TODO 状态收口
  -> 一次 Review
  -> 一次 commit / push
```

并行实例共享同一个日志文件时，由主 Agent 在最终收口前合并各项真实条目并去重；每个条目都要能在最终 diff 中找到依据。

## 合并分支时

- **fast-forward**：目标分支只是继承来源提交，沿用来源已有日志，不重复抄写整段 Git 历史，也不制造空日志提交。
- **产生 merge commit**：只新增这次合并带来的冲突解决、兼容处理或用户可见影响，和合并结果一起提交。
- **冲突解决**：记录最终保留的行为变化和必要恢复信息；不要把每个冲突文件逐条当成发布说明。

具体分支检查、`--no-commit` 语义和提交核验见 [Git 操作指南](/skills/usage/git-workflow/)。

## 推荐格式

```md
## [Unreleased]

### Added

- 新增会话接续指南，说明历史会话读取后的现场复核边界。

### Changed

- Git 合并指南明确 fast-forward 继承已有日志，避免重复记录。

### Fixed

- 修复快速上手页指向旧入口的问题。
```

按仓库既有章节和语言保持一致；没有真实条目时不要为了“有日志”填充占位内容。
